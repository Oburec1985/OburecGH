# Техническое задание: единая архитектура алгоритмов RecorderLnx

Статус: базовая архитектура реализована 16.07.2026 в `Algs/uRecorderAlgorithmManager.pas`; документ остаётся обязательным контрактом для развития новых типов алгоритмов.

## 1. Цель

Создать единый менеджер алгоритмов RecorderLnx, который отделяет регистрацию типов, сериализацию, жизненный цикл, готовность, обработку данных и UI настройки от конкретных реализаций. Спектр становится одним из зарегистрированных типов алгоритма, а не специальным сервисом приложения.

Референс поведения и структуры: `D:\works\OburecGH\recorder\plgControlCyclogram`, прежде всего:

- `units/uBaseAlg.pas`: `cBaseAlgContainer`, `cAlgMng`, `ready`, `doOnStart`, `doEval`, `doChangeRState`, `regObjClasses`;
- `forms/uAlgFrame.pas`: базовый настроечный frame и виртуальные `setProperties/getProperties`;
- `units/uSpm.pas`: получение общего FFT-плана через `GetFFTPlan`.

Копировать Delphi/плагинные зависимости нельзя; переносится контракт и жизненный цикл средствами FPC/LCL. Связь Recorder → менеджер, реестр тегов → менеджер и менеджер → алгоритмы выполняется явными вызовами. `EventBus` допускается для динамических внешних наблюдателей и UI-уведомлений, но не является внутренним механизмом lifecycle или доставки входов алгоритмам.

## 2. Менеджер алгоритмов

Должен существовать один `TRecorderAlgorithmManager`, принадлежащий ядру Recorder. Он обязан:

1. Регистрировать типы алгоритмов по стабильному строковому имени типа (`TypeName`).
2. Хранить фабрику runtime-класса и фабрику соответствующего LCL frame настроек.
3. Создавать алгоритм по `TypeName` при загрузке проекта.
4. Сериализовывать список алгоритмов без зависимости от Pascal `ClassName` и RTTI. Минимальная запись: `TypeName`, `Id`, общая строка свойств и список строк свойств привязок тегов.
5. Неизвестный `TypeName` не должен приводить к падению или подмене другим типом: конфигурация сохраняется как неподдерживаемая, алгоритм считается неготовым, пользователю доступна диагностика.
6. Владеть всеми экземплярами алгоритмов, вызывать их lifecycle-функции и расчёт, освобождать их до уничтожения реестра тегов/EventBus.
7. Иметь одну функцию обработки изменения состояния Recorder с явным `case` по `TRecorderStateTransition`.

Требуемая логика переходов:

- `rstStopToView`, `rstStopToRecord`: вызвать `DoStart` у всех алгоритмов;
- `rstViewToStop`, `rstRecordToStop`: вызвать `DoStop`;
- `rstViewToRecord`: не сбрасывать накопленные данные, если тип алгоритма явно не требует нового сеанса записи;
- `rstRecordToView`: вызвать `DoStopRecord`, затем при необходимости `DoStart` по контракту типа;
- загрузка/переконфигурирование: остановить вычисления, перелинковать теги, пересчитать `Ready`, подготовить планы и буферы, затем опубликовать готовность конфигурации;
- завершение приложения: остановить вычисления, уничтожить алгоритмы, затем освободить глобальные вычислительные ресурсы.

UI формы не должны самостоятельно вызывать lifecycle алгоритмов.

## 3. Базовый алгоритм

Абстрактный `TRecorderAlgorithm` должен предоставлять:

- `Id`, `TypeName`, отображаемое имя;
- общую строку `Properties`, описывающую настройки всего алгоритма;
- набор привязок к тегам, каждая имеет отдельную строку `TagProperties` со специфичными для входного тега настройками;
- `SetProperties/GetProperties`;
- `SetTagProperties/GetTagProperties`;
- `LinkTags` и удаление устаревших ссылок;
- `Ready: Boolean` и текст причины неготовности;
- `DoStart`, `DoStop`, `DoStopRecord`;
- `InputUpdated` или эквивалентную проверку версии входных данных;
- `DoEval`.

`Ready=False`, если отсутствует/удалён входной тег, источник данных неактивен, параметры некорректны, вычислительный ресурс не подготовлен либо выходной тег невозможно создать. Неготовый алгоритм не вызывается из расчётного пути. После изменения тегов, источников или конфигурации менеджер обязан повторно вычислить готовность.

`DoStart` вызывается при начале нового сеанса из Stop. В нём очищаются входные/выходные накопительные буферы, индексы кадров, счётчики усреднения, отметки версий входов и другое состояние предыдущего запуска. Выделение больших буферов и построение планов в `DoStart` запрещено: это выполняется при загрузке или переконфигурировании.

## 4. Обновление данных и DoEval

Менеджер подписывается на обновления блоков тегов. Для каждого события он:

1. определяет алгоритмы, зависящие от обновившегося входа;
2. пропускает алгоритмы с `Ready=False`;
3. сравнивает версию/счётчик входного блока с последней обработанной версией;
4. вызывает `DoEval` только при наличии новых входных данных;
5. после успешного расчёта обновляет версию входа и публикует выходные данные через реестр тегов/EventBus.

Повторная доставка одного события не должна повторно рассчитывать тот же блок. Алгоритм с несколькими входами сам объявляет условие готовности набора входов: любое обновление, все входы новой версии либо синхронизированный временной диапазон.

В горячем пути запрещены создание объектов, `SetLength`, построение FFT-планов, выбор SIMD backend, файловый/сетевой ввод-вывод и работа UI.

## 5. Настроечные frame

Для каждого `TypeName` регистрируется наследник `TRecorderAlgorithmSettingsFrame`.

Базовый frame обязан иметь виртуальные функции:

- `SetProperties(const AValue: string)` — заполнить элементы управления из строки;
- `GetProperties: string` — собрать строку из текущих элементов управления;
- аналогичные функции для `TagProperties`, если редактируется конкретная привязка;
- проверку допустимости значений без изменения runtime.

Frame получает только строку настроек и модель редактирования. Он не владеет алгоритмом, не запускает расчёт и не обращается к устройствам. Общие поля редактируются на узле алгоритма, специфичные для тега — на дочернем узле привязки. Apply сначала записывает frame в модель, затем менеджер выполняет единую переконфигурацию.

## 6. Сериализация

Формат обязан быть расширяемым и сохранять строки без знания их внутреннего состава:

```text
Algorithm.Type=Spectrum
Algorithm.Id=...
Algorithm.Properties=...
Binding.Count=N
Binding.0.TagId=...
Binding.0.TagName=...
Binding.0.Properties=...
```

Ссылка на тег хранится атомарной парой `TagId/TagName`. Загрузка сначала разрешает `TagId`, затем совместимое имя. Изменение выбранного тега обновляет оба поля. Повторное сохранение неизвестного типа не должно терять его строки.

## 7. FFT-планы спектров

Для спектров используется глобальный список неизменяемых планов, аналогичный `GetFFTPlan` из `plgControlCyclogram`:

- ключ плана — минимум `FFTSize` и, если потребуется разный алгоритм преобразования, идентификатор backend;
- первый запрос создаёт план;
- повторный запрос возвращает тот же объект;
- план хранит `BitReverse`, базис `Twiddle = exp(-i*2*pi*k/N)`, выбранную функцию преобразования и диагностическое имя backend;
- изменяемые рабочие буферы принадлежат экземпляру алгоритма/каналу, а не общему плану;
- список планов освобождается один раз при завершении приложения, после уничтожения алгоритмов.

Текущее состояние RecorderLnx уже соответствует этой части ТЗ: `TRecorderSpectrumComputeManager` глобально кэширует `TRecorderSpectrumFFTPlan` по размеру, план содержит `BitReverse/Twiddle`, выбирает численно проверенный `Pascal inline` или `AVX vector2`, а finalization освобождает менеджер. Этот код должен быть сохранён при переносе спектра под общий менеджер алгоритмов.

## 8. SIMD и выбранная техника

Использовать результаты исследований:

- `Docs/spectrum_compute_manager.md`;
- `Docs/spectrum_best_pipeline.md`;
- `Docs/notes_spectrum_math_benchmarks.md`;
- `Tests/TestSpectrumMath/uSpectrumMathBench.pas`.

Обязательная базовая техника: заранее рассчитанные `BitReverse/Twiddle`, выровненные на 64 байта рабочие буферы, inline Pascal butterfly как переносимый backend, AVX vector2 только после проверки CPU+OSXSAVE/XGETBV и сравнения результата с Pascal reference с допуском `1e-8`. Выбор backend выполняется при создании плана, не при `DoEval`. AVX-512 не является обязательным: FPC 3.2.2 не поддержал нужный inline-asm путь.

## 9. Этапы внедрения

1. Ввести базовые интерфейсы, реестр типов и сериализацию, не меняя математику спектра.
2. Ввести общий lifecycle manager и тесты таблицы переходов.
3. Обернуть существующий spectrum runtime в `TRecorderSpectrumAlgorithm`; сохранить формат старой конфигурации через миграцию.
4. Вынести spectrum frame настроек в зарегистрированный тип frame с общей и tag-specific строками.
5. Перевести доставку обновлений на dependency index менеджера и `Ready/DoEval`.
6. Удалить специальное управление спектром из `TMainForm` только после прохождения функциональных и производительных тестов.

## 10. Критерии приёмки

- Алгоритм создаётся и загружается по строковому `TypeName`.
- Неизвестный тип безопасно сохраняется и диагностируется.
- Все переходы Recorder покрыты тестом и вызывают ожидаемые lifecycle-функции ровно один раз.
- `Ready=False` исключает `DoEval`; восстановление тега возвращает алгоритм в расчёт без перезапуска приложения.
- Один входной блок рассчитывается один раз.
- Общие и tag-specific свойства проходят round-trip строка → frame → строка и проект → загрузка.
- Два спектра одинакового размера получают один план; разных размеров — разные планы.
- В `DoStart/DoEval` отсутствуют построение планов и выделение долговременной памяти.
- Численная погрешность каждого выбранного backend относительно Pascal reference не превышает `1e-8`.
- Существующие проекты со спектрами загружаются через миграцию и дают прежние спектры/оценки, кроме явно изменённых соглашений имён (`fmax` → `f1`).

## 11. Реализованная структура

- `TRecorder` владеет `TRecorderAlgorithmManager` и уничтожает его раньше spectrum runtime и реестра тегов.
- Все реализации алгоритмического слоя собраны в `Algs`: менеджер, spectrum runtime, FFT engine и частотные полосы. В `Core` остаются только универсальные сервисы Recorder.
- Менеджер расположен в `Algs`, регистрирует runtime-класс и класс настроечного frame по стабильному `TypeName`, создаёт их строковой фабрикой и владеет экземплярами.
- Базовый алгоритм хранит `Id`, имя, общие свойства, список привязок `TagId/TagName/Properties`, `Ready` и причину неготовности.
- Неизвестный тип загружается как `TRecorderUnsupportedAlgorithm`, остаётся неготовым и возвращает исходную сериализованную строку без потерь.
- `PrepareConfiguration`, проверка перехода и lifecycle вызываются из `TMainForm` явно. Внутри менеджера переходы разобраны одним `case`.
- Скалярные и блочные обновления реестр тегов передаёт менеджеру прямыми callback-вызовами. Менеджер проверяет `Ready` и `AcceptsTag`, затем вызывает `DoEvalValue/DoEvalBlock`.
- Спектр зарегистрирован как `Spectrum` и обёрнут `TRecorderSpectrumAlgorithm`; скрытые подписки spectrum runtime на EventBus удалены. EventBus остался только для публикации готового кадра динамическим UI-наблюдателям.
- Существующие FFT-планы, worker и совместимое свойство `TRecorder.SpectrumManager` сохранены. Новому коду следует обращаться к `AlgorithmManager`; совместимое свойство предназначено только для чтения спектральных кадров существующим UI.
