# OPC UA в RecorderLnx

В каталоге находится самостоятельная реализация интеграции на Object Pascal.
Она компилируется FPC вместе с RecorderLnx и не требует C/C++, DLL/SO,
open62541 или отдельного toolchain.

`open62541` и руководство из `Docs/opc ua` используются только как описание
последовательности OPC UA-сервисов и поведения пользовательского интерфейса.
Код библиотеки с приложением не связывается и в поставку не входит.

Архитектура повторяет разделение ответственности Delphi2020 `Devices/MIC-140`:

```text
uRecorderOpcUaFactory
        | создаёт и связывает
        v
uRecorderOpcUaDevice          uRecorderOpcUaDataSource
UA Binary/TCP и session  <--- lifecycle + worker + привязка тегов
                                      |
                                      v
                              TRecorderTagRegistry
```

- `uRecorderOpcUaBinaryClient` кодирует и разбирает OPC UA Binary, работает
  через кроссплатформенный TCP-слой RecorderLnx;
- `uRecorderOpcUaApi` предоставляет узкий Pascal API клиенту/серверу;
- `uRecorderOpcUaDevice` отвечает за стадии подключения и OPC UA-сессию;
- `uRecorderOpcUaDataSource` связывает каналы с тегами Recorder;
- `uRecorderOpcUaSourceEditor` содержит настройки, диагностику и поиск узлов.

Конфигурация хранится в `dataSources[].specificConfigText` как JSON. Каждый
элемент `nodes[]` содержит `nodeId`, отдельное имя тега Recorder
`tagName`, стабильную ссылку `recorderTagId`, `dataTypeNodeId`, `readable` и
`writable`. Например, `cmd_but` сохраняется как Boolean (`i=1`), чтобы
`WriteRequest` передавал серверу Variant правильного типа. Пароль в проект не
записывается: хранится только имя переменной окружения.
Переименование тега в общем редакторе не разрывает связь: runtime и
редактор OPC UA сначала разрешают `recorderTagId`, а имя подтягивают из
живого объекта `TRecorderTag`.

Редактор разделяет способы входа `Анонимно` и `Логин / пароль`. Кнопка
`Проверить связь` выполняет HEL/ACK, открытие SecureChannel с
SecurityPolicy=None, CreateSession и ActivateSession. `Найти теги` просматривает
переменные от Objects Folder, читает `AccessLevel/UserAccessLevel` и строит
дерево. По умолчанию включён упрощённый вид: `Устройство` (если сервер управляет
несколькими устройствами) -> `Каналы` -> `Только чтение` / `Чтение и запись`.
Вложенные Variable канала показываются как его подсвойства. Отдельная ветка
`Свойства` содержит параметры оборудования только для просмотра: теги Recorder
из них не создаются. Флажок `Упрощённая структура` возвращает полное
диагностическое дерево OPC UA. Найденное не добавляется в Recorder
автоматически: рабочий канал выбирается двойным щелчком и появляется в общей
таблице `Тег / Тип / Доступ / NodeId / Значение / Качество / Время`.
Успешный Browse целиком сохраняется в `browseCache` конфигурации. При
повторном открытии диалога дерево восстанавливается без сетевого запроса;
сервер перечитывается только по кнопке `Обновить дерево`.
Для конфигураций старого формата без `browseCache` редактор строит офлайн-ветку
из сохранённых используемых каналов и явно сообщает, что полное дерево надо
один раз обновить и сохранить. Во вкладке используемых каналов выбор листа
показывает его имя Recorder, endpoint, полную строку `endpoint | NodeId`,
серверное имя и путь, тип, доступ, роль, последнее значение, качество и время.
Имя Recorder в этой панели можно изменить; связь остаётся привязанной к NodeId.
В общем диалоге тега поле `Адрес` для OPC UA показывает полную строку
`источник | NodeId`, например
`OPC UA: client opc.tcp://192.168.15.130:4840 | ns=4;s=...`.
Тип берётся из атрибута OPC UA `DataType`, а не из `TypeDefinition`; цвет
иконки канала соответствует группе типа. Форма хранится в LFM, дерево и таблица
разделены рабочими голубыми сплиттерами. `Прочитать значения`
выполняет тот же числовой Read,
что DataSource, и показывает тег, NodeId, значение, качество и время. Все
сетевые операции идут в рабочем потоке.

Тестовый ПЛК: `opc.tcp://192.168.15.130:4840`.

Клиент использует синхронные пакетные Read/Write для настроенных узлов. Внешняя запись
из кнопок и полей сохраняет переходы значения тега; входящие значения
не отражаются обратно на сервер. После потери связи DataSource полностью
пересоздаёт транспорт и сессию с ограниченным backoff.

Несколько команд записи за цикл источника объединяются в один OPC UA
`WriteRequest`. Для каждого узла передаётся отдельный `WriteValue`, а размер
кадра ограничивается настройкой `maxNodesPerWrite`. Повторные команды одного
узла с одинаковым значением схлопываются, но переход `1 → 0` сохраняется и
отправляется не быстрее одного состояния на тег за такт. Запись и чтение выполняются
только на такте OPC-источника; запись идёт перед пакетным чтением.

## Параметры протокола в редакторе

В таблице настроек числовые значения применяются при сохранении источника и
используются в рабочих запросах:

- `Тип приёма` выбирается выпадающим списком: `Read` выполняет пакетные
  ReadRequest по такту источника, `Subscribe` создаёт OPC UA Subscription и
  MonitoredItems, после чего принимает изменения через Publish.
- `Период Read/публикации` задаёт период чтения или запрошенный интервал
  публикации. Сервер может вернуть скорректированный интервал; Publish ожидает
  уведомление или keep-alive. Очередь MonitoredItem настроена на последнее
  значение, так что при перегрузке применяется политика latest-value.
- `Макс. узлов за ReadRequest` ограничивает число узлов в одном пакетном Read.
- `Метка времени` выбирается из выпадающего списка `Server`, `Source`, `Both`,
  `Neither`. Режим передаётся в ReadRequest. Для числового тега выбранная UTC-
  метка преобразуется из Unix времени сервера в относительное время сессии
  Recorder; `Neither` использует время приёма.
- `Макс. узлов за WriteRequest` ограничивает размер пакетной записи.
- `Макс. ссылок на узел за BrowseRequest` задаёт лимит ссылок Browse на узел.
- `Таймаут одного Browse/BrowseNext` применяется и как socket IOTimeout, и как
  OPC UA TimeoutHint для каждого ответа Browse, BrowseNext и чтения атрибутов.
  Минимум — 30 секунд; отдельно действует обычный TimeoutHint Read/Write.

`Read` и `Subscribe` передают массивы и сложные значения в сущности «Сообщения»
как JSON. Массив содержит встроенный тип, элементы и `dimensions`, если сервер
их прислал. Скалярные встроенные типы, кроме Boolean/чисел/String, также
представляются JSON. Для `ExtensionObject` сохраняются тип NodeId, кодирование и
исходное тело Base64 (или XML). Поля пользовательской структуры не
интерпретируются без её схемы. Числовой тег предназначен для одного скалярного
числа. `HistoryRead` по-прежнему не реализован.

В конфигурации также сохраняются серверные ограничения чтения, записи и
просмотра, `TimeoutHint`, режим метки времени, тип опроса и параметры архива.
Текущая реализация применяет `maxNodesPerRead`, `maxNodesPerWrite`,
`requestTimeoutMs` для обычных запросов и `browseTimeoutMs` для каждого
ответа Browse/BrowseNext (по умолчанию 180 с, минимум 30 с). Из-за
подтверждённого ограничения PLC210 эффективный пакет
чтения временно ограничен 100 узлами: запрос 1000 узлов сервер отвергает
`BadTooManyOperations`. Остальные значения сохранены для Browse и HistoryRead.

Подробная схема и актуальный перечень ещё не реализованных возможностей
находятся в документальном снимке `Docs/opc ua/src/ARCHITECTURE.md` и
`Docs/opc ua/src/MISSING.md`.
