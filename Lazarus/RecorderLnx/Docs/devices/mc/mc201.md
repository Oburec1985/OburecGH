## Разбиение MDP-команд на куски

Полезная нагрузка Ethernet-пакета может нести до `1024` слов, но буфер
аргументов команды в оригинальном `mdpEthernet81` значительно меньше:

- `mdpEthernet81.cpp`: `MAX_TX = 32`, `SIZE_TX_ARRAY = 32`;
- `Mc031ethernetifc.cpp`: `SetSizeTXArray(ARGC_SIZE_PROPERTY / sizeof(WORD))`;
- `CMD_IDMAPUTARRAY` / `CMD_IDMAGETARRAY` имеют 5-словный заголовок аргументов:
  `slot`, `dataReg`, `idmaReg`, `address`, `count`.

Поэтому безопасный IDMA-кусок данных модуля — не `1024` слова. Он ограничен
32-словным массивом аргументов команды. Для записи PM кусок также должен быть
четным, потому что PM-адрес увеличивается на `count / 2`.

В тесте RecorderLnx используется:

```text
CMc201CommandMaxArgWords = 32
CMc201IdmaArrayHeaderWords = 5
CMc201IdmaArrayMaxDataWords = ((32 - 5) div 2) * 2 = 26
```

Проверки на стенде 2026-07-14:

- `1016` слов данных приводили к `LOAD_MC201_BIOS failed ... MDP command timeout`;
- `27` слов доходили до модуля, но сбивали выравнивание PM-адреса, затем
  загрузка BIOS заканчивалась timeout/status `0x0000`;
- `26` слов прошли живые `Config`, `STARTSCANMAIN`, прием данных и
  `STOPSCANMAIN`.

## Ускорение программирования MC-201

Оригинальный Recorder не обязан заливать BIOS модуля при каждом
программировании скана: `Module::LoadBiosIdma()` ставит состояние
`BIOS_LOADED`, а обычное `ScanModule::ModuleIdmaProgramming()` дальше
выполняет модульные команды через уже готовый BIOS.

В тесте сделан такой же быстрый путь:

1. перед полной загрузкой `.bio` в `TMc201LegacyMdpClient.LoadMc201BiosIdma`
   записывается IDMA-регистр `0x6000`;
2. читается `VAR_TMODE`;
3. если там `A5A5`, выполняется легкий `CMD_INIT` через модульный BIOS;
4. если `INIT` прошел, слот считается готовым и тяжелая загрузка `.bio`
   пропускается;
5. если признак или `INIT` не прошли, выполняется полная загрузка `.bio`.

Успешные слоты кешируются только внутри текущего TCP-клиента. Это ускоряет
повторный `Config`, но не сохраняет сомнительное состояние между разными
соединениями.

В exe вкомпилирован ресурс `MC201A_BIO` типа `MC201BIO`. Используется свой
строковый тип ресурса, а не Windows-константа `RT_RCDATA`, чтобы тот же код
работал через `TResourceStream` в Windows и Linux.

Проверка без прибора:

```powershell

```

Ожидаемый результат:

```text

```

Правило для MIC-185 и следующих устройств: все бинарники, которые нужны для
настройки железа, складывать в `resources/devices/<device>/`, добавлять в `.rc`
как отдельный именованный ресурс, а в коде читать сначала из ресурса. Файловый
путь можно оставлять только fallback для диагностики старых сборок.

## Поведение GUI/CLI

Exe по умолчанию запускает GUI. GUI дает те же низкоуровневые действия, которые
планируются для будущего класса устройства: поиск, тест, connect, поиск модулей,
config, play, stop и reset.

`--cli` запускает консольную диагностику из того же проекта и тех же исходных
модулей. Это держит протокольный код в одном месте и позволяет выполнять
автоматические проверки:

```powershell
D:\works\OburecGH\Lazarus\Tests\RecorderTests\Mc201ProtocolDebug\lib\Mc201ProtocolDebug.exe --cli --play-diagnostic-ms=1 --host=192.169.12.87 --port=4000 --timeout-ms=1200 --slots=4
```

GUI и CLI используют один `TMc032Device`; различаются только представление и
диагностика. Это сделано намеренно: при переносе в RecorderLnx граница класса
уже похожа на будущую границу устройства/источника данных.
