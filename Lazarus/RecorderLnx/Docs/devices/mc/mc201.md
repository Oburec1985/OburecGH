## Scan Start Notes

The standalone test now follows the critical original Recorder setup step from
`CCDevice::Config()`:

1. `CMD_RESETSCANMAIN`.
2. `CMD_CONFIGSCANMAIN` with CC81 Ethernet timer values from `cc81ifc.cpp`:
   `scale=1`, `period=640`; the command receives `0` and `639`.
3. MC-201 module programming from `Mc201.cpp`: module IDMA descriptor,
   stop/reset module scan, RAW/DBL/MIX channel chains, control-register write,
   grid/frequency/channel-list commands, then `GET_FINAL_FLAG_CC`.
4. Controller scan descriptors: `CMD_APPENDSCANMAIN`, `CMD_ADDCHANNELMODULE`,
   `CMD_SCAN_SET_CHANS`.
5. ADC start trigger list and `CMD_START_TRIGGERSTARTADC`.
6. Runtime start/stop: `CMD_STARTSCANMAIN` / `CMD_STOPSCANMAIN`.

Without step 2 the command `STARTSCANMAIN` succeeds, but no stream packets are
received. With it, the live acceptance command below passed on 2026-07-14:

```powershell
D:\works\OburecGH\Lazarus\Tests\RecorderTests\Mc201ProtocolDebug\lib\Mc201ProtocolDebug.exe --cli --acceptance-ms=5000 --update-ms=200 --timeout-ms=1200 --connect-attempts=3 --connect-retry-ms=1000 --slots=4
```

Observed result: `25` update blocks for 5 seconds at the default `200 ms`
update interval, with `6738` raw Ethernet frames. Typical raw frame sizes were
`266`, `532`, and `798` words.

## MDP Command Chunking

The Ethernet packet payload can carry up to `1024` words, but the original
`mdpEthernet81` command argument buffer is much smaller:

- `mdpEthernet81.cpp`: `MAX_TX = 32`, `SIZE_TX_ARRAY = 32`.
- `Mc031ethernetifc.cpp`: `SetSizeTXArray(ARGC_SIZE_PROPERTY / sizeof(WORD))`.
- `CMD_IDMAPUTARRAY` / `CMD_IDMAGETARRAY` have a 5-word argument header:
  `slot`, `dataReg`, `idmaReg`, `address`, `count`.

Therefore the safe module IDMA data chunk is not `1024` words. It is limited by
the 32-word command argument array. For PM writes the chunk must also stay even
because the PM address advances by `count / 2`.

RecorderLnx test stand uses:

```text
CMc201CommandMaxArgWords = 32
CMc201IdmaArrayHeaderWords = 5
CMc201IdmaArrayMaxDataWords = ((32 - 5) div 2) * 2 = 26
```

Live checks on 2026-07-14:

- `1016` data words reached `LOAD_MC201_BIOS failed ... MDP command timeout`.
- `27` data words reached the module but corrupted PM chunk alignment, then
  BIOS load timed out with `status=0x0000`.
- `26` data words passed live `Config`, `STARTSCANMAIN`, data reception and
  `STOPSCANMAIN`.

`TMc201LegacyMdpClient` also caches successfully loaded MC-201 BIOS slots for
the current TCP client. A repeated GUI `Config` in the same connection skips the
heavy `.bio` upload, while a fresh connection still reloads safely.

## Implementation Decisions Captured in Code

The current implementation documents these decisions directly in Pascal
comments so they survive the later move from the debug project into RecorderLnx:

| Code area | Decision |
| --- | --- |
| `uMc201ProtocolTypes.pas` | Stand defaults are the live lab setup: `192.169.12.87:4000`, four slots, `57600 Hz`. They are debug defaults, not a global RecorderLnx policy. |
| `uMc201ProtocolTypes.pas` | Raw MDP packet size (`1024` words) is separate from command argument size (`32` words). IDMA chunks are capped at `26` data words. |
| `uMc201LegacyMdpClient.pas` | GUI paths use a non-throwing TCP connect helper because `TInetSocket.Create` raises on normal timeout/refused states and stops Lazarus debugger workflows. |
| `uMc201LegacyMdpClient.pas` | MC-201 BIOS upload is cached only inside the current TCP client. A fresh connection reloads the BIOS because module memory/loader flags can be stale. |
| `uMc032Device.pas` | `Config` follows original Recorder scan programming order and leaves `CMD_STARTSCANMAIN` to `Play`. |
| `uMc032Device.pas` | `Config` performs one reset/reconnect retry after a programming failure, then reprograms from an empty module list. |
| `Mc201ProtocolDebug.lpr` | `--gui-connect-on-create-test` is a regression mode for testing the GUI connect action without mouse input. |

## GUI/CLI Behavior

The executable starts the GUI by default. The GUI exposes the same low-level
actions planned for the future device class: search, test, connect, module
scan, config, play, stop and reset.

`--cli` runs console diagnostics from the same project and source modules. This
keeps the protocol code in one place while allowing automated checks such as:

```powershell
D:\works\OburecGH\Lazarus\Tests\RecorderTests\Mc201ProtocolDebug\lib\Mc201ProtocolDebug.exe --cli --play-diagnostic-ms=1 --host=192.169.12.87 --port=4000 --timeout-ms=1200 --slots=4
```

The GUI and CLI both use `TMc032Device`; differences are limited to presentation
and diagnostics. This is intentional: when the protocol is moved into
RecorderLnx, the class boundary already matches a future device/data-source
boundary.
