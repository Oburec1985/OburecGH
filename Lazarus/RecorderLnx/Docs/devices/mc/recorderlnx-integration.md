# Интеграция MC-032 и MC-201 в RecorderLnx

## Термины и границы

`MIC-200` — название конструктива прибора, а не отдельного протокола или
контроллера. В RecorderLnx программная граница называется `MCbus`:

- `MC-032` — Ethernet-контроллер крейта и ведущий шины;
- `MC-201` — четырёхканальный измерительный модуль в слоте;
- `Device/MCbus` — весь специфичный для этой связки транспорт, протокол,
  адаптер устройства, runtime-источник и диалоги.

MIC-140 и MIC-185 не зависят от MCbus. Общая граница устройств проходит через
`TRecorderDevice`; объединять можно жизненный цикл, но не форматы MDP/Mebius.

## Карта модулей

| Модуль | Ответственность |
| --- | --- |
| `uMc201ProtocolTypes.pas` | Константы MDP/MC-201, структуры слотов, конфигурации и программирования |
| `uMc201LegacyMdpClient.pas` | TCP-поток, MDP-кадрирование, команды контроллера и модулей, IDMA, загрузка BIOS |
| `uMc201FirmwareResources.pas` | Чтение встроенного ресурса `MC201A_BIO`, файловый путь только как диагностический fallback |
| `uMc032Device.pas` | TEST, поиск слотов, программирование scan, start/read/stop и разбор вложенных BIOS-сообщений |
| `uRecorderMcbusDevice.pas` | Адаптация MC-032 + MC-201 к `TRecorderDevice`, декоммутация и сбор блока каналов |
| `uRecorderMcbusDataSource.pas` | Рабочий источник Preview: поток устройства → теги Recorder |
| `UI/uRecorderMc032SettingsDialog.pas` | Добавление контроллера, автопоиск, TEST и поиск модулей |
| `UI/uRecorderMc201SlotSettingsDialog.pas/.lfm` | Аппаратные свойства четырёх каналов выбранного MC-201 |

## Конфигурация и дерево

Источник сохраняется как `MC-032: <host>:<port>` в общем списке
`ConfiguredDataSources`. Слоты и их настройки сохраняются в конфигурационном
тексте источника. Нельзя восстанавливать дерево только из списков MIC-140,
MIC-185 и MERA: иначе MC-032 будет удалён при синхронизации реестра.

Диалог MC-032 выполняет:

1. поиск адреса в подсети `192.169.13.*`;
2. обязательный `TEST_LOAD`, подтверждающий поддерживаемый протокол;
3. чтение flash-полей слотов и распознавание MC-201/MC-201A;
4. сохранение найденных модулей после `Применить`/`OK`.

В дереве MC-032 является родителем, найденные MC-201 — дочерними узлами.
Двойной клик по дочернему узлу обязан открывать диалог слота MC-201, а не
диалог контроллера. Маршрутизация проверяет номер слота, маркер `MC-201` и
наличие родителя.

Для каждого MC-201 создаются четыре доступных канала. Имя канала имеет вид
`MC201_<индекс-источника>-<слот>-<канал>`, адрес — только цифровую часть
`<индекс-источника>-<слот>-<канал>`. Первый компонент адреса всегда равен
текущему индексу аппаратного узла. Для виртуальных тегов используется префикс
адреса `v`, а не слово `virtual`. Выбранные теги не должны повторно появляться
в списке доступных.

## Жизненный цикл Preview

Путь данных:

```text
TMainForm
  → TRecorderMcbusDataSource (рабочий поток)
  → TRecorderMcbusDevice (TRecorderDevice)
  → TMc032Device
  → TMc201LegacyMdpClient
  → MC-032 / MC-201
  → TRecorderAcquisitionBlock
  → TRecorderTagRegistry
  → визуальные компоненты
```

Последовательность подготовки и запуска:
`Connect → ProgramDevice → Start → ReadBlock`. Обычная остановка Preview
выполняет `Stop`; `Disconnect` относится к уничтожению или переконфигурации
источника. UI не читает потоковые данные.

В production `Connect → ProgramDevice` выполняются при загрузке проекта или
переконфигурировании. Успешный `Stop` сохраняет запрограммированную TCP-сессию,
поэтому следующий Preview выполняет только `STARTSCANMAIN`. Накопительные
массивы, матрица блока и массив времени повторно используются; Start/Stop не
меняют их ёмкость. Полный Disconnect выполняется при уничтожении источника.

`STOPSCANMAIN` может не получить подтверждение от контроллера. Если TCP-сессия
после этого безопасно закрыта, остановка считается завершённой, исключение в UI
не выбрасывается, а причина остаётся в логе. Teardown должен быть идемпотентным.

## Формат потока и объём данных

MDP-пакет может содержать несколько вложенных BIOS-сообщений. Его нельзя
трактовать как один канал. Для каждого вложенного сообщения:

- определяется канал по полной паре `slot + final flag`;
- первые 10 слов являются служебным заголовком и не публикуются как сигнал;
- payload накапливается отдельно по каждому из 16 каналов;
- готовый блок за 200 мс содержит 11 520 отсчётов на канал при 57 600 Гц.

Критический инвариант: `SetADSPFifoSize(256)` означает 256 отсчётов **на каждый
канал**, а не общий FIFO, делимый на 16. Деление на число каналов даёт примерно
1 700 отсчётов за 5 секунд и является ошибкой.

Проверенный результат стенда `192.169.12.87:4000`: 16 каналов, 25 блоков за
5 секунд, `25 × 11 520 = 288 000` отсчётов на канал, то есть ровно 57 600 Гц.

## Осциллограмма

Диалог показывает единый список каналов. Отдельной пользовательской сущности
«Основной канал» нет. Первый добавленный канал получает синюю линию, второй —
зелёную, третий — красную. Ограничение выбора каналами того же аппаратного
модуля сохраняется.

В модели первая линия исторически хранится в `TRecorderComponent.TagName`, а
остальные — в `TRecorderOscillogramComponent.Lines[]`. Это деталь совместимости
формата проекта, которая не должна проявляться в UI.

# Сервисные команды канала MC-201

Диалог настройки тега использует те же сервисные кнопки, что MIC-140/MIC-185:

- аппаратная настройка открывает `uRecorderMc201SlotSettingsDialog` для слота,
  вычисленного из адреса выбранного канала;
- балансировка проходит через `IRecorderZeroBalanceSupport`, затем через
  `IRecorderDevice.ExecuteDeviceAction(rdaZeroBalance, ...)`;
- чтение аппаратной калибровки вызывается через общий
  `rdaReadHardwareCalibration`.

Поддержка определяется базовым контрактом устройства, а не кодом протокола в
форме. Текущая балансировка MC-201 программная и действует до пересоздания
драйвера. Формат чтения заводской калибровки из flash MC-201 пока не портирован;
до его реализации общий вызов возвращает пользователю явную ошибку.
