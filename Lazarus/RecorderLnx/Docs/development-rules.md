# Правила разработки RecorderLnx

## Служебные файлы и журналы

- Изменяемые служебные файлы размещать только в `RecorderServicePath`
  (`<MeraFiles>\RecorderLnx`), а не рядом с EXE в Program Files.
- Ошибка открытия диагностического журнала не должна прерывать работу приложения.
  Нельзя безусловно закрывать `TextFile`, если его открытие могло завершиться ошибкой.
- Подробную покадровую трассировку графики и пакетную трассировку включать только явно
  для диагностики. В штатной сборке активен общий `LogWindows.log`/`LogLinux.log`.
- Проверка: запуск установленного приложения обычным пользователем, переход на BasePage
  и создание графиков проходят без исключений; общий журнал появляется в
  `<MeraFiles>\RecorderLnx`.

Маркер: `RLNX_SERVICE_FILES_OUTSIDE_PROGRAMFILES_2026_07_29`.

## Проверка холодного жизненного цикла оборудования

- Изменения `Connect/Init/Config` сетевого прибора принимаются только после
  аппаратной перезагрузки прибора. Тёплый Start/Stop не является проверкой Init.
- Разовые операции загрузки, reset и ожидания готовности принадлежат `Init`.
  Запись таблиц и arm-последовательность принадлежат повторяемому `Config`.
- Проверка должна подтвердить непрерывный поток дольше переходных ожиданий,
  последовательность номеров блоков и отсутствие подготовки прибора другим ПО.
- Для MIC-140 доказательства и команды приведены в
  `errors/2026-07-28-mic140-production-cold-init-fixed.md`.

Маркер: `RLNX_COLD_DEVICE_LIFECYCLE_ACCEPTANCE_2026_07_28`.

## Пути к ресурсам и системным данным

- В исходном коде запрещены абсолютные пути машины разработчика к BIOS,
  firmware, иконкам и другим неизменяемым ресурсам.
- Ресурс задаётся логическим относительным именем и разрешается через
  `RecorderResolveResourceFile`: явная настройка, `RECORDERLNX_RESOURCES`,
  `resources` рядом с exe, `Mera Files/Resources`, затем build-tree для IDE.
- Калибровки и SDB разрешаются только от `RecorderMeraFilesPath`, который
  загружается из настроек приложения; разделитель каталогов — `PathDelim`.
- Сборка обязана копировать файловые fallback-ресурсы рядом с exe. Проверка
  выполняется из рабочего каталога, не совпадающего с каталогом приложения.

Маркер: `RLNX_PORTABLE_RESOURCE_PATHS_2026_07_21`.

## Проверка сетевого устройства перед рабочим Connect

- `TestLink` является отдельным безопасным probe и не должен оставлять сокет,
  который затем неявно используется `Init/Config`: peer вправе закрыть сеанс
  после тестовой команды.
- После probe рабочий `Connect` обязан создать свежую TCP-сессию.
- Ошибка `TestLink`, `Connect`, `Init` или `Config` при автоматическом старте
  переводит только соответствующий источник в offline; она не должна выходить
  модальным исключением в общий UI.
- Проверка: при недоступном peer приложение запускается без исключения; при
  доступном peer цикл Preview/Stop получает данные и завершается штатно.

Маркер: `RLNX_DEVICE_PROBE_SESSION_ISOLATION_2026_07_21`.

## 1. Главный стиль и согласование перед кодом
### Согласование перед реализацией
Маркер правила: `RLNX_COLLAB_BEFORE_CODE`.
Перед реализацией любого нового функционала сначала задавать пользователю наводящие вопросы и фиксировать решение. Код писать только после согласования поведения, границ и ожидаемого примера/теста.
Минимальный набор вопросов перед созданием класса или крупного блока:
- Какую задачу решает функционал и кто его будет вызывать;
- Какие входы, выходы и ошибки считаются нормальными;
- В каком потоке работает код и кто владеет данными;
- Какие существующие классы/интерфейсы нужно переиспользовать;
- Какой пример использования будет одновременно тестом;
- Что записать в карту классов после реализации.

Если пользователь уже дал точное решение, уточняющие вопросы можно сократить, но шаг согласования не пропускать.
Пишем системно и неспешно. Каждый класс или крупный блок проходит цикл: назначение и место в архитектуре, публичный интерфейс, минимальная реализация, пример использования, запись в карту классов/интерфейсов, короткая заметка в `cach/plan.md` или проектной документации.
Если функционал уже есть в проекте, используем его. Если кажется, что нужно написать похожий класс, сначала проверяем существующие исходники.

### Порядок разработки функционала
Маркер правила: `RLNX_CORE_FIRST_FLOW_2026_05_25`.
Когда возникает выбор, что делать следующим, использовать постоянную последовательность RecorderLnx:
1. Сначала ядро: доменные типы, состояния, алгоритмы, потоки, структуры данных без UI.
2. Затем минимальный интерфейс наблюдения состояния, если он помогает видеть работу ядра: индикатор состояния, журнал событий, простые команды запуска/остановки без полноценной настройки.
3. Потом инструменты настройки и тестовые функции-примеры: один или несколько примеров для проверки разных режимов и демонстрации использования.
4. Потом сохранение/загрузка конфигурации для уже проверенного ядра.
5. Только после этого полноценный визуальный интерфейс настройки, который подключается к готовому ядру и конфигурации.

UI не должен становиться местом, где впервые появляется доменная логика. Минимальный интерфейс наблюдения состояния допускается рано, но он только показывает состояние и дергает готовые команды ядра. Если для UI настройки не хватает модели или конфигурации, сначала возвращаемся к ядру/примеру/сериализации.

- Один доменный параметр должен иметь в диалоге один элемент выбора. Не дублировать выбор одного канала/тега отдельными combo box для добавления и редактирования: выбранная строка списка задаёт редактируемую линию, единый selector задаёт канал, а остальные элементы меняют только свойства линии. Проверка: выбор строки восстанавливает её канал и свойства; добавление, удаление, цвет, видимость и сохранение всех линий работают без второго selector.

- В обработчике пользовательского выбора текущее выделение UI имеет приоритет над ранее сохранённым состоянием модели. Значение модели допускается только как fallback, когда control не имеет выделенной строки. Проверка: последовательные клики по двум разным объектам изменяют модель на второй объект и немедленно обновляют зависимые представления.

### Тип теста перед реализацией
Маркер правила: `RLNX_TEST_TYPE_AGREEMENT_2026_05_25`.
Перед созданием нового теста/примера в RecorderLnx сначала спрашивать пользователя, какой тип проверки нужен: отдельный консольный `.lpi`, тест внутри основного проекта, compile-time включаемый/отключаемый блок, UI-demo или другой вариант. По умолчанию для ранних UI/модельных функций предпочтительнее проверка в рамках основного проекта, если пользователь не просит отдельный тестовый проект.

## 2. Безопасное обновление и запись файлов
### Безопасное обновление файлов
Маркер правила: `RLNX_FILE_UPDATE_SAFETY_2026_05_25`.
При работе с Lazarus-проектом нельзя полагаться только на факт успешного патча или сборки: IDE может создавать `backup\`, а при копировании из backup можно случайно оставить старое время изменения или перетереть новую версию старой.
Правила обновления исходников:
- Редактировать только рабочий файл проекта, а не `backup\`, `lib\`, `__history\` или сгенерированные копии;
- После правки проверять рабочий файл по полному пути: наличие ключевых строк/методов, размер и `LastWriteTime`;
- Если восстановление делалось из backup или копированием, обновить `LastWriteTime` рабочего файла текущим временем, чтобы Lazarus предложил перечитать файл;
- Перед финальным ответом для измененных units выполнять принудительную сборку (`lazbuild -B` или `fpc -B` для теста), когда есть риск устаревших `.ppu`/`.o`;
- При подозрении на дубликаты искать файл по всему дереву проекта и сверять рабочую версию с backup;
- Не считать backup источником истины: источник истины — рабочий файл в `D:\works\OburecGH\Lazarus\RecorderLnx\...` плюс проходящий тест/сборка.

Если Lazarus не предлагает перечитать файл, первым делом проверять `LastWriteTime`, наличие дубликатов и принудительно компилировать с `-B`.

### Безопасное редактирование и патчи
- Отдавать предпочтение точечным патчам перед полной перезаписью файлов.
- Если инструмент применения патчей не может прочитать файл из-за проблем с кодировкой, не перезаписывать его вслепую. Сначала проверить текущую кодировку байт, а затем выполнить явное редактирование с сохранением кодировки или осознанную полную конвертацию.
- Если UI-исключение указывает на поле управляющего элемента (control field), убедиться, что это поле действительно создано перед использованием. Динамически создаваемые формы LCL не получают дизайнерскую инициализацию для необъявленных компонентов.

### Защита от поломки файлов при восстановлении и скриптовой записи
Маркер правила: `RLNX_SAFE_SCRIPTED_WRITES_2026_06_05`.
При восстановлении, массовой правке или редактировании файлов через скрипт нельзя писать результат сразу в рабочий исходник без промежуточной проверки. Это особенно критично для Pascal/Lazarus-файлов с CP1251/UTF-8 и для команд вида `git show ... > file`, которые при ошибке могут оставить пустой или перекодированный файл.
Правила:
- Перед записью проверить текущий размер файла и focused `git diff`;
- Восстановление или генерацию сначала писать во временный файл;
- Временный файл проверять на ненулевой размер, ожидаемые ключевые строки и корректную кодировку;
- Только после проверки заменять рабочий файл;
- После замены сразу смотреть `git diff --stat` и focused diff;
- Если diff показывает удаление всего файла, mojibake/битую кириллицу или несвязанные изменения, немедленно остановиться и восстановить файл до дальнейших правок.

## 3. Кодировки исходных файлов Lazarus / Delphi
### Смещения в UTF-8 `AnsiString`
- Не использовать литералы, полученные подсчётом видимых символов, как позиции для `Copy`, `Delete` и аналогичных операций над UTF-8 `AnsiString`.
- Вычислять границы через `Length`, `Pos`/`PosEx` или Unicode-aware API.
- Проверять парсер на входе с не-ASCII префиксом; успешная сборка не заменяет эту проверку.

### Стандарты кодировок
- Все `.pas` и текстовые `.dfm` в Delphi-проектах сохранять в `Windows-1251` (CP1251), без `BOM`, с переводами строк `CRLF`.
- Русские комментарии в Delphi-модулях разрешены и предпочтительны.
- Перед редактированием любого `*.pas` or `*.lfm` (Lazarus) файла с русским текстом проверять реальную кодировку файла и Pascal-директиву в верхней части модуля:
  - Байт-код файла и директива должны совпадать: `{$codepage UTF8}` для UTF-8 файлов, `{$codepage cp1251}` для Windows-1251 файлов.
- Не перезаписывать модули Pascal через дефолтные текстовые писатели без явного указания кодировки. Ошибки кодировки могут скомпилироваться успешно, но превратить заголовки LCL и ресурсы в `????`.
- Для UI-модулей Lazarus в кодировке UTF-8: сохранять как UTF-8 и использовать `{$codepage UTF8}`. Строки для LCL — обычные литералы, **без** `CP1251ToUTF8` (см. `Docs/source-encoding.md`, пилот: `UI/uTagSettingsDialog.pas`).
- Для устаревших модулей в cp1251: либо сохранять cp1251 без изменений, либо осознанно конвертировать весь модуль в UTF-8 и обновлять директиву в рамках одной правки (предпочтительный путь для RecorderLnx UI).
- Правило `CP1251ToUTF8` для cp1251-модулей остаётся до их миграции; новые и переведённые модули на UTF-8 этой обёртки не используют.
- После любых автоматических правок файлов `.pas/.dfm` проверять, что русские комментарии читаются именно как cp1251 (или UTF-8 для LCL), а не превратились в `????` или mojibake.
- После правок проверять:
  - файл открывается как обычный русский текст;
  - комментарии читаемы;
  - нет лишних пустых строк между строками кода;
  - нет BOM;
  - формат строк CRLF.

## 4. Стандарты кодирования и именования
### Именование переменных и типов
- Локальные переменные: префикс `l` (например, `lName`, `lNum`).
- Глобальные переменные: префикс `g_` (например, `g_DBase`), использовать только при крайней необходимости.
- Поля классов защищенные и приватные: префикс `f` (например, `fProperty`, `fName`).
- Члены классов с доступом: префикс `m_`.
- Интерфейсы: префикс `I` (например, `IRecorderCore`).
- Классы: префикс `T` (например, `TRecorderCore`).

### Lazarus/FPC стандарты
- Режим компиляции по умолчанию: `{$mode objfpc}{$H+}`.
- Не использовать API конкретной ОС в ядре без абстракции/интерфейса.
- UI строится исключительно на LCL.
- Бизнес-логику выносить из форм в отдельные модули (units).
- При создании/изменении форм Lazarus проектировать их визуально через формы `.lfm`, а не создавать элементы интерфейса динамически в коде. Это упрощает редактирование и локализацию.

### Документация в коде
Маркер правила: `RLNX_CODE_DOCS_2026_05_25`.
Каждый значимый модуль RecorderLnx должен содержать:
- Аннотацию в начале модуля: назначение, место в архитектуре, ограничения.
- Описание назначения публичных классов, функций и процедур.
- Описание параметров публичных функций/процедур.
- Комментарии внутри кода для сложных алгоритмов, переходов состояний и потоков.
Комментарии должны объяснять намерения разработчика, а не просто пересказывать код.

## 5. Потоки, память и производительность
### Владение реестрами и round-trip конфигурации
- Компонент синхронизации может удалять из общего реестра только записи типов, которыми он явно владеет. Отсутствие чужой записи в его локальном списке не означает разрешения на удаление.
- Каждое поле долговременной конфигурации должно проходить round-trip `model -> save -> load -> model` без потерь.
- При добавлении поля в модель одновременно проверять создание, копирование, очистку, сериализацию и десериализацию.
- Если параметр хранится в конфигурации устройства и одновременно проецируется
  в универсальный тег для UI, загрузка и редактирование обязаны синхронизировать
  обе модели; миграция не должна очищать проекцию тега. Проверка: после
  `save -> restart -> load` значение одинаково в диалоге, device config и
  runtime, а снятие флага также сохраняется после повторного запуска.

### Единая проекция источника в UI
- Каждый настроенный источник должен иметь одну и ту же проекцию в дерево устройств, каталог доступных каналов, выбранные теги и runtime-источник.
- Поддержка аппаратного устройства считается завершённой только при наличии полного runtime-среза: конфигурация и её round-trip, дерево и каталог каналов, фабрика `IRecorderDataSource`, lifecycle connect/program/start/stop и публикация блоков в реестр тегов. Проверка в режиме просмотра обязана подтвердить в логе создание источника и получение хотя бы одного блока; успешной компиляции и отображения каналов в настройках недостаточно.
- Принадлежность канала определять по явному `SourceId`/группе, а не по непрямому полю вроде `FileName`.
- Индекс узла аппаратного дерева в адресе канала вычислять одной общей функцией; не кодировать его независимо в UI и playback.
- Проверка: выбранный канал не показывается как доступный, не исчезает при `OK` и получает данные после повторной загрузки проекта.
### Потоки и данные
- Общий изменяемый контейнер и время жизни хранимых в нём объектов защищать одной блокировкой на всём участке поиска и использования элемента. Нельзя возвращать указатель из защищённого списка и разыменовывать его после снятия блокировки, если другой поток может удалить или очистить список. Проверка — многократный цикл `Start/Stop` под активной публикацией данных без access violation и зависаний.
- Размер аппаратного FIFO трактовать только в его документированной размерности (`на канал`, `на модуль` или `на устройство`); не делить константу повторно по числу каналов. Проверка высокочастотного источника обязана сравнивать не только число блоков, но и сумму отсчётов на канал с `Fs * duration`, а также подтверждать, что протокольные заголовки исключены из payload.
- Остановка сетевого источника должна быть идемпотентной: если команда завершения не подтверждена, но соединение безопасно закрыто, teardown не выбрасывает исключение в UI. Причина фиксируется в логе, состояние становится disconnected; проверка обязана включать цикл start/read/stop на реальном или протокольном стенде.
- UI-поток не должен выполнять сбор данных, запись файлов, сетевой обмен и тяжелую обработку.
- Рабочие потоки публикуют снимки данных (snapshots) или используют потокобезопасные очереди, а не напрямую передают изменяемые UI-объекты.
- Состояние рабочих потоков (например, play/suspend) менять только из самих потоков! Извне можно давать только команды.
- Не изменять существующие вызовы suspend в потоках, если они используются осознанно.

### Управление памятью
- В критических путях выполнения, циклах и рендеринге сводить к минимуму частые аллокации памяти (создание временных массивов или объектов).
- В RunTime (в потоках) память динамически не выделять! Вся рабочая память под буферы должна выделяться заранее на основе априорных данных.
- Очищать объекты вместо пересоздания: при смене состояний, запуске/останове использовать методы очистки (`Clear`), а не уничтожать и создавать объекты заново, чтобы не нарушать внешние ссылки на них.
- Для больших файлов данных (сигналы, осциллограммы) использовать постраничное чтение или Memory Mapping.

### Производительность и рефакторинг
Маркер правила: `RLNX_PERFORMANCE_ACCELERATION_2026_05_25`.
- Избегать поэлементных циклов там, где можно применить блочные высокопроизводительные функции (`Move`, `BlockRead`, специализированные математические методы).
- Автовыбор оптимизированной реализации вычислительного ядра не должен выполнять длительный бенчмарк при каждом запуске. Корректность кандидата проверяется отдельно, а сравнительный прогон ограничивается десятками итераций; проверка — измерение времени от загрузки конфигурации до первого аппаратного `PrepareHardware` и неизменный результат вычислительных тестов.
- `PrepareHardware` независимых источников разрешено выполнять параллельно: каждый источник обязан владеть своим транспортом, не обращаться к UI и публиковать состояние только через потокобезопасные реестры. Операции одного request/reply-протокола не распараллеливаются между потоками.
- Длительную аппаратную операцию делить на последовательную передачу и независимое ожидание готовности. Если модули используют один командный канал, команды остаются последовательными, но выдержка готовности предыдущего модуля может перекрываться передачей следующему; после группы сохраняется одна финальная выдержка. Проверка — стабильный поток каждого модуля после холодного запуска.
- По возможности использовать аппаратно-ускоренные библиотеки (например, `uHardwareMath` в Lazarus SharedUtils).
- Проектировать многопоточный код без возможности дедлоков (deadlocks): минимизировать время нахождения в критических секциях, соблюдать строгий порядок захвата блокировок, избегать вложенных блокировок.
- Предотвращение избыточной перерисовки UI: UI должен перерисовываться по таймеру с фиксированной частотой (например, 5 Гц / 200 мс), а не инициироваться непосредственно при каждом приеме данных.
- Крупные буферы источника и программирование аппаратного scan выполняются при
  загрузке или переконфигурировании. Повторный `Start/Stop` подготовленного
  источника только переключает сбор и сбрасывает счётчики: запрещены `SetLength`,
  повторный `ProgramDevice` и безусловный `Disconnect`. Проверка — два цикла
  Preview подряд; во втором цикле в логе нет повторного `programmed`.
- Оптимизация рендеринга и отложенная сборка данных (Lazy Recompile): в графических подсистемах (например, OpenGL с пакетной отрисовкой) выполнять подготовку и сборку массивов данных только тогда, когда это действительно необходимо:
  - Выставлять инвалидирующий флаг (например, `needrecompile`) при изменении условий отрисовки: поступление новых данных, изменение масштаба отображения или изменение настроек шкалы.
  - Сборку данных и компиляцию графических структур производить непосредственно перед выводом кадра только при установленном флаге `needrecompile`, сбрасывая его по окончании сборки. Если флаг сброшен, повторно использовать ранее подготовленные структуры без перерасчета.

Маркер правила: `RLNX_ALARMS_COLOR_DISPLAY`.
Срабатывание любых тревог (alarms) на каналах или системных событиях должно обязательно визуализироваться цветами в любых графических и табличных компонентах пользовательского интерфейса (например, подсветка ячеек формуляров, изменение цвета графиков/осей, мигание индикаторов состояния).

### Кроссплатформенная плагинная система
Маркер правила: `RLNX_CROSSPLATFORM_PLUGINS`.
Для реализации плагинов расширения к RecorderLnx, работающих и собирающихся под Windows и Linux по одной кнопке без изменения кодовой базы проектов, используется технология **динамических библиотек (Shared Libraries / DLL)** с плоским интерфейсом функций **Flat C API** (использование `stdcall`/`cdecl` вызовов, простых типов вроде `Double`, `Integer`, `PChar`/`PAnsiChar` в UTF-8/CP1251 и `record`-структур без динамических массивов LCL). Загрузка плагинов на стороне RecorderLnx осуществляется динамически через функции модуля `DynLibs` (`SafeLoadLibrary`, `GetProcedureAddress`, `FreeLibrary`).

## 9. Error investigation journal (errors/)

Rule marker: `RLNX_ERROR_JOURNAL_2026_06_29`.

When solving a bug, regression, build failure, crash, device/protocol issue, encoding issue, or any recurring suspicious behavior, keep a persistent investigation file in `D:\works\OburecGH\Lazarus\RecorderLnx\errors\`.

At the start of debugging:
- Search `errors/` for related symptoms, modules, log text, device names, and error messages.
- Read the relevant investigation files before creating new hypotheses.
- Continue an existing file when the symptom is the same or clearly related; create a new file only for a distinct error.

During debugging:
- Use one Markdown file per error, named `YYYY-MM-DD-short-error-slug.md`.
- Record confirmed facts separately from hypotheses.
- For every checked hypothesis, write what was checked, how it was checked, the command/log/test/code location used, and the result.
- Keep rejected hypotheses in the file so future sessions do not repeat the same checks.
- After every meaningful change, record what changed and how behavior/build/tests/logs changed.
- When fixed, record root cause, final fix, verification command, result, and remaining risk.

Minimum sections:
- `Symptom`
- `Context`
- `Facts`
- `Hypotheses`
- `Actions`
- `Current Conclusion`

`cach/notes_last_state.md` may contain a short session summary, but the detailed debugging history for errors belongs in `errors/`.

- Перед `Connect`, `ProgramDevice` и `Start` сетевого устройства выполняется не бросающий исключение TEST/probe. При отрицательном результате источник помечается offline, опасные операции не вызываются, а его worker остаётся штатно остановленным. Успешный TEST MC-032 сохраняет тот же TCP-сеанс для последующего программирования.
- `Connect` открывает и проверяет только транспорт. Поиск состава крейта и другие операции, результат которых теряет силу после аппаратного `RESET`, выполняются в `Init` после сброса и не дублируются перед ним. Проверка: в логе холодного запуска между `connect attempt` и единственным `SearchModules` нет предварительного обхода слотов.
- Транспортный декодер не отбрасывает пакет по амплитуде, смещению, насыщению или форме измеряемого сигнала. Прибороспецифичные эталоны применяются только отдельным диагностическим/приёмочным тестом. Проверка транспорта опирается на кадрирование, длину, служебные поля, последовательность и контрольные суммы протокола.

- При сравнении production-драйвера с диагностическим примером эталонный тест обязательно пересобирается из текущих исходников. Старый EXE нельзя считать доказательством корректности текущего протокольного кода.
### Инициализация оборудования после загрузки

- `rstInit` автомата состояний не является событием и не заменяет lifecycle-нотификацию.
- `rceInitialized` публикуется только после загрузки проекта и форм, создания и привязки источников, выделения буферов и попытки программирования оборудования.
- После загрузки или переконфигурирования порядок неизменен: пересоздать источники → `ConfigureTagsAll` → `PrepareHardwareAll` → публиковать событие готовности.
- Нельзя прятать программирование оборудования внутри фабрики источников или публиковать готовность до создания источников. Проверка: первый Preview после загрузки должен сразу получать данные без повторного конфигурирования.
- Нельзя фильтровать создание runtime-источников через UI-видимость или `ActiveSourceIds`: активность является результатом создания источника. Источники строятся по сохранённой конфигурации тегов; UI-фильтры применяются только при отображении.
# Спектральные алгоритмы

- Чистые вычислительные юниты спектров размещаются в `Algs`; `Core` содержит orchestration/runtime и доменную модель приложения.
- Производные теги спектральных оценок создаются в `PrepareConfiguration`, а не в потоковом `HandleChannelFrame`.
- Любое новое сериализуемое поле спектральных настроек должно быть добавлено в defaults, чтение, запись, UI и автоматический тест.
- Маркер правила: `RLNX_SPECTRUM_PER_CHANNEL_GRID_2026_07_16`. Границы частотной полосы нельзя переводить в индексы округлением к ближайшему FFT-бину: для включительного диапазона `[F1,F2]` применяются `Ceil(F1/df)` и `Floor(F2/df)`. `df` вычисляется отдельно для каждой привязки из фактической `PollFrequencyHz` входного тега и FFTSize. Обязательные тесты: граница между бинами и два канала одного спектрального узла с разными частотами дискретизации.

# Правки больших Pascal-юнитов

- При вставке обработчика или блока инициализации нельзя ориентироваться на короткий повторяющийся фрагмент (`end;`, одинаковый `if ... <> nil`). Контекст патча должен включать имя целевой процедуры или уникальные соседние строки. После вставки проверить расположение через `rg -n -A/-B` и обязательно выполнить полную сборку.

# Синхронизация настроек диалога

- Если настройки одновременно представлены элементами управления и сериализованной строкой `Cfg`, изменение каждого элемента управления должно сразу обновлять `Cfg`. Проверка исправления обязательна по сценарию: изменить галочки → «Применить» → повторно выбрать алгоритм; значения не должны сбрасываться.
- Маркер правила: `RLNX_VISUAL_SETTING_FULL_CHAIN_2026_07_16`. Любая настройка визуального компонента должна быть подключена по всей цепочке: диалог → модель → фактическая отрисовка → сохранение и загрузка проекта. Одного поля в модели и элемента диалога недостаточно. Проверка: изменить настройку, закрыть диалог, сохранить и повторно загрузить проект — вид и выбранное значение должны сохраниться.

# Иконки тегов в таблицах

- Иконки состояния и типа тега рисуются единым обработчиком первой колонки таблицы через `ImageList.GetBitmap` и `Canvas.StretchDraw`. Для виртуального тега используется индекс 20; признак виртуального тега имеет приоритет над иконкой неактивного аппаратного источника.
- Виртуальность является явным свойством `TRecorderTag.IsVirtual` и задаётся при создании тега через конструктор или `TRecorderTagRegistry.CreateTag`. UI, фильтры и алгоритмы не должны выводить виртуальность из имени, адреса, типа модуля или `SourceId`. Анализ старого `SourceId` допустим только при миграционной загрузке проекта без сохранённого поля `isVirtual`.

## Материализация производных объектов при Apply

Если флаг конфигурации объявляет создание тегов, каналов или иных производных объектов, обработчики всех кнопок «Применить» и OK должны выполнять полный цикл: сохранить текущие контролы в модель, перенести модель в рабочую конфигурацию, материализовать производные объекты и обновить UI. Сохранение одного флага без вызова конфигурационной фазы считается незавершённым применением настройки.

Материализация обязана быть идемпотентной: повторный Apply с той же конфигурацией не меняет число объектов. Производные теги искать не только по отображаемому имени, но и по устойчивой доменной идентичности владельца и назначения; новый объект создавать лишь при отсутствии обоих совпадений.

После закрытия модального редактора все внешние представления изменяемого реестра должны перечитать модель независимо от `ModalResult`, если внутри редактора существует отдельная кнопка «Применить». `ModalResult` определяет выполнение отложенных операций OK, но не является достоверным признаком того, изменялась ли модель ранее.
# Статус сетевого устройства

Маркер правила: `RLNX_DEVICE_STATUS_EVIDENCE_2026_07_16`.
При вычислении статуса сетевого устройства более новое успешное свидетельство
(активная сессия и поступающий поток) имеет приоритет над сохраненной старой
ошибкой. Ручной сброс обязан выполнить безопасный `TEST` и назначать зеленый
статус только после успеха. Hint и другие обработчики наведения должны быть
read-only и не выполнять сетевой ввод-вывод. Проверка: работающий источник не
остается красным после старой ошибки; неработающий после сброса сохраняет текст
ошибки; многократное движение мыши не создает TCP-запросов. Если Stop сохраняет
рабочую сессию для быстрого Restart, он не имеет права удалять ее из live-реестра;
успешный Start должен идемпотентно восстановить регистрацию.
# Атомарное изменение ссылки на тег

Маркер правила: `RLNX_TAG_REF_PAIR_2026_07_16`.
Если модель хранит ссылку на тег одновременно как `TagId` и `TagName`, диалог
или команда обязаны изменять оба поля из одного объекта `TRecorderTag`. Нельзя
оставлять старый ID при новом имени: последующая синхронизация по ID восстановит
прежний тег. Проверка: после выбора другого тега, повторного открытия диалога и
сохранения/загрузки проекта остаются одинаковые ID и имя выбранного тега.

# Миграция имён производных тегов

Маркер правила: `RLNX_DERIVED_TAG_RENAME_2026_07_16`.
При изменении соглашения об имени автоматически создаваемого тега нельзя создавать
новый тег только потому, что старое отображаемое имя больше не совпадает. Сначала
следует найти прежний объект по старому имени либо по устойчивой паре
`SourceId/Address`, затем переименовать и обновить его метаданные с сохранением
`TagId`. Проверка обязана подтвердить одновременно: новый суффикс опубликован,
старого имени больше нет, `TagId` не изменился, повторная подготовка конфигурации
не создаёт дубликат.

# Явные архитектурные вызовы и EventBus

Маркер правила: `RLNX_EXPLICIT_ARCHITECTURE_CALLS_2026_07_16`.
Lifecycle, подготовка конфигурации и основной путь данных между статически
известными подсистемами выполняются явными вызовами методов. `EventBus` применять
для динамически подключаемых наблюдателей, плагинов и UI-уведомлений, когда набор
получателей действительно неизвестен во время компиляции. Проверка: переходы
Recorder → менеджер алгоритмов и обновления тегов → менеджер находятся обычным
поиском вызовов в исходниках; для понимания цепочки не требуется runtime-трасса
подписок.

При замене EventBus-маршрута прямым вызовом необходимо перечислить и проверить
все формы доставки соответствующих данных: scalar, полный block и block-tail.
Нельзя считать миграцию завершённой по одному `PublishValue`. Проверка должна
подтверждать одинаковый вызов обязательной модели для одиночного значения и для
последнего значения опубликованного блока.
# Возможности устройств в общих диалогах

Маркер правила: `RLNX_DEVICE_ACTION_CAPABILITY_2026_07_16`.

Если сервисная кнопка общего диалога зависит от возможностей прибора
(балансировка, аппаратная настройка, чтение калибровки), нельзя определять её
работоспособность закрытым списком имён моделей. Действие объявляется в базовом
контракте `IRecorderDevice`/`TRecorderDevice`, а конкретный драйвер переопределяет
проверку поддержки и выполнение. UI отвечает только за отображение и открытие
редактора, но не содержит реализацию протокола устройства.

Обязательная проверка: новый драйвер подключается к существующей команде без
копирования её обработчика; неподдерживаемая команда возвращает диагностическое
сообщение; после изменения интерфейса собираются все его реализации и полный
`RecorderLnx.lpi`.

# Перенос эталонных палитр

Маркер правила: `RLNX_REFERENCE_PALETTE_EXACT_COPY_2026_07_16`.

Если пользователь указывает эталонную палитру другого проекта, переносить весь
массив, его длину, порядок и семантические имена. Нельзя субъективно заменять
только проблемный цвет, пока исходный массив не найден. При преобразовании
`point3`/OpenGL RGB в `TColor` явно учитывать BGR-представление и проверить
первый, последний и указанный пользователем индекс. Затем пересобрать пакет
графиков и основной проект.

Явно запрошенное пользователем изменение конкретного элемента после переноса
эталона является допустимым проектным отклонением. Оно вносится только в общий
массив палитры; все назначения цвета по индексу обязаны вызывать функции этого
массива, а не содержать локальные копии или `case`.

# Аппаратные перечисления и индексы UI

Маркер правила: `RLNX_HARDWARE_ENUM_INDEX_2026_07_16`.

При переносе списка аппаратных режимов, диапазонов или частот копировать из
первичного исходника полный список и исходный порядок. Если `ItemIndex`
сохраняется в конфигурации либо передаётся устройству, порядок является частью
протокола и не может исправляться по внешнему виду диалога. Проверка: первый и
последний элементы, количество элементов и соответствие каждого индекса
эталонной таблице подтверждены по исходнику; полный `RecorderLnx.lpi` собран.

Настройка аппаратного режима считается перенесённой только после проверки всей
цепочки `UI → сериализация проекта → runtime-источник → конфигурация драйвера →
отправленный регистр/пакет`. Одной работающей формы и сохранённого индекса
недостаточно. Для значения по умолчанию и хотя бы одного отличающегося значения
нужно подтвердить разные протокольные слова по первичному исходнику устройства.

Если режим реализован дочерним аппаратным субмодулем, нельзя включать его в
регистр родительского модуля по сходству UI. Нужно отдельно перенести обнаружение
субмодуля, установку всех его свойств и команду применения. Проверка должна
подтвердить положительный ответ субмодуля; сохранённая галочка и успешный основной
регистр не доказывают включение режима.

Маркер правила: `RLNX_COUPLED_HARDWARE_UI_2026_07_16`. При переносе связанных
аппаратных элементов управления копировать из оригинала не только сохраняемые
значения, но и обработчики переходов, принудительные значения и `Enabled`-состояния.
Минимальная проверка включает включение, выключение, повторное открытие диалога и
вариант отсутствующего дочернего оборудования. Для ICP MC-201 это означает:
ICP включён — вход недифференциальный и список заблокирован; ICP снят — вход
дифференциальный и список доступен; без MM202 оба элемента недоступны.

Маркер правила: `RLNX_DEVICE_OUTPUT_UNIT_PIPELINE_2026_07_27`. Единица тега
сетевого устройства определяется не отдельным полем UI, а фактически активными
ступенями преобразования. Для MIC-140 инвариант такой: аппаратная ГХ выключена —
`code`; аппаратная ГХ включена без температурной канальной ГХ — `mV`;
аппаратная и температурная ГХ включены — `degC`. Один общий метод обязан
применяться после аппаратного диалога, изменения галки, загрузки проекта и перед
запуском источника. Проверка включает последовательность
`degC → выключить аппаратную ГХ → code → включить → degC` и отдельный канал mV.

Маркер правила: `RLNX_DEVICE_ENUMS_FROM_MODULE_2026_07_16`. Универсальные диалоги
не должны содержать таблицы допустимых частот, диапазонов или режимов конкретных
приборов. Аппаратный модуль публикует перечень через общий реестр/контракт, UI
только отображает его. Проверка: добавление нового устройства с собственной сеткой
не требует изменения универсального диалога, а элементы совпадают с первичным
исходником драйвера.

При вычислении аппаратной сетки нельзя подставлять найденную рядом константу
кварца напрямую. Нужно проследить виртуальный getter до фактически выбранного
источника тактирования (`self clock`, backplane, измеренная или файловая настройка)
и использовать один расчёт для UI и кодирования протокола. Проверка обязана
сравнить крайние точки сетки и аппаратные коды хотя бы для двух частот.

Если аппаратная возможность различается между экземплярами одного типа источника
(например, кварц MC-032), регистрировать её по полному `SourceId`, а не только по
типовому префиксу. Одно сохранённое значение обязано одновременно определять UI,
runtime-конфигурацию и преобразование в аппаратный код; глобальная таблица типа
устройства допустима только как значение по умолчанию.

Перед реализацией аппаратной настройки определить её область владения: канал,
модуль/слот или контроллер. Одна и та же область обязана соблюдаться в UI,
сериализации, программировании, размерах буферов и метаданных записи. Для свойства
модуля изменение одного канала атомарно обновляет все каналы модуля и не меняет
соседние модули. Проверять минимум на двух модулях с разными значениями.

Аппаратную балансировку, калибровку или компенсацию нельзя заменять программным
вычитанием, если эталонный драйвер управляет ЦАП/регистром в замкнутом цикле.
Нужно воспроизвести последовательность «аппаратная команда → свежий сбор → оценка
→ уточнение», сериализовать её с рабочим I/O, восстановить старое значение при
ошибке и сохранить результат в исходной области конфигурации (канал и диапазон).

При служебном сборе через пакетный транспорт ограничивать требуемое число
отсчётов максимальной завершённой порцией протокола. Не считать полную свежую
порцию ошибочной только потому, что `Fs * duration` больше транспортного пакета;
проверять достаточность оценки и отсутствие лишнего ожидания на каждом шаге.
## Длительные аппаратные операции из UI

Циклические сервисные операции устройств (балансировка, калибровка, тест с
накоплением данных) не выполнять в GUI-потоке. Запускать их в worker, блокировать
повторный запуск модальным окном состояния и переносить в GUI только готовый
результат. Не передавать LCL-компоненты в worker и проверять, что во время операции
главное окно продолжает перерисовываться.

При сохранении вычисленного аппаратного параметра нельзя предполагать, что
секция конфигурации уже существует. Обновление должно создавать отсутствующую
секцию с корректными значениями по умолчанию; проверка — пересоздать источник и
убедиться, что тот же параметр повторно отправлен устройству.

Успешный ответ аппаратной команды не доказывает, что исполнительный узел
сработал. Для ЦАП, реле и программируемого усилителя нужен короткий smoke-тест
«измерение до → безопасное изменение кода → измерение после → восстановление».
Команды модуля при активном IDMA обязаны идти через активный командный путь;
запрещены безусловные обходы в вариант для остановленного IDMA.

Один TCP-поток устройства не должен одновременно читаться штатным read-thread и
служебной процедурой измерения. Перед прямым служебным чтением приостанавливать
фонового потребителя на всю транзакцию и обязательно восстанавливать его в
`finally`; аппаратный скан при этом можно оставить активным.

Длительная аппаратная настройка из UI должна показывать живой диагностический
журнал с физическим адресом узла, отправленными кодами, объёмом принятой выборки
и измеренным результатом. При ошибке журнал нельзя автоматически закрывать:
пользователь должен иметь возможность прочитать или скопировать его.

## Ошибки TCP под UNIX

Маркер правила: `RLNX_UNIX_SOCKET_SIGPIPE_2026_07_21`.

Каждый `TSocketStream`, выполняющий TCP-запись под UNIX, обязан устанавливать
`WriteFlags or MSG_NOSIGNAL`. Процесс дополнительно игнорирует `SIGPIPE` после
`Application.Initialize` как второй рубеж защиты. Закрытие peer между проверкой
соединения и отправкой должно возвращаться драйверу как `EPIPE`, а не становиться
внешним исключением FPC или остановкой Lazarus debugger. Проверка: GDB с
`handle SIGPIPE stop print pass` не останавливается при запуске с недоступным
TCP-источником; приложение проходит Preview, остальные источники работают.
Детали: `errors/2026-07-21-linux-startup-sigpipe.md`.

## Временные эпохи потоковых данных

Маркер правила: `RLNX_SIGNAL_TIME_EPOCH_MONOTONIC_2026_07_21`.

Кольцевой буфер тега обязан хранить отсчёты с монотонно неубывающим временем.
Если после Stop/Start, переподключения или перезапуска источника время первого
нового отсчёта меньше времени последнего сохранённого отсчёта, это начало новой
временной эпохи: прежняя история должна быть очищена атомарно вместе с добавлением
нового блока. Нельзя оставлять в одном снимке конец старой эпохи и начало новой —
графики используют бинарный поиск по времени и при нарушении сортировки временно
теряют линию. Проверка: регрессионный тест публикует блок/точки с большим временем,
затем данные от нуля и подтверждает, что снимок содержит только новую эпоху и
остаётся отсортированным.

## Граница универсального UI и устройств

Маркер правила: `RLNX_UNIVERSAL_UI_NO_DEVICE_IMPLEMENTATIONS_2026_07_21`.

Универсальные UI-модули (`uMainForm`, общие диалоги и визуальные компоненты) не
должны импортировать реализации приборов, разбирать их `SourceId`, создавать
конкретные data source или вызывать диалоги конкретных модулей. Композиция
runtime-источников и маршрутизация аппаратных команд размещаются в слое
`Device` за нейтральным фасадом. Проверка: поиск имён типов/юнитов конкретных
устройств в `uMainForm.pas` возвращает пустой результат, а полная сборка проекта
проходит без изменения состава источников.
## Производительность OpenGL-ресурсов

Маркер правила: `RLNX_OPENGL_RESOURCE_BUILD_NO_PIXEL_API_2026_07_21`.

При построении текстур, атласов и других больших растров запрещено обходить
изображение через `TCanvas.Pixels`: под Linux/X11 это отдельный дорогой вызов на
каждый пиксель. Для кроссплатформенной обработки использовать нормализованный
`TLazIntfImage` (`Colors[]`/`TFPColor`); прямой `TBitmap.ScanLine` допустим только
при явно проверенном для каждой платформы формате байтов. Результат проверять
снимком в Windows и Linux. Генерацию BMP и текстовых дампов выполнять только в
явно включённом диагностическом режиме, не из штатного первого кадра.

## Кроссплатформенные изображения LCL

Маркер правила: `RLNX_LCL_IMAGE_FALLBACK_KEEP_EMBEDDED_2026_07_21`.

Если внешний файл изображения недоступен, не заменять уже встроенную в LFM
эталонную картинку программно нарисованным fallback. Замену в `TImageList`
выполнять только после успешной загрузки ресурса; одинаковый вид и прозрачность
проверять сборкой и запуском в Windows и Linux.

## Многоканальная визуализация результатов

Маркер правила: `RLNX_MULTICHANNEL_VIEW_NO_REQUIRED_INDEX_ZERO_2026_07_21`.

В многоканальном компоненте не считать элемент с индексом 0 обязательным
источником общих аннотаций, диапазонов или оценок. Выбирать первый готовый
результат либо явно назначенный опорный канал; проверять сценарий, где первый
канал недоступен, а последующий продолжает выдавать данные.

Проверка: замерять отдельно построение модели страницы, `MakeCurrent`,
инициализацию renderer и полный первый кадр. Повторный вход не заменяет проверку
холодного первого открытия. Детали: `errors/2026-07-21-linux-mnemonic-first-open-slow.md`.

## Приёмка отладочного GUI устройства

Маркер правила: `RLNX_DEVICE_DEBUG_GUI_MUST_PROVE_STREAM_2026_07_22`.

Отладочный GUI сетевого прибора нельзя считать рабочим по успешным `Connect`,
`TestLink`, чтению версии или программированию конфигурации. Пример обязан пройти
полный цикл `Connect -> Init -> Config -> Start -> ReadBlock -> Stop`, вывести в
интерфейсе реальные данные всех заявленных каналов и показать число принятых
блоков. Проверка выполняется на приборе без предварительного запуска рабочего
Recorder; лог должен подтверждать ненулевой поток и нулевые счётчики разрывов,
дубликатов, повреждений и рассинхронизации.

## Формат аппаратной балансировки MC-201

Команда `SEND_BALANCE_CC` принимает номер канала и два независимых 8-битных
кода `code_lo`, `code_hi` в смещённом формате (`0=-128`, `128=0`, `255=127`).
Хотя транспорт MDP передаёт каждый аргумент как 16-битное слово, значимы только
младшие 8 бит каждого кода. Запрещено объединять их в линейный 12-, 14- или
16-битный код либо менять порядок аргументов без проверки обработчика BIOS.
Коэффициент пересчёта обязан следовать аппаратной схеме или подтверждаться
стендовым измерением; неподтверждённую формулу произведения кодов применять
нельзя.

Стенд MC-201 подтвердил мультипликативную модель балансировки:
`deltaADC ≈ -2,8*(lo-128)*(hi-128)`. Деление поправки выполняется относительно
кода 128 отдельно для каждого ЦАП; деление упакованного 16-битного слова
некорректно. Для сохранения разрешения выбирается минимальное положительное
`lo-128`, при котором `abs(hi-128) <= 127`, а знак поправки задаётся кодом `hi`.

Сервисная балансировка может временно запустить скан и затем выполнить
`STOPSCANMAIN`. Нельзя считать, что после остановки модуль сохранил состояние
балансировочных ЦАП. После изменения кода уже запрограммированную конфигурацию
нужно пометить устаревшей и при ближайшем старте один раз выполнить штатное
программирование модуля до `STARTSCANMAIN`. Запрещено отправлять служебные
модульные команды после запуска потока: они конкурируют с пакетами данных.
Проверка исправления обязана включать сценарий: балансировка из
Stop → переход в просмотр с первого раза → проверка изменившегося среднего.

Для MC-201 транспортное подтверждение `SEND_BALANCE_CC` не завершает процедуру
применения ЦАП. Оригинальный `ChanCalibrFullSingleScan` после каждой такой
команды вызывает `GetChanMeanSingleScan`, который выполняет отдельный
`single_scan->StartStop()`. Порт обязан сохранять эту последовательность:
команда ЦАП → следующий цикл скана → контрольная выборка. Задержка по времени и
повторная отправка команды не являются эквивалентом цикла скана.
# Сервисные операции сетевых устройств

- Маркер правила: `RLNX_DEVICE_DIALOG_NO_IMPLICIT_IO_2026_07_27`.
  Открытие аппаратного диалога и обычный `OK` являются только чтением и
  сохранением конфигурационной модели. Они не должны неявно выполнять
  `Connect`, TEST, чтение firmware/EEPROM или создавать временный транспорт.
  Аппаратный обмен запускается только явной сервисной кнопкой и использует
  зарегистрированную live-сессию устройства, если она уже существует.
- Если источник уже зарегистрировал live-устройство, чтение памяти,
  балансировка, диагностика и другие сервисные команды обязаны выполняться
  через его существующую сессию. Не открывать конкурирующий TCP к тому же
  прибору.
- Сервисная операция должна явно проверять состояние устройства. Операции,
  несовместимые с `Play`, отклоняются до отправки команды.
- После остановки потока перед командным обменом очищать накопленные пакеты
  потока штатным методом транспорта.
- Проверка: в логе одна сессия-владелец; сервисная команда проходит без
  повторного `Connect`; после неё штатный `Start` снова выдаёт блоки.

## Выбор строки в LCL-таблицах

Маркер правила: `RLNX_GRID_SELECTION_USE_EVENT_COORDINATES_2026_07_27`.

В обработчиках `TStringGrid.OnSelectCell` выбранную модель определять по
переданным `aRow`/`aCol`. Не читать в этом обработчике `Grid.Row`/`Grid.Col`:
LCL может вызвать событие до обновления этих свойств, из-за чего редактор
свойств покажет и изменит предыдущую строку. Проверка должна переключать строки
с различной доступностью действий и подтверждать, что подписи, значения и
`Enabled` относятся к подсвеченной строке.

## Бюджет периодических RunTime-циклов

Маркер правила: `RLNX_RUNTIME_TICK_MUST_HAVE_HEADROOM_2026_07_27`.

Наличие `Sleep` в конце worker-цикла само по себе не доказывает, что поток
ожидает. Для каждого периодического источника измерять процессорное и
астрономическое время `Tick`: в установившемся режиме обработка обязана
завершаться заметно раньше периода. Если `Tick >= period`, внешний планировщик
не имеет возможности уснуть и формально периодический worker становится
непрерывным busy-loop.

В RunTime запрещено:

- читать или писать `TStream` по одному отсчёту;
- передавать в график все высокочастотные отсчёты без ограничения разрешением
  экрана;
- считать отсутствие явного `while True` доказательством отсутствия busy-loop.

Файловый и сетевой I/O выполнять порциями в заранее выделенные буферы.
Осциллограммы хранить как кольцо заранее выделенных порций источника. Кадр
собирать из последних N порций несколькими `Move`, сохраняя все отсчёты, а
линию заменять одним пакетным вызовом. В RunTime запрещены поточечные
`SetLength`/`AddValue`; прореживание не является обязательной частью этого
пути. При аудите сначала снимать дельту CPU по потокам и сопоставлять TID
с именами/логами worker-ов, затем проверять I/O; нельзя лечить перегрузку
добавлением новых потоков.

Подробное исследование:
`errors/2026-07-27-preview-two-cpu-cores.md`.

### Перекомпиляция линий OglChart только по изменению

Маркер правила: `RLNX_OGL_LINE_RECOMPILE_ONLY_WHEN_DIRTY_2026_07_27`.

В OglChart штатным признаком необходимости пересборки линии является
`cBaseTrend.GLListID = 0` (аналог прежнего `needRecompile`). UI-таймер не должен
сбрасывать этот признак, если содержимое линии не изменилось.

- Буфер сигнала увеличивает `Revision` при добавлении или очистке данных.
- Осциллограмма сравнивает текущие ревизии всех отображаемых тегов с ревизиями
  предыдущего кадра.
- `Snapshot` и `ReplaceValues` вызываются только при изменении данных либо
  длительности отображаемого окна.
- Изменения осей, логарифмического масштаба, стиля и геометрии продолжают
  инвалидировать display list штатными средствами OglChart.
- После EOF файлового источника число компиляций линий не должно расти, пока
  пользователь не изменил оси или настройки отображения.

Нельзя вводить параллельный флаг перерисовки, конкурирующий с `GLListID`.
Ревизия данных лишь определяет, нужно ли передавать новый массив в chart;
решение о компиляции OpenGL-геометрии остается за OglChart.

### Кэш RunTime-маршрута аппаратного источника

Маркер правила: `RLNX_DEVICE_RUNTIME_CACHE_ON_CONFIGURE_2026_07_27`.

После `Configure/PrepareHardware` аппаратный источник обязан хранить прямые
ссылки на свои теги, настройки каналов, калибровки и описание каналов.
В обработке очередного блока запрещено:

- получать `GetChannels`, если метод возвращает копию массива;
- искать каждый тег через `FindByName` или перебор реестра;
- разбирать адрес либо `SourceId` строковыми функциями;
- повторно читать конфигурацию канала для каждого отсчёта;
- выполнять несколько глубоких копирований одного принятого блока.

MIC-140 строит такой кэш после программирования прибора. При
переконфигурировании источник и кэш пересоздаются вместе. Полная проверка
качества всех кодов является диагностикой протокола: допустимы первые блоки и
редкая контрольная выборка, но не сплошной проход на каждом блоке штатного
сбора.
## Уведомление и чтение потоковых данных

- `EventBus` не переносит массивы измерений ни в Preview, ни в Record. Событие
  может означать только изменение состояния/ревизии.
- Каждый тег ведёт монотонный счётчик готовых логических блоков. Длина блока
  равна `Round(PollFrequencyHz * DataUpdateMs / 1000)`; сетевой пакет блоком не
  является. Каждый потребитель ведёт собственный счётчик прочитанных блоков и
  по настраиваемому периоду проверяет разницу.
- ГХ, оценки тегов, уведомления и инвалидация визуализации выполняются только
  для готового логического блока. Транспортный пакет может лишь дополнять
  заранее выделенный накопитель; запрещено запускать полный вычислительный
  тракт для каждого пакета. Проверка: число таких вызовов за секунду близко
  `1000 / DataUpdateMs`, а не частоте сетевых пакетов.
- Период потребления берётся из `RunSettings.DataUpdateMs`; значение 200 мс
  является только возможной настройкой, но не константой архитектуры.
- Только при наличии непрочитанных блоков потребитель входит в критическую
  секцию буфера и забирает очередной целый блок. Начало вычисляется из
  стартового отсчёта, фиксированной длины и номера блока; таблица границ и
  копия массива в очереди уведомлений отсутствуют.
- Окно осциллограммы рассчитывается и хранится в отсчётах. Число и размер
  сетевых пакетов за цикл не должны менять длительность отображаемого сигнала.
- Проверка: несколько малых блоков за один цикл дают то же число отсчётов в
  кадре, что один объединённый блок; повторное чтение с тем же курсором не
  возвращает данные.
## RLNX_RUNTIME_REUSE_TAG_ESTIMATES_2026_07_27

Результаты расчётов, используемые другими расчётами, передавать через штатные
теги Recorder. Если тег уже вычислил оценку блока, потребитель читает готовую
оценку и не обходит исходные отсчёты повторно. Инвариантную часть вычисления
выносить на самый внешний допустимый уровень и задавать явную инвалидизацию.

Для медленно меняющихся параметров (например температуры холодного спая)
использовать текущее МО тега, если алгоритму не требуется синхронная
поточечная форма. Последний снимок побочного потока публиковать только при
изменении его revision; нельзя повторно назначать его каждому блоку основной
FIFO.
## Автономные эталоны протоколов

Проекты, объявленные эталонными или референсными стендами протокола, должны
быть полностью автономны. Нельзя добавлять в них пути к исходникам, PPU,
библиотекам и ресурсам изменяемого RecorderLnx или SharedUtils. Все необходимые
прикладные юниты и ресурсы фиксируются внутри каталога стенда.

Автономность считается проверенной только после чистой сборки (`lazbuild -B`)
копии проекта из произвольного отдельного каталога. Отдельный каталог вывода
PPU обязателен, чтобы старые модули не маскировали отсутствующие зависимости.

Маркер правила: `RLNX_STANDALONE_PROTOCOL_REFERENCE_2026_07_28`.

## RLNX_DEVICE_CONFIG_DIRTY_2026_07_28

Аппаратный жизненный цикл разделён на независимые фазы:
`Connect -> Init -> Configure -> Start -> Stop -> Disconnect`.

- `Init` выполняется один раз на открытую физическую сессию.
- `Stop` останавливает только сбор и сохраняет TCP-сессию, результат Init и
  применённую конфигурацию.
- Перед повторным Start выполняется `TestLink` существующей сессии. При
  успешном тесте и чистом флаге конфигурации тяжёлые Init/Configure запрещены.
- Потерявшее связь устройство помечается offline и исключается из опроса.
- Изменение аппаратных настроек и явная команда «Сброс устройства» выставляют
  dirty/reset. Следующий Prepare выполняет Disconnect, Connect, Init и
  Configure, после чего очищает dirty.
- Перед открытием любого диалога тега сохраняется сигнатура аппаратных
  настроек его узла источника. После `OK` источник помечается dirty только при
  изменении этой сигнатуры; само подтверждение диалога не является изменением
  конфигурации. Это правило обязательно для обоих входов: главной формы и
  таблицы каналов общего окна настроек.
- В сигнатуру входят только параметры, передаваемые прибору: адрес и порт,
  состав каналов, частота, диапазоны и коммутация. Имя, единицы, программные
  ГХ, оценки и параметры отображения не должны запускать Init/Configure.
- Запись аппаратного параметра из диалога также должна быть идемпотентной:
  перед групповым применением частоты, диапазона или режима сравнить новое
  нормализованное значение с текущим. Неизменённый `OK` не должен обходить
  каналы, менять их буферы или выставлять признак переконфигурации.
- При закрытии приложения/удалении источника выполняется Disconnect.

Приёмочный тест: два Preview без изменения настроек должны содержать в логе
один Init/Configure и два Start/Stop. После явного Reset должен появиться ровно
один новый Init/Configure. Открытие настройки тега MIC-140, MIC183/185 или
MC-201 с немедленным `OK` должно дать сообщение `programming skipped` и не
вызывать Stop, Clear, Init или Configure. Проверяется именно вызывающий код,
а не только наличие функции вычисления сигнатуры.

## RLNX_RUNTIME_NO_IDLE_RENDER_OR_SUCCESS_PACKET_LOG_2026_07_28

- Успешный транспортный пакет является штатным RunTime-событием. Запрещено
  форматировать и синхронно писать строку лога для каждого успешного пакета.
  Подробный пакетный trace включается только специальной диагностической
  сборкой либо автономным протокольным стендом.
- Периодический UI-таймер не является основанием для полной перерисовки
  страницы. Таблица, мнемосхема и набор графиков обновляются только при
  изменении сводной ревизии входных тегов либо при явном изменении страницы,
  геометрии или настроек отображения.
- Приёмочная проверка: после прекращения обновления входов число полных render
  не растёт; production-лог не содержит периодических сообщений об успешных
  пакетах; CPU процесса измеряется по потокам, а не по общей диаграмме системы.

## RLNX_CALCULATION_RENDER_SEPARATION_2026_07_29

- Расчёты алгоритмов и публикация тегов работают по приходу данных и не
  зависят от открытой страницы.
- Визуальная подготовка (`Snapshot` для окна, экранные диапазоны, геометрия,
  подписи, `Invalidate`/`Repaint`) вызывается только из display-цикла
  `DoRepaintVisiblePage`.
- Display-цикл обслуживает только активную видимую страницу. Для пользовательской
  мнемосхемы `RefreshLive` обходит компоненты только её видимой панели; скрытые
  страницы запрещено обновлять «на всякий случай».
- Компонент видимой страницы всё равно обязан проверять revision/dirty:
  видимость разрешает отрисовку, но не требует пересборки неизменившейся линии.

Приёмочная проверка: после переключения вкладки счётчик визуальной подготовки
предыдущей страницы перестаёт расти, а расчётные теги продолжают обновляться.

## RLNX_UI_QUEUE_NO_TAG_BLOCK_COPIES_2026_07_29

- UI определяет обновление данных по ревизиям кольцевых буферов тегов. Полные
  блоки тегов в очередь UI не помещаются.
- Очередь главной формы хранит только редкие события, которые нельзя восстановить
  из текущего состояния модели, прежде всего переходы тревог.
- Уведомления спектров и тегов обслуживаются профильными потребителями; общая
  UI-очередь не создаёт для них дублирующие объекты.

Приёмочная проверка: при живом сборе число событий в общей UI-очереди остаётся
нулевым без тревог, графики обновляются по экранному периоду, тревоги
по-прежнему отображаются.

## RLNX_SOURCE_ENABLED_IS_NOT_HARDWARE_DIRTY_2026_07_29

- Включение и отключение источника меняет только участие уже созданного
  runtime-контекста в сборе.
- Изменение `Enabled` не очищает менеджер источников, не уничтожает аппаратные
  сессии и не вызывает общий `PrepareHardwareAll`.
- Перед применением настроек сравнивать программируемую сигнатуру отдельно для
  каждого `SourceId`. Создавать, удалять или тяжело конфигурировать разрешено
  только добавленный, удалённый или действительно изменённый источник.
- Изменение одного источника не останавливает, не пересоздаёт и не программирует
  остальные источники.
- Отключённый контекст не проходит `PrepareHardware`, не получает рабочий поток
  и не собирает данные. Повторное включение готовит и запускает только этот
  источник, если сбор уже активен.

Приёмочная проверка: отключение Mera File и `OK` не создаёт в логе сообщения
`Hardware configuration changed`, не вызывает программирование MIC-140/MC-032
и не задерживает закрытие диалога на время аппаратной инициализации.
Изменение аппаратного параметра одного прибора создаёт в логе ровно одну строку
`Runtime source reconfigured` с его `SourceId`.
# Клиенты кольцевых буферов тегов

Когда конкретный клиент многократно читает кольцо тега, его клиентская обёртка
хранит собственный номер прочитанного блока и рабочий буфер. Перед блокировкой
кольца и копированием она сравнивает номер со счётчиком тега. Не переносить эту
ответственность в движок или общий менеджер без отдельной архитектурной задачи.
Подробный контракт описан в `Docs/tag-data-client-model.md`.

# Недоступное устройство — штатное состояние

- Перед `Connect`, `Init`, `Config`, чтением памяти или калибровки выполнять невыбрасывающий `TestLink`.
- `TestLink` и общий уровень подготовки источника обязаны преобразовать транспортное исключение в `False` и текст ошибки.
- При неуспешном TEST пометить только этот `SourceId` как offline, записать причину в журнал и не вызывать последующие аппаратные операции.
- Offline-источник не получает поток сбора. Успешный повторный TEST или явный сброс снимает offline-состояние.
- Пользовательское отключение источника и потеря связи — разные состояния: первое сохраняется в конфигурации, второе является диагностикой текущей сессии.
# Размещение компонентов мнемосхемы

## Связанные поля временного диапазона

Если диалог одновременно показывает `От`, `До` и длительность окна, эти поля
образуют один инвариант: `Окно = До - От`. Изменение `От` или `До` обязано
пересчитать окно; изменение окна пересчитывает `От`, сохраняя `До`. Проверка:
после потери фокуса любым полем все три значения согласованы, а `До > От`.

Исторический график обязан отображать серию из одной точки отдельным маркером;
проверка только соединяющей линии недостаточна.

При выборе инструмента добавления хранить только тип будущего компонента. Модель
компонента создаётся и добавляется в `TRecorderFormPage` только после щелчка по
полотну; после создания инструмент обязан отжаться. Проверка: до щелчка
`ComponentCount` не меняется, после одного щелчка увеличивается ровно на один.

При смене режима edit/runtime интерактивные LCL-controls должны пересоздаваться
или явно получать полный набор обработчиков нового режима. Проверка: в edit
щелчок только выделяет компонент, в runtime тот же щелчок выполняет его команду.

Состояние, управляемое и тегом, и отдельным UI-переключателем, после успешного
изменения обязательно публиковать в этот тег. Проверка: оба входа немедленно
дают одинаковое значение тега и одинаковое состояние подсистемы.
## Отсечение линий графика при зуме

При панорамировании или зуме не ограничивать экранные координаты точек границами области построения: это прижимает внешние значения к рамке и искажает форму сигнала. Клиповать каждый отрезок по прямоугольнику графика, сохраняя соседние точки за его границами для расчёта пересечения; маркеры рисовать только для точек внутри окна. Проверка: сегмент между внешней и внутренней точкой доходит до рамки, а две внешние точки на одной стороне не отображаются.
## Цвет нормального состояния и исключений

Метод получения цвета тревоги должен возвращать нейтральный sentinel `0`, если нет активной уставки. Нельзя реализовывать цвет исключительного состояния заменой результата по умолчанию: серый цвет допустим только в явной ветке `OutOfRange`. Проверять три независимых случая: нормальное значение без тревоги, активная уставка, выход за допустимый диапазон.

## Пакетное удаление узлов UI, владеющих моделью

Перед удалением нескольких элементов дерева сначала снять отдельный список объектов модели. После первого `DeleteBinding`, `DeleteNode` или другого освобождающего вызова запрещено повторно читать `TTreeNode.Data` и проверять тип объекта по сохранённому адресу. Родительские и дочерние элементы обрабатывать без двойного удаления: выбранный родитель поглощает удаление своих выбранных детей. Производные теги удалять по устойчивому признаку владельца только после применения новой конфигурации и только если на источник больше не ссылается ни один оставшийся алгоритм.

Приёмочная проверка: выделить через Ctrl/Shift несколько дочерних узлов, затем смешанную выборку родителя и ребёнка, дважды подряд выполнить удаление; исключений и оставшихся осиротевших производных тегов быть не должно.
# Адреса аппаратных каналов нескольких одинаковых приборов

- Адрес физического канала обязан включать устойчивый логический номер конкретного источника. Нельзя прошивать один номер узла для всех экземпляров прибора.
- Каталог каналов, настроечный диалог, сохранение проекта и runtime-драйвер должны получать номер узла из одного общего метода.
- Имя тега может быть человекочитаемым, но аппаратная идентичность определяется парой `SourceId + Address`.
- Нельзя переиспользовать найденный по имени аппаратный тег, если его `SourceId` отличается от создаваемого источника.

# Единственный владелец TCP-соединения аппаратного прибора

- Для одного аппаратного endpoint `host:port` в RecorderLnx одновременно существует только один TCP-клиент — клиент активного runtime-источника.
- Диалог настройки не должен создавать второе соединение, если endpoint уже принадлежит runtime. Он сохраняет конфигурацию, а её применение выполняется штатной переинициализацией соответствующего источника.
- Данные для подписей UI (серийный номер, версия, состояние) сначала читать из runtime-кэша или live-device, не выполняя дополнительный `Connect` и не отправляя диагностический запрос при каждом перестроении дерева.
- Приёмочная проверка: открыть подключённый MIC-185, изменить настройку и нажать OK — исключения `already has an active TCP client` быть не должно; в дереве остаётся один узел с подписью `SN=<номер>`.
