# Архитектура SQL-хранилища RecorderLnx

**Статус:** рабочая архитектура и план развития  
**Версия схемы:** 6  
**Дата:** 09.11.2026

## 1. Решение в одном абзаце

Firebird остаётся основной БД RecorderLnx на текущем этапе. Поток порядка 300
скалярных значений в секунду для него мал. Обнаруженная задержка была вызвана не
пределом СУБД, а размещением файла `.fdb` внутри loop-образа ext4 на NTFS/FUSE и
долгоживущей транзакцией клиента. Рабочий файл перенесён на локальный native
ext4 сервера `192.168.9.92`; запись выполняется кадрами и каждый кадр завершается
полным `COMMIT`. Архитектурный резерв — PostgreSQL. Репозиторий уже умеет
создавать `TPQConnection`, поэтому переход не требует менять предметную модель.

## 2. Границы системы

SQL-хранилище отвечает за долговременные скалярные значения, события, сведения
об объектах и испытаниях, ссылки на файлы замеров и состояние экземпляров
RecorderLnx. Оно не заменяет проект RecorderLnx: каналы, мнемосхемы и графики
остаются в проектной конфигурации. Параметры подключения являются системными и
должны иметь один источник истины — `app.ini`; проектный `sql-db.ini` хранит
только выбор каналов, период записи и параметры отображений.

## 3. Развёртывание

| Роль | Значение |
|---|---|
| Сервер Firebird | `192.168.9.92:3050` |
| Файл БД | `/var/opt/mera/firebird-native/recorderlnx.fdb` |
| Файловая система | локальный ext4 на сервере |
| Клиенты | KIP-1…KIP-4, АРМ, сервисные утилиты |
| Доступ | только через Firebird TCP/IP |
| Схема | создаётся и мигрирует `TRecorderSqlDbRepository` |

Файл БД нельзя размещать на Samba/NFS, в FUSE-слое или в loop-образе на другой
файловой системе. Сетевой доступ предоставляется сервером Firebird, а не общей
папкой с `.fdb`.

## 4. Поток данных

```text
приборы -> источники RecorderLnx -> реестр тегов
                                  |
                                  v
                     TRecorderSqlDbManager
                                  |
                       снимок разрешённых тегов
                                  |
                                  v
                     TRecorderSqlDbRuntime
                                  |
                       очередь кадров (bounded)
                                  |
                                  v
                  TRecorderSqlDbWriterThread
                                  |
                     один кадр = одна транзакция
                                  |
                                  v
                  TRecorderSqlDbRepository -> Firebird

Firebird -> один пакет актуальных значений -> SQL data source -> обычные теги
Firebird -> диапазон значений/событий -> SQL trend -> линии, оси, экспорт
```

Кадр формируется с заданным периодом и содержит по одному значению каждого
разрешённого канала. Репозиторий сначала разрешает идентификаторы сигналов,
затем пишет значения пакетами. После кадра выполняется полный `COMMIT`, поэтому
читатели видят кадр целиком. Зеркальные теги SQL data source повторно в SQL не
записываются, что исключает цикл чтение → запись.

## 5. Компоненты

| Компонент | Ответственность |
|---|---|
| `TRecorderSqlDbManager` | включение записи, период, настройки, команды RCPanel |
| `TRecorderSqlDbRuntime` | таймер, снимок тегов, ограниченная очередь, состояние |
| `TRecorderSqlDbWriterThread` | последовательная запись кадров вне UI-потока |
| `TRecorderSqlDbRepository` | SQL, транзакции, DDL, миграции, чтение трендов |
| `TRecorderSqlDataSource` | пакетное чтение последних значений как обычных тегов |
| `TRecorderSqlTrendView` | исторические диапазоны, события, масштаб и экспорт |
| `TRecorderSqlDbProjectManager` | проектные настройки и список разрешённых каналов |
| RCPanel/Coordinator | централизованные команды хоста, периода и разрешений |

Основной объём создаёт `signal_values`. Историческая точка ссылается на
`signals.id`, поэтому переименование канала не требует переписывать историю.
Идентичность физического канала определяется сочетанием объекта, источника и
адреса Recorder, а имя является отображаемым атрибутом.

## 7. Индексы и типовые запросы

Критические индексы: `signals(name)`, `signal_values(signal_id,
timestamp_utc)`, `signal_values(registration_id)`, `events(event_type,
timestamp_utc)`, `events(registration_id)`, `tests(object_id,started_at)` и
`registrations(object_id,test_id,started_at)`. Запрос тренда обязан фильтровать
по `signal_id` и ограничивать диапазон времени. Последнее значение группы тегов
читается одним пакетным запросом, а не отдельным запросом на каждый тег.

## 8. Транзакции и устойчивость

1. Один период записи формирует неизменяемый кадр.
2. Один writer последовательно пишет кадры; параллельных writers внутри одного
   RecorderLnx нет.
3. Один кадр соответствует одной короткой транзакции.
4. Подготовленные batch-запросы принадлежат транзакции и уничтожаются после
   полного `COMMIT`.
5. Ошибка кадра откатывает только этот кадр и переводит runtime в состояние
   ошибки; UI и устройства продолжают работать.
6. Очередь ограничена. Переполнение должно учитываться счётчиком пропусков, а
   не бесконтрольным ростом памяти.
7. Событие выхода за уставку не генерируется при первом чтении уже аварийного
   значения; требуется переход состояния.

## 9. Эксплуатация Firebird

- файл БД — только на физически подключённом локальном диске сервера;
- `Forced Writes` оставлять включённым;
- использовать SuperServer и единый серверный процесс;
- размер page cache выбирать по доступной памяти и контролировать фактический
  cache hit rate, а не задавать максимально возможное значение;
- ежедневно выполнять логический `gbak`, периодически проверять восстановление;
- контролировать размер БД, свободное место, oldest/next transaction, число
  активных соединений, p95 времени записи кадра и возраст последней точки;
- плановый `sweep`/backup-restore выполнять в окно обслуживания;
- не копировать работающий `.fdb` обычным файловым копированием;
- логировать на уровне кадра: длительность, число точек, commit, очередь,
  отклонённые кадры и текст первой ошибки; штатные успешные кадры не спамить.

Рекомендуемые сигналы тревоги: последняя точка старше двух периодов записи;
p95 commit дольше одного периода; очередь занята более чем на 50%; свободное
место ниже 20%; рост ошибок подключения или rollback.

## 10. Оценка альтернатив

| СУБД | Лицензия | Сильные стороны | Ограничения для RecorderLnx | Решение |
|---|---|---|---|---|
| Firebird 5 | свободная IPL/IDPL | простое развёртывание, малый ресурс, SQL/ACID | чувствителен к файловой системе; меньше средств наблюдаемости | оставить сейчас |
| PostgreSQL | свободная PostgreSQL License | зрелая эксплуатация, партиционирование, COPY, экосистема | тяжелее администрировать | основной резерв и следующий этап |
| TimescaleDB Apache | Apache 2.0 поверх PostgreSQL | hypertable-подход для временных рядов | часть расширенных функций не входит в Apache-редакцию | только опционально |
| ClickHouse | Apache 2.0 | высокая скорость аналитики и сжатие | иной драйвер/диалект, слабее подходит для метаданных и частых корректировок | отдельный аналитический контур при очень большом объёме |
| SQLite | public domain | локальная встраиваемая БД | один файл/локальный writer, не сервер для KIP-флота | только тесты/автономный режим |

### Рекомендация

Не мигрировать по факту одной проблемы хранения. Сначала собирать метрики не
менее месяца. Готовить миграцию на PostgreSQL, когда выполняется хотя бы одно
условие: устойчивый p95 «кадр → виден читателю» больше двух периодов; объём и
retention требуют секционирования/сжатия; появляются тысячи и десятки тысяч
точек в секунду; одновременно работают тяжёлые аналитические запросы; требуется
репликация/высокая доступность штатными средствами.

Путь миграции: сохранить интерфейс `TRecorderSqlDbRepository`, довести
PostgreSQL-ветку DDL до схемы 6, писать кадр multi-row INSERT/COPY, перенести
историю отдельным проверяемым заданием, затем переключить читателей и только
после сверки количества/диапазонов переключить writers. Для TimescaleDB или
ClickHouse предметная модель меняться не должна.

## 11. Проверки перед выпуском

- KIP-1…KIP-4 пишут в один заданный сервер и путь;
- канал `3Е64` появляется каждые 6 секунд и виден на АРМ не старше 12 секунд;
- перезапуск Firebird, KIP и АРМ не создаёт дубликаты сигналов;
- SQL data source читает последние значения одним запросом;
- SQL trend читает диапазон пакетно и не сбрасывает пользовательский zoom;
- mirrored SQL tags нельзя включить в обратную SQL-запись;
- недоступный сервер отображается как «SQL недоступен», без исключения UI;
- backup восстанавливается на отдельном тестовом файле.
