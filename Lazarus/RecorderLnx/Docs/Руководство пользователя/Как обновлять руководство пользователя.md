# Как создавать и обновлять руководство пользователя RecorderLnx

## 1. Назначение процесса

Эта инструкция описывает повторяемое обновление руководства после изменения
интерфейса RecorderLnx. Программа сама открывает формы, создаёт PNG-снимки с
номерами интерактивных элементов и формирует технические карты элементов.
Разработчик затем сверяет снимки и актуализирует пользовательские описания.

Результаты находятся здесь:

- `Руководство пользователя RecorderLnx.md` — основной документ;
- `screens/*.png` — нумерованные снимки форм;
- `screens/*.elements.md` — автоматически сформированные карты элементов;
- `screens/index.md` — сводный перечень снятых форм.

## 2. Реализация генератора

Точка включения режима находится в `RecorderLnx.lpr`. Сам генератор расположен
в `UI/uRecorderUserGuideCapture.pas`.

Режим включается только аргументом `--capture-user-guide`. При обычном запуске
RecorderLnx генератор не создаётся и на работу программы не влияет.

Последовательность работы:

1. RecorderLnx загружает проект и создаёт главную форму.
2. Таймер даёт LCL завершить первичную компоновку интерфейса.
3. Генератор последовательно создаёт production-формы.
4. Форма показывается и перерисовывается в `TBitmap`.
5. На копию изображения наносятся номера видимых интерактивных элементов.
6. PNG и таблица `*.elements.md` сохраняются в выходной каталог.
7. После последней формы приложение автоматически завершается.

Нумерация не добавляет контролы в настоящую форму и не изменяет `.lfm`.

## 3. Сборка перед созданием снимков

Закройте запущенный `RecorderLnx.exe`, затем выполните forced build:

```powershell
Set-Location D:\works\OburecGH\Lazarus\RecorderLnx
C:\lazarus\lazbuild.exe -B RecorderLnx.lpi
```

Ожидаемый результат — код возврата `0`. Предупреждения и hints допустимы,
ошибки компиляции необходимо исправить до запуска генератора.

Если рабочий exe нельзя заменить из-за запущенного RecorderLnx, для проверки
можно временно собрать файл с другим именем:

```powershell
C:\lazarus\lazbuild.exe -B `
  --opt=-oD:\works\OburecGH\Lazarus\RecorderLnx\lib\x86_64-win64\RecorderLnx_guide_check.exe `
  RecorderLnx.lpi
```

Такой exe является временным проверочным артефактом и не входит в документацию.

## 4. Создание снимков в Windows

Запустите собранную программу из каталога проекта:

```powershell
Set-Location D:\works\OburecGH\Lazarus\RecorderLnx
& ".\lib\x86_64-win64\RecorderLnx.exe" `
  --capture-user-guide `
  "--guide-output=D:\works\OburecGH\Lazarus\RecorderLnx\Docs\Руководство пользователя\screens"
```

Во время прогона формы будут кратковременно появляться на экране. Не управляйте
ими мышью и клавиатурой до автоматического завершения процесса.

Снимок главной формы зависит от открытого проекта. Перед эталонным прогоном
выберите конфигурацию с содержательной мнемосхемой, тегами и компонентами, но
без секретов, персональных данных и недоступных для публикации путей.

## 5. Создание снимков в Linux

Соберите Linux-версию обычным `lazbuild -B`, затем запустите:

```bash
./RecorderLnx \
  --capture-user-guide \
  --guide-output="/path/to/RecorderLnx/Docs/Руководство пользователя/screens"
```

Для GUI-прогона требуется работающий графический сеанс и корректная переменная
`DISPLAY` или Wayland-окружение. Снимки Windows и Linux могут отличаться
метриками системного шрифта и оформлением окон, поэтому не следует смешивать их
в одном комплекте без явного указания платформы.

## 6. Проверка результата

После прогона выполните проверки:

```powershell
$screenDir = "D:\works\OburecGH\Lazarus\RecorderLnx\Docs\Руководство пользователя\screens"
Get-ChildItem "$screenDir\*.png"
Get-ChildItem "$screenDir\*.elements.md"
Select-String -Path "$screenDir\index.md" -Pattern "ошибка|Access violation"
```

Для текущего проекта ожидаются 21 PNG и 21 карта элементов: все уникальные
production LFM-формы. Не учитываются дубликаты `.lfm` в корне, `_buildverify`,
выходных каталогах и отдельных тестовых приложениях.

Проверьте вручную минимум:

- главную форму;
- самую большую форму настроек;
- изменённую в текущей итерации форму;
- форму с таблицей или графиком;
- отсутствие обрезанных подписей и пустого изображения;
- соответствие номера на PNG строке в `*.elements.md`.

Строки `ошибка создания`, `ошибка снимка`, `ошибка освобождения` или
`Access violation` в `screens/index.md` означают, что комплект не готов.

## 7. Как описывать форму в руководстве

Руководство строится не по алфавиту форм, а по пути пользователя и тракту
данных. Рекомендуемый верхний уровень: термины -> назначение -> путь данных ->
быстрый старт -> главное окно -> настройка регистратора -> источники и приборы
-> каналы/теги -> ГХ -> формуляры/компоненты -> запись/SQL -> диагностика.

Перед таблицей формы объясните:

- на каком уровне настройки она находится;
- откуда форма получает данные;
- какие объекты проекта изменяет;
- какие другие настройки зависят от результата;
- что форма намеренно не изменяет.

Для каждой пользовательской формы используйте следующий шаблон:

```markdown
![Название формы](screens/NN-file-name.png)

### Название формы/компонента

| № элемента | Назначение | Описание как работает | Клавиши |
|---:|---|---|---|
| 1 | Краткое назначение | Что меняет элемент, ограничения и результат | `Enter` |
```

Правила описания:

- название таблицы должно совпадать с именем формы или компонента;
- номера берутся с актуального PNG, а не из старой версии руководства;
- соседние однотипные поля допустимо объединять диапазоном, например `3–7`;
- описывайте пользовательский результат, а не имя Pascal-обработчика;
- не объединяйте разные по смыслу поля диапазоном только ради краткости;
- для каждого поля указывайте связь с источником, тегом, ГХ, компонентом,
  записью или SQL, если такая связь есть;
- различайте частоту источника/тега, период обновления UI и период SQL-записи;
- указывайте единицы, допустимые значения и необратимые действия;
- для кнопок `OK`, `Применить`, `Отмена` объясняйте различие;
- клавиши указывайте только если они реально поддерживаются;
- предупреждения о потере данных размещайте перед опасным действием.

Автоматическая карта `*.elements.md` содержит имя контрола, класс, подпись и
типовые клавиши. Это исходный материал для автора, а не замена пользовательскому
описанию.

## 8. Добавление новой LFM-формы

Если в проект добавлена пользовательская форма:

1. Подключите её unit в `uses` файла `UI/uRecorderUserGuideCapture.pas`.
2. Добавьте класс и стабильное имя файла в массив `CForms`.
3. Используйте имя вида `NN-short-form-name` без пробелов и русских букв.
4. Пересоберите проект и выполните полный GUI-прогон.
5. Добавьте снимок и таблицу формы в основное руководство.
6. Проверьте, что число PNG равно числу `*.elements.md`.

Обычный `TFormClass.Create` разрешён только для формы, которая корректно
инициализируется стандартным конструктором без рабочей модели.

## 9. Формы, которым нужна модель или контекст

Диалог нельзя создавать пустым, если его конструктор ожидает устройство, тег,
компонент, реестр или другой объект. Для него добавляется публичная guide-фабрика
в том же unit:

```pascal
function CreateExampleGuideForm(AOwner: TComponent): TForm;
```

Фабрика должна:

1. Создать минимальную безопасную тестовую модель.
2. Вызвать штатный конструктор диалога.
3. Передать модели правдоподобные демонстрационные значения.
4. Явно определить владельца модели и освободить её вместе с формой.
5. Не обращаться к физическому прибору, сети, рабочей SQL БД и пользовательским
   файлам.

Поля на снимке не должны оставаться пустыми, если в штатной работе они обычно
заполнены. Guide-фабрика задаёт явно демонстрационные, но правдоподобные адреса,
диапазоны, единицы, коммутацию, баланс и состояния. В тексте состояния следует
указывать `Демонстрационные данные (без связи)`, чтобы снимок нельзя было принять
за результат настоящего опроса прибора.

Примеры находятся в диалогах MIC-140 и картинки. Нельзя обходить штатную
инициализацию вызовом обычного `Create`, если деструктор или обработчики ожидают
созданные конструктором списки. Именно такой обход ранее приводил к падению
`TRecorderImageSettingsDialog` при освобождении.

## 10. Какие элементы нумеруются

Генератор нумерует видимые элементы управления следующих типов:

- кнопки;
- поля ввода и spin edit;
- combo box;
- check box и radio button;
- списки, деревья и таблицы;
- page control.

Если новый интерактивный класс не отмечается, добавьте его в `IsInteractive`,
реализуйте извлечение подписи в `ControlCaption` и при необходимости описание
клавиш в `ControlKeys`. После изменения обязательно переснимите весь комплект:
порядковые номера последующих элементов могут измениться.

## 11. Обновление руководства после изменения UI

1. Выполните forced build.
2. Переснимите весь комплект, а не одну форму.
3. Проверьте `screens/index.md` на ошибки.
4. Сравните изменившиеся PNG и `*.elements.md`.
5. Обновите номера, назначение, поведение и клавиши в основном руководстве.
6. Проверьте существование всех Markdown-ссылок на изображения.
7. Просмотрите изображения визуально в Markdown viewer.
8. Зафиксируйте обновление в `cach/notes_last_state.md`.

## 12. Критерии готовности

Обновление руководства считается готовым, когда:

- RecorderLnx собирается с кодом возврата `0`;
- генератор завершается самостоятельно;
- для каждой production LFM-формы существуют PNG и `*.elements.md`;
- `screens/index.md` не содержит ошибок;
- номера в тексте совпадают с номерами на изображениях;
- все ссылки Markdown открываются;
- изменённые формы проверены визуально;
- в снимках отсутствуют пароли и другие секреты;
- журнал проекта обновлён.
