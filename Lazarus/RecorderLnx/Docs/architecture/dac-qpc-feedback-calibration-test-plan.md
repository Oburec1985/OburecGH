# Измерение задержки USB-ЦАП и привязка QPC / deviceTime

Дата плана: 2026-10-26. Обновление 2026-10-28: реализованы первый feedback-режим, ограниченный pending-буфер, marker provider, настройки и журнал. Forced build и синтетические/production-MERA тесты прошли; аппаратная приёмка ещё не выполнена. Состояние стенда: `../../errors/2026-10-28-dac-feedback-calibration.md`.

Пользовательский сценарий первой версии: запустить сбор PXI, явно выбрать физический DAC и feedback-вход, нажать «Калибровать»; при включённой привязке обычный Play также получает собственный тестовый фронт. Глобальный старт записи больше не включает DAC автоматически; Stop останавливает его. Результат — время порогового фронта относительно спокойной предыстории. Серийная статистика/графики дрейфа из полного плана остаются следующим этапом, а не реализованным UI.

## Уточнение: зеркало в часах канала обратной связи

Цель — привязать всю шкалу зеркала DAC к аппаратной шкале выбранного feedback-канала, включая первый блок MERA. Независимая абсолютная привязка QPC нужна для абсолютной оценки задержки, но для относительной фазовой привязки DAC→feedback достаточно достоверного соответствия отсчётов и аппаратного времени фронта.

Если фронт расположен в DAC-отсчёте m, а PXI зарегистрировал его в своём времени d: `d0 = d - m/Fdac`. Для блока с первым DAC-отсчётом s: `dBlock = d0 + s/Fdac`; отсчёт i имеет время `dBlock + i/Fdac`. При фронте в отсчёте 0 и времени 4.1 с в шкале PXI следующий непрерывный блок после 200 мс начинается в 4.3 с. Условие — непрерывное воспроизведение; underrun/перезапуск требует новой привязки, длительная работа — оценки отношения частот DAC/PXI.

Не смешивать шкалы: если d — абсолютное контроллерное время, результат тоже абсолютный. Если 4.1 — секунды от старта Recorder, перевод через карту PXI↔QPC выполняется явно. Пара «получено в ПК в 1 с, deviceTime=10 с» сама по себе не доказывает offset=9 с: нужно знать отсчёт/событие, к которому относится deviceTime, и учесть доставку.

В оригинале MX-248 наследует CMX255/CMX224v14. `mx224v14/mx224v14.cpp:1381` обрабатывает ADCTIME0 с SampleClk_, SyncClk_, Clk_; `mx224v14ain.cpp:1080` вычисляет PROP_START_OFFSET как Corr + (Sample0-StartDAQ)/DaqClk. `rc_core/MeasurementTag.cpp:2172` добавляет offset к времени блока и сохраняет начало первого блока; `rc_core/TagMeraInfoWritter.cpp:143` использует его для Start= в обычном относительном режиме. Оригинал не ограничивается sample cursor. Интерполяция device→UTS есть в `devapi/Device.cpp:556`, но это ещё не доказанная карта QPC: точная цепочка controller↔PC для MX-248 требует дальнейшей проверки.

В RecorderLnx калиброванные блоки должны иметь общий clock domain и origin с feedback. `UI/uMainForm.pas:3344` нормализует время по origin домена, writer `Core/uRecorderDataStorage.pas:903` запоминает первый X как Start. Собственный origin зеркала уничтожит задержку; сырые PXI seconds нельзя помечать recorder-monotonic.

Обратная связь приходит позже первого сгенерированного блока: начальные DAC-блоки следует удержать до определения привязки и затем публиковать/писать с правильным временем, либо реализовать явную ретроспективную коррекцию всех потребителей и файла. Предпочтителен ограниченный pending-буфер с таймаутом/лимитом и явной ошибкой при отсутствии feedback. Нельзя смешивать предварительные и калиброванные времена. На каждый пуск новая привязка, включая времена порций MERA. Исходные индексы DAC и QPC сохраняются как provenance.

Привязка устраняет временной сдвиг, но не произвольную частотно-зависимую фазу аналоговых фильтров — её при необходимости измеряют отдельно.

## Назначение

В компоненте ЦАП предлагается режим «Измерение задержки по обратной связи», прежде всего для USB-аудиоустройства. Выбирается входной тег аппаратного АЦП; выполняется серия пусков с известным маркером, сохраняются результаты каждого пуска. Это измерение тракта, а не безусловная аппаратная синхронизация.

Для будущего PXI-ЦАП основной путь другой: общий аппаратный триггер и, при поддержке платами, общий такт/reference clock. Один триггер согласует начало, но не устраняет дрейф независимых генераторов. Обратная связь остаётся средством проверки задержки аналогового тракта. Поддержку общего такта и триггеров конкретными драйверами ещё необходимо подтвердить. Связь общего аппаратного события с QPC — отдельная задача.

## Что реализовано сейчас

- `Core/uRecorderBlockClock.pas`: Windows QPC, Linux monotonic clock; преобразование deviceTime в RecorderTime только сдвигом, без оценки скорости/дрейфа часов.
- `Device/DAC/Core/uRecorderDacSession.pas`: якорь — середина вызова Start, с оценкой неопределённости и добавлением длительности блока. В Pump QPC фиксируется перед SubmitBlock. Это не время появления напряжения на выходе; один блок — эвристика, не гарантированная граница очереди.
- `Device/DAC/Core/uRecorderDacTagMirror.pas`: зеркало сохраняет переданную временную шкалу блока и шаг 1/Fs, а не время обновления UI. Время отправки и неопределённость не являются отдельными отсчётами выходного тега.
- `Device/DAC/Audio/uRecorderAudioDacBackend.pas`: блокирующий PortAudio WriteStream. API stream time/info и callback timestamps сейчас не подключены.
- `Device/PXI/MX248/Runtime/uRecorderPxiMx248DataSource.pas`: аналогичная приблизительная привязка по середине Start.
- `Device/PXI/MX248/Transport/Windows/uRecorderPxiMx248WindowsTransport.pas`: FirstTimeSec = fSampleCursor / Fs. Это программно восстановленная шкала отсчётов, не прочитанный аппаратный timestamp. Потеря данных/непрерывность требуют явного контроля.
- Для остальных драйверов нельзя автоматически считать временную область такой же. Проверка проведена для DAC и MX248; старое описание time-system.md не полностью отражает актуальный код.

## Предлагаемый интерфейс

Выбор физического ЦАП, входного feedback-тега (поиск по подстроке имени/адреса/описания, хранение stable TagID), числа повторов, пауз, маркера и безопасной амплитуды. Вход должен давать исходные аппаратные отсчёты с известной Fs и временной областью; виртуальное зеркало ЦАП не является физической обратной связью.

Кнопки «Подготовить», «Запустить серию», «Стоп». Таблица: номер пуска, QPC отправки, индекс и deviceTime обнаружения, наблюдаемое смещение, длительность отправки, качество обнаружения, статус/причина недостоверности. Итоги: медиана, минимум/максимум, p95, разброс, число успешных/ошибочных попыток; для длинной записи — дрейф ppm и остатки модели.

В общей архитектуре разделить стратегии HostEstimated, UsbFeedbackMeasured и PxiHardwareSynchronized. Последняя допустима только после подтверждения настройки и аппаратного события. Калибровка не должна незаметно менять raw timestamps всех тегов.

## Стенд и процедура

1. Один компьютер выполняет DAC и захват PXI: QPC разных компьютеров нельзя непосредственно вычитать. Для MIC315 закрепить именно Sound Blaster PLAY! 3 VID_041E/PID_324D, не Remote Audio и не автоматически подставленный default endpoint.
2. Соединить аналоговый выход USB-ЦАП с входом PXI, проверить допустимые напряжения, ослабление, землю, coupling; отключить питание датчика/IEPE, если оно не требуется. Конкретное подключение согласовать с электрическими характеристиками входа.
3. Запустить непрерывный захват АЦП до первой попытки и не переякоривать его между пусками. Сохранять raw вне ограниченного кольца тега (оно может содержать лишь несколько секунд).
4. Выдать тишину, уникальный ограниченный по амплитуде кодированный пакет/свип, затем тишину. Бесконечный синус неоднозначен на целый период; DC-ступень непригодна как универсальный маркер аудиовыхода с AC coupling.
5. Выполнить 50–100 попыток, сохраняя все исходы. Отдельные серии: холодный Start/Stop потока и маркеры внутри уже работающего потока. Не смешивать startup latency и steady-state latency.
6. Для дрейфа — маркеры на протяжении 10–20 минут внутри непрерывного потока. Повторить при нескольких поддерживаемых размерах блока и под нагрузкой; host API исследовать раздельно.
7. Проверить Stop, повторный запуск, разрыв/переподключение, underrun/overflow и пропуск данных. После смены устройства/настроек предыдущую калибровку не применять автоматически.

## Какие события записывать

QPC raw ticks и frequency, идентификатор часов/запуска, run ID и generation; QPC до/после native Start и WriteStream, индекс блока и первого отсчёта маркера, Fs, число кадров, выбранный endpoint/host API. Для АЦП — Start brackets, непрерывный индекс отсчёта, исходные метаданные блока, Fs, счётчики потерь; QPC получения/публикации — только диагностика доставки, не timestamp измеренного сигнала.

Инструментировать фактическую границу вызова драйвера. Возврат WriteStream не означает, что аналоговый сигнал уже прозвучал; длительность блокирующего вызова не считать точностью timestamp. При дальнейшем подключении PortAudio callback time info отдельно сопоставить его timebase с QPC и проверить оценку физическим loopback.

События складывать в заранее выделенную очередь; экспорт CSV/бинарных данных вне горячего цикла. Не писать лог на каждый отсчёт и не выполнять анализ/UI в потоке выдачи.

## Расчёт и принципиальное ограничение

Маркер искать нормированной корреляцией исходных отсчётов с шаблоном в частоте АЦП. Учитывать resampling, положение начала шаблона, огибающую и задержку фильтров. Сохранять индекс пика, неоднозначность, SNR, клиппинг. Интерполяция пика может улучшить оценку, но не доказывает субдискретную точность.

Пусть n — индекс обнаружения в непрерывном потоке АЦП, q — QPC отправки, j — положение начала маркера внутри отправленного блока. При имеющейся карте часов наблюдаемое смещение:

`Delta = mappedAdcQpc(n) - (q + j / Fdac)`.

Это операционная оценка относительно выбранного события отправки; j/Fdac — номинальная поправка, а не доказанное время выхода. Более общая модель: `adcQpc(n) = a + b*n`, наблюдения `a + b*n_k = q_k + j_k/Fdac + L_k`.

Из одного loopback нельзя независимо определить a (эпоху АЦП) и постоянную L (задержку DAC/очередей/аналогового входа). Повторы оценивают составное смещение и jitter. Дрейф оценивается при достаточно стабильной статистике задержки, а не из произвольного сдвига каждого пуска.

Для абсолютной USB-задержки нужна независимая привязка АЦП к QPC: аппаратное событие с timestamp, либо чтение аппаратного счётчика с QPC-bracketing и обоснованной неопределённостью. Дополнительно учесть групповую задержку АЦП. Сначала выяснить доступность таких механизмов у MX248/bridge. Без них результат явно маркировать «приблизительная host-привязка / суммарная задержка тракта».

## Проверка и результат

Сначала синтетические тесты известных offset/drift/delay, шумов, неоднозначного маркера, пропущенных блоков и смены generation. Затем аппаратный прогон с сохранением raw; проверочные маркеры, не участвовавшие в подгонке. Порог допустимой задержки/разброса задать до прогона, исходя из задачи.

Отчёт содержит каждый пуск, метрики, неопределённость и причины брака; недостоверные попытки не удаляются молча. Калибровочная запись привязана к устройствам, host API, драйверу, Fs, буферам, входным фильтрам/coupling и сеансу часов. Raw остаётся неизменным; коррекция — отдельная явно включаемая модель с происхождением и областью действия.

## Реализация двухфронтовой привязки (2026-10-28)

Два одинаковых положительных маркера длительностью 20 мс разделены заданным
интервалом 0.1–30 с (по умолчанию 2 с). Индексы фронтов округляются в целые
отсчёты DAC до расчёта. По временам их отклика в выбранном канале вычисляются
`Fs_eff=(n2-n1)/(t2-t1)` и `start=t1-n1/Fs_eff`. До получения обоих фронтов
данные зеркала удерживаются; после проверки публикуются с `t=start+n/Fs_eff`.
Номинальная частота аппаратуры не меняется. Проверяются диапазон ±1%,
таймаут, переполнение и непрерывность входного канала. Время ожидания должно
превышать интервал между фронтами с запасом на запуск.

Эффективная частота записывается в метаданные зеркального тега до публикации.
История зеркала заранее рассчитана на timeout+2 с. При изменении измеренной
частоты в уже открытом MERA кадре канал получает явные X; предыдущие порции
восстанавливаются с учётом их `.prt` начал и пауз, пакетами по 8192 отсчёта.
Первичная частота дескриптора не переписывает прошлую историю.

Корреляция по пожеланию пользователя не применяется. Пороговая привязка
содержит задержку аналогового тракта и зависит от формы отклика; постоянная
остаточная фаза сама по себе не доказывает ошибку часов. Рабочая фаза
измеряемого тракта автоматически не удаляется. Аппаратная приёмка новой
двухфронтовой сборки на MIC315 пока не выполнена.

## Актуальный режим калибровочного сигнала (2026-10-28)

Настройка «Время калибровочного сигнала» задаёт всё окно, по умолчанию 5 с.
Первый фронт расположен в 0.1 с, второй — за 0.3 с до конца окна; длительность
каждого импульса 20 мс. Расстояние фронтов получается duration−0.4 с. Ручной
порог и старая настройка интервала больше не управляют детектором.

После noise-gate кандидат накапливается в заранее выделенном 16-мс окне.
Уровень ступени оценивается по устойчивой части отклика, midpoint находится
по первому пересечению половины высоты с линейной интерполяцией. Нестабильные
кандидаты отвергаются; полярность обоих принятых маркеров должна совпадать.
Источник привязывается к середине перехода между отсчётами n−1 и n,
то есть n−0.5. Корреляция не вычисляется.

Опция запуска потока выбирает вход в Preview или первый Play. При старте
в Preview калибровка выполняется заранее, затем идут нули до Play; при старте
по Play после калибровочного окна сразу начинается выбранный сигнал. После
Play/Stop поток остаётся открытым на нулях, его frame counter не сбрасывается.
Конечный Pulse останавливает лишь gate. Полный Stop Recorder закрывает поток
и инвалидирует привязку. Record↔Preview не меняет DAC-сессию.

Смена waveform подменяет подготовленный provider под control-lock; backend
Configure/Start не повторяются. Смена устройства/Fs/feedback требует нового
потока и калибровки. Ожидание первого нового ADC блока после входа в Preview
проверяет cursor, а не сравнивает его приблизительный host timestamp с QPC.
Подготовка/отмена не зависят от видимости виджета.

Измеренная Fs_eff применяется также к синтезу рабочего сигнала: внутренний
provider получает копию nominalConfig с SampleRateHz=Fs_eff. Поэтому шаг
фазы, Sweep/Pulse времена и ресэмплирование входного тега соответствуют
фактическому темпу отсчётов. Native backend config и калибровочные индексы
остаются номинальными. Подготовка выполняется один раз в control timer;
до её успешного завершения выбранный сигнал заблокирован и выдаются нули.
Замена provider использует сохранённую Fs_eff; повторное применение того же
значения не сбрасывает фазу.

## Режим запуска калибровки фазы (2026-10-29)

Радиогруппа задаёт событие калибровки отдельно от Play/gate:

- При старте измерения: Stop→Preview/Record запускает калибровочный поток;
  последующий Play использует его привязку. Record↔Preview не калибрует снова.
- По кнопке Play: каждый явный пуск выполняет новую калибровку; редактирование
  частоты/амплитуды вызывает ApplyOutputSettings и не считается новым Play.
- По кнопке: Preview и Play не генерируют маркеры; явная верхняя кнопка
  «Калибровка фазы» запускает тест и возвращает прежнее состояние play/mute.

Новое поле DacPhaseCalibrationMode сохраняется как enum0..2. Для прежних
конфигураций DacStartStreamOnPreview=true соответствует первому режиму,
false — второму. Кнопка доступна в верхней части старых низких виджетов.
Обычный Play при автоматической калибровке ставит рабочий сигнал в очередь,
а не превращается в отмену из-за одного CalibrationRunning.

При отсутствии сохранённого endpoint список не подставляет первое устройство:
это могло скрыто выбрать Remote Audio. Ошибка выводится рядом с Play.
На RDP-клиенте audiomode:i:1 оставляет звук на удалённом компьютере; настройка
применяется к новому подключению. Default.rdp клиента для MIC315 исправлен
с0 на1, со сделанной резервной копией; текущий сеанс надо переподключить.
