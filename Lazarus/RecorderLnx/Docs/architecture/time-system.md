# Система времени RecorderLnx

## Назначение

Система времени связывает относительную шкалу каждого измерительного канала с астрономическим временем. Это позволяет открыть данные SQLdb как тренд за календарный интервал и совместить медленные значения, события, спектры и осциллограммы по одной временной оси.

Главный инвариант:

```text
AbsoluteUtc = SessionStartUtc + ChannelTimeSec / 86400
```

`SessionStartUtc` фиксируется при переходе `Stop -> Preview` или `Stop -> Record`. Если запись включена из уже работающего Preview, начало временной шкалы не меняется. `ChannelTimeSec` — timestamp конкретного отсчёта в секундах от начала текущего сеанса.

## Две связанные шкалы ПК

При старте `TRecorderTimeSystem` почти одновременно фиксирует:

- `StartLocalTime` — календарное локальное время для интерфейса;
- `StartUtcTime` — календарное UTC-время для хранения и обмена;
- `StartTickMs` — монотонный счётчик `GetTickCount64`, аналог назначения `QueryPerformanceCounter` в оригинальном Recorder.

Календарные часы ПК могут быть переведены пользователем, NTP или службой времени. Поэтому после старта длительность сеанса считается по монотонному счётчику, а не повторными вызовами `Now`. Изменение часов ПК посреди записи не создаёт скачка временной оси.

## Оригинальный Recorder

Проверенная схема оригинала:

- `CRcCore` при старте фиксирует `m_systimeFrameStart` (`GetLocalTime`);
- кадр данных содержит `FRAME.dblTimeDevice` и `FRAME.dblTimeUTS`;
- аппаратный источник передаёт своё внутреннее время через `PushDataEx`;
- если собственного времени нет, `CBufferSupportTag` использует счётчик Recorder (`GetTimeCounter`);
- первое аппаратное время канала сохраняется как `SignalStartTime`;
- свойство `RCPROP_STARTTIME` и заголовок MERA отдают астрономическое время начала кадра.

RecorderLnx повторяет эту модель без Windows-зависимого COM: абсолютный якорь хранится в `TRecorderTimeSystem`, а относительное время проходит вместе с точкой через реестр тегов.

## Аппаратные каналы

Аппаратный драйвер формирует время блока и каждого отсчёта:

```text
SampleTimeSec[i] = Block.FirstTimeSec + i / SampleRateHz
```

Если прибор передаёт собственный счётчик, драйвер должен нормализовать его к моменту запуска текущего сбора. Если прибор timestamp не передаёт, источник использует монотонное время ПК относительно старта сеанса. Сетевое время получения пакета нельзя подставлять вместо времени отсчёта: задержка сети не является временем измерения.

Для MIC-140 и MIC-185 `FirstTimeSec` строится из индекса первого отсчёта и частоты дискретизации. Служебные значения MIC-140 используют текущий конец аппаратного блока, а не uptime операционной системы.

## Виртуальные и расчётные каналы

- Программные генераторы и диагностические каналы начинают шкалу с `0` при каждом `Start` и увеличивают её на свой период обновления.
- Расчётный канал должен наследовать timestamp входного отсчёта или согласованное время конца входного блока. Время завершения вычисления использовать нельзя.
- Оценка блока (СКО, математическое ожидание, максимум, полоса спектра) привязывается к документированному якорю блока; для текущей runtime-модели это timestamp опубликованного результата, полученный из входных данных.
- При воспроизведении MERA сохраняется временная шкала файла; она не заменяется временем чтения файла.

## SQLdb и будущий тренд

До этой доработки SQLdb записывала `Now` в момент обработки очереди, поэтому сохранялось время записи в БД, а не время измерения канала. Теперь `TRecorderSqlDbManager` использует `TRecorderTagUpdateEventData.TimeSec` и переводит его через `TRecorderTimeSystem.ChannelTimeToUtc`.

В `signal_values.timestamp_utc`, `events.timestamp_utc`, полях регистраций и якорях файлов хранится UTC как `TDateTime`/OLE Automation `Double`: целая часть — число суток от 30.12.1899, дробная — время внутри суток. Для показа пользователю значение переводится из UTC в локальную временную зону только на уровне интерфейса.

Будущий запрос тренда выбирает один или несколько `signal_id` и календарный диапазон `[fromUtc, toUtc]`, сортирует по `timestamp_utc`, а затем переводит X-координаты в локальное время для подписей. Файлы и события выбираются по той же UTC-шкале, поэтому маркер спектра или осциллограммы попадает в правильную точку тренда.

## Правила для новых источников

1. Timestamp относится к моменту измерения, а не к моменту доставки или записи.
2. Шкала нового живого сеанса начинается с нуля либо явно нормализуется к старту RecorderLnx.
3. Внутри сеанса время не убывает; переполнение/сброс аппаратного счётчика обрабатывает драйвер.
4. `Now` не вызывается для каждой точки и не используется как замена timestamp канала.
5. SQL, события и файлы используют один UTC-якорь `TRecorderTimeSystem`.

## Автоматическое время PublishValue

`TRecorderTagRegistry.PublishValue(TagName, Value)` автоматически присваивает точке текущее
относительное время Recorder (`TRecorderTimeSystem.Snapshot.ElapsedSec`). Тот же расчёт
выполняется для полной формы `PublishValue(TagName, TimeSec, Value)`, если `TimeSec <= 0`.
Положительный timestamp считается явно заданным временем канала и сохраняется без изменения.
Если реестр используется автономно без `TRecorderTimeSystem`, применяется монотонное время от
момента создания реестра.
