# Архитектура ЦАП RecorderLnx

## Цель

Добавить в RecorderLnx потоковый аналоговый выход, который одинаково работает
с аудиоустройством Windows/Linux и с аппаратным модулем (например PXIe), не
связывая генератор сигнала, теги, UI и API конкретного драйвера.

Поддерживаются два основных маршрута:

```text
компонент формы/генератор -> источник отсчётов -> сессия ЦАП -> backend -> железо
                                                |
                                                +-> зеркало фактического блока -> тег

генерируемый или измерительный тег -> клиент кольца -> источник отсчётов -> сессия ЦАП
```

Компонент формы хранит конфигурацию и управляет запуском, но не генерирует
данные из UI-потока. Поток вывода работает с моделью компонента либо с тегом.

## Что показал `plgControlCyclogram`

- `TDacProgram` формирует нормализованный блок, затем переводит его в PCM.
- `TSoundCardDac` владеет WinMM, очередью блоков и потоком дозаполнения.
- `TDacVectorTagMirror` публикует копию сгенерированного блока в тег.
- `cDacControl` связывает шаг циклограммы с writable-тегом и задаёт значение
  через `ITag.PushValue`; это полезный принцип маршрутизации, но не контракт
  аппаратного ЦАП.

Переносить эту иерархию буквально нельзя: базовый `TDacDevice` зависит от
Windows, знает о тегах и о формате звуковой карты, а программа генерации знает
конкретный `PSoundCardBlock`. Эти зависимости мешают Linux и PXIe backend.

## Границы модулей

### 1. Core: формат и источник отсчётов

`IRecorderDacSampleProvider` заполняет предоставленный вызывающим кодом
предвыделенный массив `Double` и сообщает число кадров. Каналы хранятся
interleaved. Значения находятся в инженерных единицах до применения диапазона
и калибровки конкретного выхода.

Первая пара реализаций:

- `TRecorderDacWaveProvider` — читает snapshot модели генератора формы;
- `TRecorderDacTagProvider` — читает непрочитанные блоки тега через собственный
  cursor и `SnapshotNextBlockInto`.

Provider не открывает устройство, не создаёт теги и не знает PCM/DAQ-кодов.

### 2. Device: сменный backend

`IRecorderDacBackend` представляет один тип транспорта/драйвера. Его жизненный
цикл явный:

`Discover -> Connect -> Initialize -> ReadProperties -> Configure -> Start -> Stop -> Disconnect`.

Минимальные операции backend:

- перечислить endpoint и возможности;
- открыть одну сессию;
- согласовать частоту, каналы, диапазоны и размер блока;
- принять готовый блок без выделения памяти в горячем пути;
- сообщить underrun, фактически принятый размер и аппаратное время, если оно есть;
- безопасно остановить выход (ноль, hold или заданное safe value).

Реализации регистрируются фабриками по стабильному `BackendId`. Первая пара —
`null` для тестов и единый `audio.portaudio` на PortAudio V19 для Windows и
Linux. Различается только динамически загружаемая нативная библиотека. PXIe
добавляется отдельным vendor-backend. Условная компиляция и нативные API
разрешены только внутри конкретного backend.

### 3. Runtime: сессия и синхронизация

`TRecorderDacSession` — стабильный оркестратор. Он владеет provider, backend,
предвыделенными буферами, состоянием и диагностикой. Такт задаёт backend:
callback или worker запрашивает следующий блок, а не UI-таймер.

Состояния: `closed`, `connected`, `initialized`, `configured`, `running`,
`stopping`, `offline`. Ожидаемые ошибки драйвера возвращаются кодом результата
со стадией и endpoint; исключения оставляются только для нарушения инвариантов.

Политики underrun задаются конфигурацией: `zero`, `hold-last`, `stop`. Для
физического выхода по умолчанию безопаснее `zero`.

### 4. Адаптер тегов

Зеркало ЦАП — отдельный tap после ограничения диапазона и калибровки, но до
квантования в формат драйвера. Поэтому тег показывает то, что было реально
передано на выход, а не идеальную форму до ограничений.

Обратный маршрут использует `TRecorderDacTagProvider`. Он имеет собственный
cursor и не назначается единственным глобальным `OnBlockPublished` registry.
Если частота тега отличается от частоты устройства, требуется явно выбранная
политика: запрет запуска либо отдельный resampler. Первая версия должна
запрещать несовпадение частот, чтобы не скрывать изменение формы сигнала.

Нельзя выбирать тег зеркала как вход той же сессии: конфигурация отклоняется как
feedback loop. Позже это правило расширяется идентификатором происхождения
блока для защиты от циклов через промежуточные виртуальные теги.

### 5. UI и persistence

Модель компонента хранит только конфигурацию:

- `BackendId`, endpoint и номера выходных каналов;
- частоту, размер блока, диапазон и safe value;
- вид источника (`wave` или `tag`) и его стабильную ссылку;
- имя/ID тега зеркала и флаг зеркалирования;
- underrun policy.

View показывает состояние сессии и счётчики, но не владеет backend и не
обрабатывает аппаратные callback. Ссылки сохраняются по стабильным ID; имена
используются для отображения и совместимого восстановления.

## Владение буферами и runtime-ограничения

- Все рабочие массивы выделяются при `Configure`.
- Provider пишет в caller-owned buffer; backend либо синхронно копирует его в
  собственный DMA/driver buffer, либо получает один из заранее выделенных
  блоков пула с явным возвратом владельцу.
- В callback запрещены `SetLength`, создание строк/объектов, доступ к LCL и
  публикация тяжёлых событий.
- Зеркало в тег не должно задерживать устройство. Сессия передаёт блок в
  ограниченную SPSC-очередь, а отдельный publisher добавляет его в registry.
- Счётчики: requested/submitted/output/mirrored frames, underruns, overruns,
  dropped mirror blocks и длительность заполнения блока.

## Первая атомарная итерация

1. Ввести Core-контракты, результат операции, конфигурацию и state machine.
2. Реализовать `null` backend с аппаратно-подобным запросом блоков.
3. Реализовать provider синуса и provider тега с точным совпадением частоты.
4. Реализовать необязательный mirror publisher и защиту от прямой петли.
5. Проверить lifecycle, порядок отсчётов, отсутствие runtime-аллокаций после
   Configure, underrun policy и оба маршрута зеркалирования.

PortAudio и PXIe backend развиваются независимыми итерациями, не меняя
контракты Core и UI. PXIe требует выбранной модели модуля и vendor SDK.
