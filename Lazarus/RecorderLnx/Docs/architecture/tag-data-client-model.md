# Клиентская модель данных тегов

## Разделение ответственности

- Движок Recorder наполняет кольцевой буфер каждого тега готовыми блоками.
- У каждого клиента тега свой монотонный счётчик прочитанного блока.
- Периодический вызов клиента (`DoGetData`) сначала сравнивает свой счётчик со
  счётчиком тега.
- Критическая секция кольца и копирование данных нужны только при расхождении
  счётчиков.
- Уведомление об обновлении не содержит массив данных. Оно лишь даёт клиенту
  повод вызвать `DoGetData`.

## Аналог в оригинальной модели

В `recorder/plgControlCyclogram` менеджер на событии обновления вызывает
`doGetData` готовых алгоритмов. Алгоритм через обёртку тега проверяет появление
новых данных и только после этого вызывает расчёт. При переходе из Stop
менеджер явно вызывает `doStart`, где клиент сбрасывает своё состояние.

Эту модель следует применять локально внутри конкретного потребителя, когда
профилирование показывает лишнее чтение кольца. Она не требует переделки
движка тегов или общего менеджера алгоритмов.

1. `TRecorderSignalBuffer.CurrentBlockCursor` возвращает номер следующего
   записанного блока без копирования данных.
2. `SnapshotNextBlock` копирует ровно один непрочитанный блок и передвигает
   курсор конкретного клиента.
3. Клиентская обёртка хранит курсор, накопительный непрерывный массив и правила
   его очистки либо переиспользования.
4. На `Stop -> Preview/Record` клиентская обёртка сбрасывает своё состояние.
5. Если клиенту достаточно последнего блока, он сравнивает собственный счётчик
   с `TRecorderTag.BlockCounter` перед вызовом `LastBlockSnapshot`.
6. Частые блоки измерений не передаются через EventBus и общую UI-очередь.

## Проверка

- При отсутствии новых блоков `DoGetData` не вызывает `SnapshotNextBlock`.
- Два клиента одного тега имеют независимые курсоры.
- Медленный клиент получает доступный непрочитанный хвост кольца; работа
  источника не зависит от скорости клиента.
- Переконфигурирование заново связывает клиентскую обёртку с входным тегом.
