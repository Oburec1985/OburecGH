# 2026-09-17 — дубли физических тегов блокируют импорт имён

## Симптом и доказательства

После импорта `recorder_tags_v02.ods` на KIP-3 каналы источника MIC-185 `192.168.9.156:4000` сохранили старые имена. Сравнение исходного ODS и экспорта `recorder_tags_v02exp.ods` показало 64 адреса `156-01`…`156-64` с одинаковыми строками `Источник` и `Адрес канала`, но разными именами. Например, исходная строка 518: `3Е1`, `156-01`; экспортная строка 60: `185-{156-1}`, `156-01`. У 134 других строк имена совпали после импорта.

Read-only аудит активного проекта KIP-3 выявил по два тега на каждый из 70 адресов `156-01`…`156-64`, `156-t1`…`156-t5`, `156-uts` при одном SourceId. Первая группа имеет ID 2166…2304, вторая 2594…2732. На обе группы уже ссылаются формы, `mic185.tagLinks` и SQL-настройки. Прямое удаление одной группы повредило бы ссылки.

## Причина

`TTagImportLookup.AddAddress` трактует повтор ключа `SourceId + Address` как неоднозначность и записывает `nil`; импорт считает все эти 64 строки отсутствующими. Различие пробелов, регистра, ведущих нулей и адреса источника проверено и отвергнуто: строки ODS и экспорта совпадают посимвольно.

## Исправление и проверка

При загрузке проекта более ранний физический тег с тем же источником и адресом не добавляется в реестр; остаётся последний тег с его метаданными и ID. Старый ID и имя временно разрешаются в оставленный тег, чтобы ссылки GUI могли перепривязаться. MIC-185 загрузчик `tagLinks` теперь выбирает канал по суффиксу и не создаёт дубль заново. Последующее штатное сохранение запишет только оставшийся тег и одну привязку канала. Исходный файл на KIP не изменён автоматически.

Принудительная Windows-сборка RecorderLnx 0.1.44 в отдельный EXE и Linux-сборка прошли; пакет 0.1.44 развёрнут на четырёх KIP. Штатный Windows EXE занят работающей программой и не заменён. Реальную загрузку и пересохранение проекта KIP-3 должен подтвердить оператор. Существующий `RecorderTagsTest --range-only` прошёл; полный старый `RecorderTagsTest` завершился на своей проверке EventBus (`expected 0, got 1`) и не служит подтверждением этой миграции.

## Риск

В `sql-db.ini` могут оставаться старые имена обеих групп до отдельной нормализации настроек SQL. Текущая миграция не переписывает этот файл автоматически.
