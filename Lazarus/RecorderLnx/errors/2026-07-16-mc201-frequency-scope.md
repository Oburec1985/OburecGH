# Частота MC-201 ошибочно применялась к каналу и всему MC-032

## Симптом

Изменение частоты одного тега меняло только его строку в UI, но при запуске
runtime брал частоту первого тега MC-032 и программировал ею все MC-201. В MERA
все сигналы записывались с одной частотой, хотя аппаратная область настройки —
один слот MC-201 (четыре канала).

## Причина

- `uTagSettingsDialog` присваивал `PollFrequencyHz` только редактируемому тегу.
- `TMainForm` сворачивал все частоты источника в одно значение.
- `TMc032Config.SampleRateHz`, `TRecorderAcquisitionBlock.SampleCount` и
  `SampleRateHz` были общими для всего контроллера.

## Исправление

- При изменении частоты MC-201 обновляются четыре тега того же SourceId и слота.
- В `TMc201SlotConfig` добавлена частота слота; перед программированием она
  собирается из тегов, а `SET_GRID/SET_FREQ` рассчитываются внутри цикла модулей.
- Блок захвата получил необязательные поканальные частоты, времена и количества
  отсчётов. MCbus извлекает и публикует за один период разное количество отсчётов
  для разных слотов.

## Проверка

Полная сборка `RecorderLnx.lpi` с `-B` завершена с exit code 0.

## Правило

Аппаратное свойство следует хранить и применять в области владения оборудования:
канал, модуль/слот или контроллер. UI, программирование, буферизация и метаданные
записи обязаны использовать одну и ту же область; проверка должна включать два
соседних модуля с разными значениями.

## Регрессия 25.09.2026: частота возвращалась после изменения

### Подтверждённые факты

- UI корректно менял `PollFrequencyHz` у четырёх тегов одного слота.
- `PrepareHardware` корректно переносил эти значения в slot config перед
  `SET_GRID/SET_FREQ`.
- После программирования `BuildChannelMap` заменял частоту каждого тега общей
  `fPollFrequencyHz` контроллера.
- Runtime factory начинал поиск максимальной частоты с 57600 Гц, поэтому любое
  снижение всех слотов ниже 57600 не влияло на aggregate.
- `BuildMcbus` создавал cached signals только из source default; при OK общего
  диалога stale signal повторно записывался в существующий тег.
- JSON round-trip тега исправен; ошибка находилась в поздней синхронизации двух
  представлений частоты.

### Исправление

- `TRecorderMcbusDevice.GetChannels` публикует `ChannelSampleRate` каждого
  программированного канала; `BuildChannelMap` использует это значение.
- Aggregate MCbus начинается с нуля, берёт максимум положительных частот тегов
  и лишь при их отсутствии использует source default или 57600 Гц.
- `BuildMcbus` сохраняет частоту уже существующего тега по `SourceId+Address`,
  поэтому повторное применение signal больше не откатывает значение слота.

### Проверка

Forced Windows-сборка `RecorderLnx.lpi` завершена с exit code 0. Стендовая
проверка смены 57600 -> 14400 Гц и двух слотов с разными частотами ещё нужна.

Дополнительно 25.09.2026 выполнена полная Linux-сборка в Astra VM:
`BUILD_EXIT=0`, ELF x86-64 создан, отсутствующих динамических библиотек нет.
