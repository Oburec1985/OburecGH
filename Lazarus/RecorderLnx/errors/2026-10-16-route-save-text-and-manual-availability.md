# Медленное сохранение точки АКА и доступность следующего ручного съёма

## Запрос и критерий
Секундная ручная порция показывается, Save занимает долго; после следующего
шага кнопка съёма неактивна. Пользователь уточнил: хранить бинарный MERA,
как оригинальный plgControlCyclogram, а не текстовые массивы.

## Факты и проверки
- FrfPointStore писал session.json через DOM + FormatJSON для каждого отсчёта.
- Remote MIC315 point1/2/3 session.json имеют по 12 049 205 байт.
- Локальный benchmark JSON: 1с 44.1к+54к,32769 bins: 2641 мс.
- StoreRoutePoint делал deep-copy всей RAM-истории, затем выкидывал все
  реализации кроме выбранной. Исправляется selected-only snapshot.
- Существующий ImpactMeraAdapter вопреки имени также пишет текстовые .dat;
  он не подходит для настоящего бинарного MERA.
- Новый формат должен оставаться читаемым стандартным uMeraFile, сохранять
  raw native timestamps/FRF/SPM/phase/coherence и идентичность каналов.
- Реальный UI smoke capture→save→next→same-model Configure→second capture
  проходит: сервис не пересоздаётся, кнопка доступна, вторая порция завершается.
- Remote LogWindows содержит global Preview→Stop в16:08:45,16:10:14,16:12:03.
  Точная причина отключения кнопки у пользователя пока не доказана; при Stop
  CanCapturePortion=False соответствует текущему контракту. Добавлено ясное
  пояснение в status, а не необоснованная смена жизненного цикла DAQ.

## Исправление и проверка
Новый MERA R8 codec проверен стандартным uMeraFile reader и точным roundtrip;
JSON2609мс против MERA15мс для той же секундной порции44.1/54к со спектрами.
Forced main/service/UI/codec сборки и Save→next→second manual capture PASS.
На MIC315 установлен проверенный EXE, SHA2563B041FA7F39E2B7C35E4191AB6531F68800E993A283896AB65EA44006F50AC4C,
62 настройки неизменны; исходные пользовательские сохранения не мигрировались.
Переключение шага само по себе не блокирует съём в воспроизводимом UI тесте.

## Схема хранения
Бинарный MERA point adapter, сохранение поколения в dedicated aka-подкаталоге
с rollback/backup без удаления legacyJSON и посторонних файлов. Старый JSON
остаётся read-only fallback. При пропавшем активном поколении с backup выдаётся
ошибка восстановления, а не молчаливая загрузка устаревшего JSON.
