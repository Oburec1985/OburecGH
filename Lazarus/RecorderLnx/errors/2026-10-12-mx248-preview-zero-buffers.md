# MX-248: нули в просмотре и падение моста после первого блока

## Подтверждённый сбой

На стенде `192.168.15.84`, MX-248 SN3253 (PCI 2:14), первый блок мог содержать
кодоподобные значения около -32000 и нулевой хвост. Второе чтение завершалось
ошибкой `mx248.bridge.read`. Windows WER показал `mx224v14.dll`, исключение
`c0000005`, смещение `0001acb0`. Успешные discovery/config/start и ненулевой
первый блок не являются приёмкой непрерывного сбора.

## Причины и исправления

1. Библиотека по умолчанию включает async. Её `OnInterruptScan` копирует FIFO
   в `HandlerData->buf`; прежний мост не задавал дескриптор и одновременно
   читал FIFO через Lock. Теперь используются штатные дескрипторы/callback и
   заранее выделенная очередь 32 полных блока на канал. Только готовность всех
   восьми каналов разрешает IPC-публикацию. Переполнение является ошибкой.
2. DevAPI Lock не проверяет полноту: после частичного GetData всё равно
   сообщает `m_TBlock`. Раннее чтение давало старый/нулевой хвост. Callback
   вызывается после CheckBuffer и обеспечивает целый аппаратный блок.
3. ELECTR без LoadTransformerKoefChan сохраняет исходные коды. Загружены
   коэффициенты всех восьми каналов. A/B проверка MTA/STA показала: MTA даёт
   rc=0 при загрузке, но блоки не публикуются; STA даёт непрерывный поток.
   Владелец bridge/COM обязан оставаться STA.
4. Обычный ConfigureDevice не применял сохранённый PXI Master/триггер.
   Теперь Configure включает ту же настройку, что live Apply, с программным
   триггером. Выбор off отключает внешний триггер, но не программный Start.
5. В PropertyStore оставался отдельный default 256, несмотря на общий 16384.
   При 512 кГц очередь 32*256 покрывает лишь 16 мс и переполняется между ticks.
   Default приведён к единой константе 16384. Скрытый размер блока не показывать
   оператору. После Apply обновляются буферы, частота и source units тегов.

для низких частот с большим блоком возможен промежуточный timeout. Он не должен

не заменяет проверку полного потока и публикации тегов.

## Повторный запуск после Stop — 2026-10-13 (подтверждено на стенде)

Первый прогон GUI (`--preview-seconds=4 --preview-cycles=2`) завершился после
144 блоков первого цикла таймаутом второго. Это наблюдение и прежняя гипотеза
про ожидание события устарели: повторная проверка на железе установила причину
в последовательности Programming/trigger.

После Stop DevAPI сбрасывает состояние PROGRAMMED. При повторном запуске мост
явно вызывает Programming, и обработчик MX-224 `OnProgramming` заново
конфигурирует триггер как `TRIG_TASK_SYNC`. Одного вызова Programming
недостаточно: перед повторным CreateTrigger/Start/start-pulse мост обязан
выполнить PulseTrigger (SYNC). Без этого обязательного SYNC аппаратный поток
после первого цикла не возобновлялся. После добавления PulseTrigger сразу за
FProgramming повторный запуск отработал.

Это подтверждается оригинальным исходным кодом:

- `D:\works\windev-v3.9\mx224v14\mx224v14.cpp:881-1016` —
  фактическая для MX-248 реализация `CMX224v14::OnProgramming` конфигурирует
  `CMD_CONFIG_TRIGGER` с `Args[3] = TRIG_TASK_SYNC` (строки 1010-1016).
- `D:\works\windev-v3.9\Mx224_rce\224\Mx224.cpp:730-837` — отдельная
  generic-реализация `Mx224::OnProgramming` делает то же самое; это
  дополнительное сравнение, а не первичный источник для MX-248.
- `D:\works\windev-v3.9\devapi\Device.cpp:313-323` — `StartScanMain` вызывает
  `Programming`, если состояние PROGRAMMED отсутствует.
- `D:\works\windev-v3.9\devapi\Device.cpp:335-346` — после успешного
  `OnStopScanMain` метод `StopScanMain` очищает PROGRAMMED.

изолированной замены bridge. Затем последний локальный bridge был скопирован
