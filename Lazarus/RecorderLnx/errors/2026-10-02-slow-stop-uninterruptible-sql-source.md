# Долгий переход Preview -> Stop при недоступном SQL-источнике

## Симптом

В проекте `test185_149` переход из Preview в Stop надолго блокирует интерфейс.

## Подтвержденная причина

`TMainForm.StopDataSources` синхронно вызывает
`TRecorderDataSourceManager.StopAll` в GUI-потоке. `StopAll` последовательно
вызывает `WaitFor` каждого потока источника без таймаута.

Для `TRecorderSqlDataSource` базовый `RequestStop` только устанавливает флаг.
Рабочий поток проверяет его лишь после возврата из `DoTick`, а `DoTick`
синхронно выполняет `ReadLatestSignalValues`. Соединение закрывается в
`TRecorderSqlDataSource.Stop`, но этот метод выполняется самим worker-потоком
только после выхода из блокирующего SQL-вызова. Поэтому остановка не может
прервать зависшее сетевое подключение.

В текущей конфигурации SQL-источник обращается к Firebird
`192.168.9.66:3050`. У запущенного `RecorderLnx.exe` соединение находилось в
`SYN_SENT`; отдельная контрольная TCP-попытка не завершилась за 3000 мс.
Для сравнения, настроенный OPC UA `192.168.15.130:4840` подключился за 2 мс.

## Отвергнутые гипотезы

- Закрытие Mera-записи в Preview не выполняет тяжелой работы, если файл не открыт.
- OPC UA допускает задержку до своих сетевых таймаутов, но во время проверки
  его endpoint доступен; активный незавершенный вызов обнаружен у Firebird.

## Правило для исправления

Остановка источника не должна зависеть от возврата из неограниченного сетевого
вызова. `RequestStop` обязан разбудить/прервать I/O либо I/O должно иметь
ограниченный короткий таймаут. GUI-поток не должен делать безлимитный `WaitFor`;
в журнале остановки нужно измерять время ожидания каждого SourceId.

## Проверка диагностики

- изучена фактическая конфигурация `C:\Mera Files\RecorderLnx\config\projects\test185_149`;
- проверено TCP-состояние запущенного процесса;
- выполнены контрольные подключения к SQL и OPC UA endpoint;
- прослежена цепочка `btnStopClick -> StateMachine.Stop -> StopDataSources -> StopAll`.

## Исправление

`TRecorderSqlDataSource.PrepareHardware` теперь делает короткий TCP-preflight
при загрузке и переконфигурации. Недоступный SQL помечается offline, поэтому
`StartAll` не создаёт для него worker-поток и Play/Stop к нему не обращаются.

Во время работы `DoTick` повторяет preflight непосредственно перед SQL-чтением.
Если сервер выключился, источник помечается offline, выставляет `RequestStop`
из собственного worker-потока и завершается до общего Stop.

`Stop` не закрывает repository у offline-источника: штатный `Close` сначала
завершает Firebird-транзакцию и тем самым снова может уйти в сетевой таймаут.
Освобождение такого repository остаётся вне перехода Play -> Stop — при
замене/удалении runtime-конфигурации.

## Проверка исправления

Forced Windows-сборка RecorderLnx выполнена с отдельными каталогом units и
выходным EXE (`-FU/-FE/-o`), exit code 0. Штатный каталог сборки удерживался
запущенным RecorderLnx, поэтому работающий процесс не останавливался.
