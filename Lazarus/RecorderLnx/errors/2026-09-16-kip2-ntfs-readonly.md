# KIP-2: NTFS в /mnt/DATA доступен только для чтения

## Симптом

Пользователь не может создать `/mnt/DATA/usml` на KIP-2.

## Подтверждённые факты

- KIP-2 — `192.168.9.45`. `/mnt/DATA` существует, `/mnt/DATA/usml` отсутствует.
- `/dev/sda1` (NTFS, UUID `30BA7E8BBA7E4D7A`) смонтирован в `/mnt/DATA` как `fuseblk ro`, хотя управляемая запись `/etc/fstab` задаёт обычный режим без `ro`.
- Обычный `mkdir /mnt/DATA/usml` возвращает `Файловая система доступна только для чтения`; каталог не создан.
- Привилегированная проверка `ntfs-3g.probe --readwrite /dev/sda1` сообщает: `The disk contains an unclean file system (0, 0). Metadata kept in Windows cache, refused to mount.`

## Вывод

Причина не в правах пользователя и не в имени папки: драйвер отказал в записи на некорректно завершённый NTFS-том. Принудительный RW/очистка кэша без оценки данных не выполнялись. Для безопасного восстановления требуется завершить обслуживание тома в Windows (проверка диска и полное завершение работы), затем заново проверить RW-монтирование и только после этого создать `usml`.

## Попытка восстановления после разрешения пользователя

Пользователь разрешил агрессивное восстановление: ценных данных на томе нет. Повторно сверены `/dev/sda1`, UUID и отсутствие дочерних монтирований. Попытка штатного `umount /mnt/DATA` перед `ntfsfix` завершилась ошибкой «цель занята»; `ntfsfix` **не запускался**. `fuser -vm /mnt/DATA` показал Double Commander пользователя (`PID 44712`, текущий каталог внутри тома). Принудительное отключение или завершение приложения не выполнялось, чтобы не оборвать его операции. После `systemctl stop mnt-DATA.automount` попытка восстановить automount unit не прошла при оставшемся активном монтировании; сам `/dev/sda1` остаётся смонтирован `ro` в `/mnt/DATA`.

Следующий шаг: пользователь закрывает Double Commander на KIP-2; затем повторить обычное размонтирование, `ntfsfix`, вернуть автомонтирование, проверить `rw` и создать `/mnt/DATA/usml`.

## Восстановление

Пользователь разрешил самостоятельно закрыть мешающее приложение. К моменту повторной проверки Double Commander уже завершился; команда завершения не затронула процесс. `fuser` больше не показал пользовательских держателей. После повторной сверки UUID раздел штатно размонтирован. `ntfsfix /dev/sda1` успешно обработал `$MFT`/`$MFTMirr`, очистил журнал `$LogFile` и завершился без ошибки. Системный automount запущен снова. После срабатывания automount `/dev/sda1` смонтирован в `/mnt/DATA` как `fuseblk rw`, точка доступна `user` на запись. Пользователь `user` создал `/mnt/DATA/usml` (`drwxrwxr-x user user`), каталог находится на `/dev/sda1`. Файлы пользователя вручную не удалялись; журнал NTFS сброшен штатной командой `ntfsfix`.

Корневая причина — незавершённое состояние NTFS, из-за которого драйвер перешёл в `ro` вопреки параметрам `/etc/fstab`. Различать запрошенные параметры и фактический mount. Проверка после перезагрузки пока не выполнялась; запись в `/etc/fstab` сохранена, automount активен.

## Профилактика в LinuxSetupManager

В обычный сценарий «Подключить» добавлена проверка фактического `ro` после NTFS-монтирования: она возвращает предложение восстановления, а GUI объясняет риск и спрашивает согласие. Отдельная кнопка «Исправить NTFS» оставлена для ручного вызова. Backend принимает только точное устройство/UUID, управляемую запись `/etc/fstab`, отсутствие чужих/bind-монтирований и явный флаг риска; выполняет обычное размонтирование, `ntfsfix`, восстановление automount и проверку `rw`. Без согласия ремонт не запускается. Русские CLI-сообщения передаются в UTF-8 и под `LC_ALL=C`.

Принудительные Windows/Linux-сборки GUI/CLI успешны. DEB 0.1.39 установлен на KIP-1…KIP-4 (4/4). На KIP-2 безопасный вызов CLI без флага подтвердил отказ и UTF-8-байты; реальный новый отказ `ro` в GUI не создавался искусственно на исправном диске.
