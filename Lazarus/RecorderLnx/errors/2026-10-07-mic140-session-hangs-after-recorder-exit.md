# MIC-140: сессия зависает после выхода из RecorderLnx

## Симптом

Если завершить RecorderLnx во время работающего MIC-140, не нажав предварительно
Stop, прибор может перестать отвечать на ping и новое TCP-подключение. Для
восстановления требуется выключение питания.

## Подтверждённые факты

- `TRecorderDataSourceManager.StopAll` перед уничтожением источников вызывает
  `RequestStop` и ждёт завершения worker.
- Worker в любом обычном выходе вызывает `TRecorderMic140DataSource.Stop`.
- `TRecorderMic140Device.Stop` останавливает поток чтения и отправляет
  `StopScan`, если устройство запущено либо scan отмечен активным.
- После этого `TMic140v2Tcp.Disconnect` ранее сразу освобождал `TSocketStream`,
  не выполняя двунаправленный TCP shutdown.
- В прежнем аналогичном дефекте MIC-185 отсутствие `shutdown(SHUT_RDWR)`
  оставляло firmware-сессию занятой после закрытия клиента.
- Старый лог `cach/backup_mic140_stop_20260623/LogWindows.before_changes.log`
  содержит реальный `Legacy scan stop failed: MIC-140 legacy command timeout`;
  значит освобождение транспорта обязано работать и после неуспешного StopScan.

## Исправление

В `TMic140v2Tcp.Disconnect` перед `FreeAndNil(fSocket)` добавлен
`fpShutdown(fSocket.Handle, SHUT_RDWR)`. Ошибка shutdown подавляется только на
стадии cleanup, чтобы не скрывать исходную протокольную ошибку. Порядок команд,
таймауты, программирование и поток сбора не менялись.

## Проверка

- Forced-сборка в отдельный `RecorderLnx_shutdown_verify.exe` — exit code 0.
- Независимый read-only аудит подтвердил порядок
  `RequestStop -> worker Stop -> StopScan -> Disconnect -> shutdown -> close`
  и отсутствие параллельного чтения в момент закрытия транспорта.
- Windows выбрал для `192.168.14.42` интерфейс `Ethernet 2` и адрес
  `192.168.3.65`, но ICMP завершился `General failure` при одновременном
  конкурирующем маршруте VPN. Короткий TCP-probe не выполнялся: MIC-140
  одноклиентский, и такой probe сам способен занять сессию.

## Оставшаяся проверка

На чистом маршруте `Ethernet 2`: запустить Preview, закрыть RecorderLnx без
ручного Stop, убедиться в ответе ping и повторном штатном подключении к порту
4000 без сброса питания. До этого аппаратный эффект считается неподтверждённым.

Отдельный соседний риск: после timeout `StopScan` при обычном `Stop -> Preview`
сессия остаётся открытой и помечается программно готовой. Не объединять его с
текущим исправлением выхода; проверить отдельно на стенде и только затем решать,
нужен ли forced disconnect после неуспешного StopScan.

## 2026-10-08 — удалённое выключение через rcPanel

Подтверждена отдельная причина обхода штатного cleanup: HostAgent по запросу
rcPanel сразу запускал системный poweroff и предварительно не завершал
RecorderLnx. Команда координатора `recording.stop` для этой задачи недостаточна:
она прекращает сбор, но намеренно сохраняет рабочую сессию источника.

Итоговая последовательность: локальный файл-запрос -> LCL timer -> явное
освобождение MainForm -> `FormDestroy -> StopAll -> StopScan -> Disconnect` ->
ожидание выхода -> poweroff. HostAgent ждёт до 15 секунд и при таймауте отменяет
выключение. `SIGTERM` оставлен резервным источником того же запроса.

Forced Win64- и Linux-сборки HostAgent и RecorderLnx успешны. На Astra VM
RecorderLnx завершился за 0,2 с после создания файла-запроса. DEB 0.1.149 собран
и установлен на доступные KIP-3 и сервер БД; аппаратная проверка повторного входа
в MIC-140 после команды rcPanel остаётся отдельным финальным тестом.
