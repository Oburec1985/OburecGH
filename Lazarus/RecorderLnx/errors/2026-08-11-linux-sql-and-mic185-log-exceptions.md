# Linux: исключения SQL и MIC-185 при запуске

## Симптом

При запуске Linux-сборки отладчик останавливался на отсутствии SQL-сервера, затем
на файловой операции `AppendFileLine` журнала MIC-185.

## Причина

- Включённый SQL runtime сразу вызывал `TIBConnection`; недоступность Firebird
  определялась только исключением внутри SQL-библиотеки.
- MIC-185 и `SharedLogger` независимо дописывали один `LogLinux.log`.

## Исправление

- Перед созданием SQL repository выполняется неблокирующая TCP-проверка без
  привязки к аппаратному сетевому интерфейсу. Отказ записывается в системный
  журнал, SQL runtime останавливается, приложение продолжает работу.
- Файловая запись MIC-185 переведена с `TextFile` на операции с проверяемым кодом
  возврата. Если путь совпадает с общим журналом, файл пишет только `SharedLogger`.

## Проверка

Windows и Linux clean build завершились с кодом 0. Короткий Linux-запуск без
Firebird завершился штатно с кодом 0; в журнале присутствуют `SQL server not found`,
`SQL database unavailable` и последующая строка `RecorderLnx started`.

## Дополнение: Windows-путь в общей конфигурации

В общей `sql-db.ini` был сохранён `RootDirectory=C:\Mera Files\SQLdb`. На Linux
он ошибочно превращался в каталог `.../lib/x86_64-linux/C:/Mera Files/SQLdb`.
Теперь путь другой ОС распознаётся до `ExpandFileName`: Linux использует
`<Mera Files>/SQLdb`, а Windows сохраняет исходное поведение. То же правило
применяется, если абсолютный путь записан в имени файла БД.

## Повтор старого сообщения после исправления

Lazarus продолжал держать старый отладочный процесс PID 19337, запущенный до
пересборки. Строка исключения соответствовала старому коду, хотя новый ELF уже
лежал на диске. Обычный `SIGTERM` процесс не завершил; после остановки отладочной
сессии/принудительного завершения и clean build свежий запуск завершился с кодом
0 без исключения SQL-каталога.

Правило проверки: после замены исполняемого файла убедиться, что отладчик не
удерживает старый процесс (`pgrep -a RecorderLnx`), и только затем оценивать
повторяемость исправленной ошибки.

## Окончательная причина повторного пути

После загрузки проекта `TRecorderRunControlSettings.MeraFilesPath` повторно
передавал Windows-путь в `SetRecorderMeraFilesPath`. Поэтому локальная защита
SQL была недостаточной: её fallback снова получал уже испорченный глобальный
корень. Исправление перенесено в `uRecorderMeraPaths`: и загрузка
`RecorderLnx.paths.ini`, и публичный setter отвергают путь другой ОС и выбирают
локальный системный корень.

Контрольный свежий запуск после clean build завершился с кодом 0. Для Linux
корень равен `/home/user/Mera Files`; исключения SQL-каталога нет.
