# SQL-тренд: исторические события исчезают при live reload

## Симптом

Coordinator показывает несколько SQL-событий за интервал, но RecorderLnx
после фонового обновления оставляет только новое событие. Исчезновение заметно
после закрытия карточки, хотя крестик ничего не удаляет.

## Подтверждённая причина

В режиме `sttmFixedFromToCurrentUtc` первый запрос читает весь интервал, а
последующие запросы — только короткое перекрытие примерно 30 секунд. В
`AcceptLoad` точки объединялись через `MergeLivePoints`, но `fEvents` каждый
раз целиком заменялся событиями короткого запроса. Поэтому в памяти оставалось
только самое свежее событие; строки SQL не удалялись.

## Исправление

- Результаты live-запросов событий объединяются с уже загруженной историей по
  `EventId`, обновляя состояние существующего события и добавляя новые.
- После сохранения или удаления в карточке принудительно выполняется полный
  запрос интервала, чтобы корректно отразить изменения вне короткого окна.
- Закрытие карточки крестиком по-прежнему возвращает `medrUnchanged` и не
  запускает ни удаление, ни принудительную перезагрузку.
- `ResetZoomClick` теперь включает время начала и окончания событий в полный
  X-диапазон. Раньше сброс масштаба ориентировался только на точки сигналов и
  мог оставить новые события целиком за видимой областью.

## Проверка

- В рабочей Firebird подтверждено 11 физических событий; полный запрос за день
  возвращает 11, а прежний append-запрос последних 30 секунд — только 2.
- При повторной проверке после пользовательских удалений в Firebird осталось
  8 событий/9 пакетов; production-запрос широкого интервала возвращает все 8.
- Проверена цепочка `StartLoad` → `RequestLoad` →
  `ListMeraRecordingEvents` → `AcceptLoad`.
- Полная сборка `RecorderLnx.lpi` с `-B` завершилась с кодом 0.
- `git diff --check` не выявил ошибок.

## Дополнение: Linux, локальная дата и UTC

При повторной проверке обнаружена независимая межплатформенная ошибка в
настройке интервала. `FromUtc/ToUtc` хранятся и передаются в repository как
UTC, но календарные controls показывали эти значения напрямую и возвращали
локальную полночь без `LocalTimeToUniversal`. В часовом поясе, отличном от UTC,
запрос мог охватывать не тот календарный день; тогда событие не загружалось и
`ResetZoom` физически не мог включить его в шкалу.

Граница исправлена: UTC переводится в local только для показа, выбранные
локальные даты переводятся обратно в UTC перед SQL-запросом. UTC-default при
загрузке старого GUI config также больше не строится из `Now` напрямую.
Разбор ISO-8601 времени команд Coordinator переведён в режим возврата UTC.

Отдельный риск остаётся у источника события: Coordinator принимает
`started_utc` RecorderLnx как каноническое время. Если системные часы Linux
сильно сбиты, новая строка корректно запишется, но окажется вне ожидаемого
интервала. Исправление должно быть на входе `TCoordinatorModel.AddRecordingEvent`:
сравнить client start с UTC-временем приёма, записать skew в журнал и при
превышении допустимого порога использовать время приёма для grouping/store.

Проверка дополнения: forced build `RecorderLnx.lpi` — exit code 0.

## Дополнение: подтверждение SQL-записи на стенде

Свежий журнал Linux rcPanel показал успешные `recording.started` и
`recording.completed` для двух Recorder, а также `SQL event store OK`, но не
позволял отличить реальную фиксацию строки от отсутствия исключения во время
последовательности запросов. Добавлено обязательное read-after-write по
`event_id`. Новый журнал выводит каноническое UTC-время, число связанных
замеров, backend, сервер и файл БД. Вкладка событий обновляется сразу после
подтверждённой записи, если она открыта.

Firebird на втором ПК RecorderLnx не участвует в создании события: событие
пишет rcPanel через собственное подключение. Но отсутствие клиентской
библиотеки Firebird на этом ПК независимо делает SQL-тренд неработоспособным.

Проверка: свежий repository после полного lifecycle повторно прочитал событие
и один связанный замер; `CoordinatorFirebirdLifecycleTest` — passed,
forced-сборка RecorderCoordinator Win64 — OK.

По времени на фотографии найдена причина пустой вкладки самого rcPanel:
`dtpEventsTo` один раз получал `Now` при запуске (23:19), а событие пришло позже
(23:20). Верхняя граница не обновлялась, поэтому корректно записанная строка
отсекалась `r.started_at_utc<=:to`. Значение «До» теперь следует за текущим
временем, пока оператор явно не изменит его для исторического интервала.
