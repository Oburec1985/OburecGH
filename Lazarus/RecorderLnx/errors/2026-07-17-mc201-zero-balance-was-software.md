# MC-201: балансировка ошибочно выполнялась программным вычитанием

## Симптом

Кнопка балансировки в диалоге тега брала среднее последнего общего кадра и
записывала его в `fSoftBalance`. Балансировочный ЦАП MC-201 не программировался,
служебный сбор не запускался, результат не сохранялся по диапазону.

## Эталон оригинального Recorder

`mtc/Mc201.cpp`:

- `ModuleMC201::ZBalance` временно работает в кодах и задаёт размер одной оценки
  как `max(3, Fs * 0.06)`;
- `ChanCalibrFullSingleScan` отправляет `SEND_BALANCE_CC = 53` с аргументами
  `channel, code_lo, code_hi`;
- сначала проверяются `lo=255, hi=0/255`, затем двоичным поиском уточняются
  младший и старший байты biased-кода ЦАП;
- после каждого изменения ЦАП выполняется новый сбор и вычисляется среднее;
- код хранится отдельно для канала, диапазона и восстанавливается при ошибке.

## Исправление

- В MCbus добавлена аппаратная команда `SEND_BALANCE_CC`.
- Реализован оригинальный двухступенчатый поиск по сериям `Fs * 0.06`.
- Балансировка и обычный `ReadBlock` сериализованы одним I/O lock.
- Из Stop источник временно запускает скан; из Preview использует текущий скан.
- Перед каждой оценкой очищаются старые данные; при ошибке возвращается старый DAC.
- Коды `d<channel>r<range>` сохраняются в конфигурации слота, переживают
  редактирование диалога MC-201 и повторно отправляются при программировании.
- Программное вычитание `fSoftBalance` для MC-201 удалено.

## Проверка

Полная сборка `RecorderLnx.lpi -B` завершена с exit code 0. Аппаратный эффект
требует контрольного запуска кнопки на реальном MC-032/MC-201.

### Первый запуск на стенде

Получено `balance sample timeout: 2048/3456`. Это подтвердило, что после
`SEND_BALANCE_CC` MC-032 отдаёт законченную транспортную порцию в 2048 свежих
отсчётов, тогда как буквальный расчёт `57600 * 0,06` требовал 3456 и ошибочно
считал полученные данные недостаточными. Размер одной оценки ограничен
`min(Fs * 0,06, 2048)`: на низких частотах сохраняется исходная длительность,
на высоких используется полная доступная порция (2048 отсчётов достаточно для
устойчивого среднего и не добавляет секундный таймаут на каждом шаге поиска).

Также общий диспетчер показывал второе окно «не удалось выполнить» после уже
показанного конкретного сообщения устройства. Теперь общий текст выводится только
когда ни один обработчик не сообщил причину.

## Правило

Если оригинальный драйвер определяет балансировку как аппаратную команду с
замкнутым циклом «установить → измерить → уточнить», нельзя заменять её коррекцией
данных после АЦП. Проверка обязана подтверждать передачу аппаратной команды,
повторные независимые измерения, восстановление при ошибке и сохранение результата
в той же размерности конфигурации (канал/диапазон).

Для потокового транспорта размер служебной оценки нельзя считать только как
`Fs * duration`: нужно учитывать максимальную завершённую порцию протокола. Серия
с достаточным числом свежих отсчётов является валидной; ожидание недостижимого
размера превращает каждый шаг регулирования в ложный таймаут.

### Зависание интерфейса при повторном запуске

Аппаратный поиск выполняет много последовательных шагов «установить ЦАП → собрать
свежую выборку». Вызов всей операции непосредственно из обработчика кнопки
блокировал главный поток LCL: окно не перерисовывалось и выглядело зависшим, хотя
драйвер продолжал обмен.

Балансировка перенесена в отдельный рабочий поток. На время операции показывается
модальное окно состояния без возможности запустить второй параллельный обмен.
Результат и сообщения передаются в GUI только после завершения worker. LCL-owner
в драйвер из worker не передаётся, поэтому фоновой код не обращается к `Screen`,
курсору и другим GUI-объектам.

Повторная проверка показала, что перенос в worker только скрывал первопричину:
драйвер продолжал выполнять до нескольких десятков циклов «ЦАП → выборка».
Алгоритм заменён на однопроходный: одна секундная выборка, среднее в кодах АЦП,
пересчёт смещения в код балансировочного ЦАП по номинальному коэффициенту
`Uref/Range` (`Uref=2,5 В`) и одна команда `SEND_BALANCE_CC`. Среднее считается
потоково по пакетам, полный секундный массив дополнительно не выделяется.

После первого однопроходного запуска среднее отображалось, но при следующем
программировании снова наблюдались прежние ~500 кодов. В конфигурации старого
проекта отсутствовали строки `CFG slot=...`, а `StoreBalanceDac` умел только
редактировать существующую строку и молча завершался без сохранения. Теперь при
отсутствии строки создаётся полная строка настроек слота и в неё записывается
`d<channel>r<range>`. В лог выводятся исходное среднее, диапазон, старый/новый
код и подтверждение успешной команды ЦАП.
