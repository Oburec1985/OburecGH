# Виброиндикатор не получал спектральные кадры после настройки

## Проявление

После добавления или настройки компонента виброоценки источник и параметры
спектра сохранялись правильно, но значение оставалось пустым.

## Причина

Диалог перестраивал `TRecorderSpectrumRuntimeManager` напрямую. Runtime уже был
подготовлен и содержал входной тег, однако сохранённый флаг
`TRecorderSpectrumAlgorithm.Ready` оставался `False`. Менеджер алгоритмов
проверял этот устаревший флаг и отбрасывал блоки данных до передачи в runtime.

## Исправление

`Ready` переведён на виртуальный getter. Для спектрального алгоритма готовность
определяется фактическим `Runtime.IsPrepared`. Все существующие проверки
lifecycle, одиночных значений и блоков теперь используют одно актуальное
состояние.

Индикатор дополнительно показывает диагностическое состояние: тег не найден,
нет входа спектра, spectrum runtime недоступен либо ожидается первый кадр.

## Проверка

Полная сборка `RecorderLnx.lpi` командой `lazbuild -B` завершилась успешно.

## Дополнение: дефис вместо оценки и выбор тега в Linux

На GTK исходный тег выбирался через нативный выпадающий `TComboBox`, который
разворачивал весь реестр, включая скалярные результаты спектра. Добавлен
отдельный кроссплатформенный picker фиксированного размера: поиск по подстроке
имени, адреса и описания, список с прокруткой, только `IsVector=True` и `Fs>0`.

Расчёт теперь определяет физическую единицу также по `UnitOut` назначенной
датчиковой/канальной ГХ. Раньше тег с электрической входной единицей мог иметь
вибрационную ГХ, но оценщик видел только `Tag.UnitName` и отклонял расчёт.
При отсутствии подходящей ГХ вместо безымянного дефиса показывается точная
причина. Имя индикатора дополнено выбранной полосой.

Для Mera-файлов с положительной частотой исправлено восстановление `IsVector`,
чтобы старое ошибочно сохранённое `isVector=false` не скрывало блочный канал.
