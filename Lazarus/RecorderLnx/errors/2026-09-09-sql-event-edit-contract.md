# Контракт редактирования SQL-события MERA

## Исходная проблема

Событие записи не имело независимых имени и описания. Подпись вычислялась как
`MAX(display_name)` пакетов, путями нельзя было управлять, а безопасной операции
удаления события не существовало.

## Причина

Схема v4 моделировала пакетные записи и файловые location, но карточка события
была только технической группировкой. UI Coordinator показывал in-memory
события текущего процесса вместо истории из SQL.

## Исправление

- Schema v5 добавляет `events.display_name` и `events.description` и мигрирует
  существующие события.
- Repository читает канонические свойства события, проверяет принадлежность
  location при изменении пути и удаляет событие одной транзакцией.
- Общий диалог показывает время, имя, описание, хосты, пакеты и пути; позволяет
  сохранить изменения или удалить только SQL-записи.
- Coordinator загружает события SQL за выбранный интервал и открывает тот же
  редактор, что и SQL-тренд.

## Проверка

Forced-сборки RecorderLnx, RecorderCoordinator и RecorderSqlDbMeraEventsTest
завершились с exit code 0. Запуск SQLite-теста не выполнен: в окружении нет
динамической библиотеки `sqlite3.dll`.

## Остаточный риск

Нужна стендовая проверка миграции существующей Firebird-БД и ручная проверка
открытия/правки/удаления из обеих программ.

## Исправление миграции Firebird после стендовой проверки

При первом открытии SQL-тренда Firebird вернул `-206 Column unknown
DISPLAY_NAME`. Причиной оказался `UPDATE`, подготовленный в той же транзакции,
где перед ним выполнялись `ALTER TABLE ADD DISPLAY_NAME/DESCRIPTION`: новые
метаданные Firebird ещё не были опубликованы. Между DDL и backfill добавлен
`CommitAndRestart`. Частично выполненная попытка восстанавливается безопасно:
`AddColumnIfMissing` пропускает уже созданные столбцы, затем миграция переносит
данные и только после этого записывает schema version 5.

## Потеря lifecycle после ошибки SQL

Live-проверка показала: после 15:00 новые записи отсутствовали во всех четырёх
таблицах событий; маркер 13:00 оказался старой диагностической строкой. Во
время неуспешной миграции Coordinator отвечал на lifecycle HTTP 503. Клиент
сохранял FIFO только в памяти, поэтому перезапуск Recorder удалял ожидающие
`started/completed`.

Очередь lifecycle теперь хранится рядом с клиентским INI в
`coordinator-client.events.json`, атомарно обновляется и восстанавливается при
старте. Событие удаляется из неё только после HTTP 2xx. Ответ 503 вместе с
`persistence_error` сохраняется в диагностике.

Время также исправлено: уже UTC-значение сериализуется с флагом UTC и больше не
сдвигается повторно на часовой пояс.

Coordinator пишет потокобезопасный `RecorderCoordinator.log` рядом с EXE:
приём lifecycle, grouping ID, начало/успех/ошибку SQL и HTTP-результат.
