# OPC UA Boolean отображался как 0.5, Lua засорял журнал — 2026-10-28

## Симптомы и проверенные факты

- В `C:\Mera Files\RecorderLnx\LogWindows.log` строки `Tags_[1]` шли почти
  каждые 200 мс из UI-потока.
- Источник найден в активном проекте
  `config/projects/test185_149/LuaCalc/p1.lua`: `lua_main` вызывал
  `logMessage(name_tag)` для `Tags_[1]` на каждом цикле. Это не ошибка OPC UA.
- `blinkerplc` в сохранённой конфигурации имеет NodeId
  `ns=4;s=|var|PLC210 OPC-UA.Application.GVL.blinkerplc` и DataType `i=1`
  (Boolean). Для него были включены `MO` и `portionLength=2`.
- `MO` для двух Boolean-отсчётов False/True равно 0.5. OPC Read-декодер
  Boolean корректно переводит его в 0 или 1; дробь возникает позже в оценке.
- OPC tag `PollFrequencyHz` раньше вычислялся только из 100-мс интервала
  источника, без учёта `UpdateTimeMs` общего runner.

## Исправления

- Удалён повторяющийся `logMessage(name_tag)` из активного Lua-скрипта;
  `setValue` и его поведение оставлены без изменений.
- Для OPC UA Boolean-тегов default estimate переключён на `tekLastValue`,
  MO отключён, portion length равен 1.
- Плановая частота для OPC UA tag metadata теперь ограничена большим из
  OPC-интервала и периода runner. В списке каналов она обозначается как
  `до N Гц`, то есть верхняя граница расписания, а не гарантированная частота.

## Ограничения

Фактическая частота может быть ниже верхней границы, если обработка сетевого
Read дольше интервала runner. Временные метки сервера могут быть нерегулярными;
равномерную шкалу нельзя гарантировать без ресэмплинга/интерполяции. Live UI
проверка обновлённого exe не выполнялась, чтобы не запускать второй OPC-клиент.
