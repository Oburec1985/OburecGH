# Задержка перехода в Preview и выделение памяти MCbus

## Симптом

Переход `Stop → Preview` занимал заметное время. Требование: крупные рабочие
буферы выделяются при загрузке проекта или переконфигурировании, а Start/Stop
только переключают состояние сбора.

## Подтверждённые причины

1. `TRecorderDataSourceManager.StartAll` вызывал `PrepareHardware` синхронно из
   UI-потока. Для MCbus это означало TCP connect, поиск слотов и полный
   `ProgramDevice` непосредственно перед Preview.
2. `TRecorderMcbusDataSource.Stop` всегда делал `Disconnect`; поэтому каждый
   следующий Preview повторял connect/program.
3. `TRecorderMcbusDevice.ClearPending` вызывал `SetLength` из Program, Start,
   Stop и Disconnect.
4. `AcceptPacket` мог увеличивать канал во время потока, `ReadBlock` выделял
   матрицу 16 × 11 520 при каждом блоке, `PublishBlock` — новый массив времени.
5. В `ProgramMc201Scan` есть обязательные сетевые команды и пауза 350 мс. Они
   относятся к переконфигурированию, а не к запуску уже подготовленного scan.

## Исправление

- MCbus создаётся и подготавливается сразу после загрузки/изменения конфигурации.
- `PrepareHardware` идемпотентен для состояния `rdsProgrammed`.
- Успешный Stop сохраняет TCP-сессию и запрограммированное устройство;
  Disconnect выполняется при уничтожении источника во время переконфигурации.
- Накопительные массивы, выходной блок и времена выделяются один раз при
  подготовке. Start/Stop сбрасывают только счётчики.
- Рост накопительного массива в Preview запрещён и диагностируется как ошибка
  расчёта ёмкости вместо скрытого `SetLength`.
- `ReadBlock` возвращает ссылку на повторно используемую матрицу устройства.
- Если прибор недоступен при загрузке, проект всё равно открывается; подготовка
  откладывается до Preview с записью причины в лог.

## Проверка

- `RecorderLnx.lpi`: полная сборка, exit code 0.
- Headless `--preview-seconds=3` без MCbus: переход в Preview после таймера
  занимает несколько миллисекунд (`Data sources started` → `State changed`).
- Production smoke пересобран успешно, но стенд `192.169.12.87:4000` во время
  проверки был недоступен: TCP connect timeout. Повторную аппаратную проверку
  нужно выполнить при доступном контроллере.

## Оставшиеся ограниченные операции

Менеджер создаёт и освобождает небольшие объекты thread-runner при Start/Stop.
Это не массивы данных и не причина прежней сетевой задержки. Низкоуровневый
MDP-клиент также использует динамические массивы для входных сетевых кадров;
их отдельная замена кольцевым буфером относится к оптимизации постоянного
потока, а не перехода состояния.
## Регрессия: после оптимизации Preview не получает данные

- `rstInit` оказался только начальным значением `LastTransition`, нотификации `Init` в EventBus не существовало.
- `rceConfigurationPrepared` публиковался до `EnsureDemoDataSources`, поэтому на момент события MCbus-источник ещё не существовал.
- Исправлен lifecycle: добавлен `rceInitialized`; после полной загрузки сначала создаются и привязываются источники, затем `PrepareHardwareAll` подключает и программирует устройства, после чего публикуется `Initialized`.
- Тот же порядок применяется после загрузки другой конфигурации и изменения тегов.
- Реальный лог показал отсутствие `MC-032/MC-201 source configured`: фабрика
  применяла `RecorderTagSourceIsVisible` до заполнения `ActiveSourceIds`.
  Возникал цикл «источник не активен → тег невидим → источник не создаётся».
- Runtime-фабрика теперь строит источники непосредственно по сохранённым тегам;
  видимость остаётся только политикой UI и не управляет созданием оборудования.

## Повторный Preview медленнее первого

- По трём последовательным циклам MC-032 выполнял `scan started` через 27–33 мс после `Data sources started`; повторный START контроллера задержку не создаёт.
- Между нажатием Preview и `Data sources started` повторно выполнялись TEST отключённого MIC-140 и подготовка MIC-185. Суммарная задержка составляла примерно 1,3–1,9 с.
- Причина: `Stop` обоих источников безусловно сбрасывал `fHardwarePrepareAttempted`, хотя отрицательный TEST уже был выполнен при загрузке конфигурации.
- Для offline-источника результат TEST теперь сохраняется до загрузки/изменения конфигурации. Повторный Preview не выполняет сетевые timeout. Для ранее работавшего устройства флаг по-прежнему сбрасывается, поскольку после Stop/Disconnect ему действительно нужна новая подготовка.
