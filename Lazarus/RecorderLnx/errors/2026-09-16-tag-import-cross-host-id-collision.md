# 2026-09-16 — импорт общей ODS переназвал чужой канал MIC-140

## Симптом и факты

На KIP-4 температурный канал MIC-140 с адресом `40-11` получил имя вида `1E...`. В доступной локальной копии `C:\Mera Files\RecorderLnx\config\projects\recorder_tags_v02.ods` строка `40-11` имеет пустое поле «Имя канала». Файл по точному пути пользователя (`...\recorder\_tags\_v02.ods`) на этом ПК отсутствует, поэтому конкретную строку, давшую имя `1E...`, не установить.

До исправления `ResolveImportTarget` искал тег сначала по числовому ID из ODS, затем по адресу. На разных ПК старые последовательные ID могли совпасть у разных каналов. Это подтверждённый механизм ошибочного перенаправления строки; конкретное совпадение KIP-4 без его конфигурации не подтверждено.

## Исправление

- Строка с адресом ищет цель только по адресу и источнику; отсутствие или неоднозначность совпадения означает пропуск, а не откат к ID/имени.
- Для строки без адреса диалог отдельно спрашивает, разрешать ли сопоставление по ID.
- Строка с пустым именем канала полностью пропускается до поиска цели и изменения свойств.
- Новые теги получают случайные положительные ID на основе GUID с проверкой коллизии. Сохранённые ID существующих тегов не меняются.

## Проверка и риск

Принудительная сборка Windows и проверка diff выполняются в этой итерации. Импорт на KIP-4 ещё нужно повторить на актуальной версии; старое неверное имя само не восстановится до корректного повторного импорта или ручной правки. Правило добавлено в `Docs/architecture/development-rules.md`.

## Уточнение алгоритма и ускорение

По следующему запросу пользователя приоритет изменён на «имя → источник+адрес → пропуск»; ID вообще удалён из сопоставления, поэтому вопрос об ID больше не показывается. Для таблиц, разделённых между несколькими ПК, индексы имён и адресов строятся один раз, повторы имён считаются однократно, массив выбранных строк резервируется заранее. Это устраняет повторные полные проходы по тегам и строкам. Полная Win64-сборка — OK; фактическое время импорта на KIP-4 ещё не измерено.

## Регрессия после деплоя 0.1.35: `Not allowed for sorted list`

Пользователь сообщил, что импорт перестал работать. Причина подтверждена по исходнику FPC `classes/stringl.inc`: `TStringList.Insert` при автоматической сортировке вызывает `SSortedListError`. Новый индекс адресов и список частот имён включали `Sorted=True`, но для нового ключа вызывали `InsertObject`.

Оба вызова заменены на `AddObject`, который сам вставляет элемент в нужное место сортированного списка; ветка повторного ключа сохраняет прежнее поведение. Полные сборки Windows и Linux — OK, Linux-отчёт `BUILD_EXIT=0`, `MISSING_LIBS=none`. DEB 0.1.36 установлен на KIP-1…KIP-4 (4/4). Повторный импорт через GUI пользовательского KIP ещё не выполнен; это оставшаяся проверка. Правило предотвращения добавлено в `Docs/architecture/development-rules.md`.
