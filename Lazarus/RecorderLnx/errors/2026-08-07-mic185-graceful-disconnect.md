# MIC-185: IoControl timeout после успешного TCP connect

## Наблюдение

Лог запуска 15:28 показал, что разнесение первого обмена на 150 мс устранило
часть TCP timeout, но не `Mebius IoControl timeout`: у `.151` и `.155` TCP
открывался за 31–32 мс, а `GetSoftVersion` не получал ответа за 3 секунды.
Одиночный reset `.148` после успешного TCP-пинга также завершался IoControl
timeout. Следовательно, причина не сводится к параллельному старту потоков.

## Причина и исправление

Сравнение с `windev-v3.9/Mebius/MebiusDAQ/DAQ/TCPLink/TCPLink.cpp` выявило
существенное отличие: оригинальный `CTCPLink::OnDisconnect` обязательно делает
`shutdown(SD_BOTH)` перед `closesocket`; комментарий исходника прямо указывает,
что это необходимо, чтобы BIOS прибора успел обработать disconnect. В
RecorderLnx сокет ранее сразу освобождался, что могло оставлять settings-сессию
MIC-185 занятой: следующий TCP connect принимался, но IoControl не обслуживался.

`TRecorderMebiusTcpClient.Disconnect` теперь выполняет двунаправленный
`fpShutdown(..., SHUT_RDWR)` перед закрытием. В одноразовую стадию
`TryInitializeSession` добавлена одна восстановительная попытка: корректно
завершить неответившую сессию, подождать 250 мс, заново подключиться и повторить
`GetSoftVersion`/чтение SN. Повтор не помещён в `Configure`, поэтому многократная
смена настроек не смешивается с инициализацией.

## Проверка

Полная сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0,
актуальный EXE слинкован. Требуется холодный стендовый запуск.

## 2026-08-10 — сброс после потери потока

После нескольких минут сбора запись в старую TCP-сессию завершалась `Mebius TCP
write failed`. Ручной сброс закрывал объект устройства, но начинал новую
инициализацию через 250 мс. По журналу TCP к этому времени уже принимался, а
Mebius `IoControl` ещё не обслуживался.

Сброс теперь выдерживает 1500 мс после обязательных `Stop` и `Disconnect`, затем
выполняет полный `Connect -> Initialize -> Configure`. Ошибка чтения, закрытие
сокета и нулевая запись помечают сессию потерянной; источник удаляет такой
клиент и на следующем запуске создаёт новую сессию вместо повторной записи в
старый сокет.

Полная сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0. Требуется
стендовая проверка: длительный Preview, Stop/Preview и ручной сброс MIC-185.

## 2026-08-10 — регрессия запуска и каскадный recovery

Защита от ошибки записи ошибочно заменила контракт `Start`: новый вариант
разрешал запуск только уже запрограммированной сессии и не выполнял прежние
`Connect -> Initialize -> Configure`. Узел мог быть зелёным, но поток не
запускался. Рабочий контракт `Start` восстановлен.

Также после первой неудачной подготовки UI дважды выполнял reset/reconnect всех
offline MIC-185 через общий `PrepareHardwareAll`. По журналу это создавало три
волны подключения пяти приборов и могло занять единственную settings-сессию у
всей группы. Автоматический групповой recovery удалён. Ошибка одного источника
оставляет offline только его; повторная подготовка выполняется адресной командой
«Сброс устройства».

Сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0. Приборы после
предыдущих каскадных попыток пока отвечают на TCP, но не отвечают на IoControl;
для подтверждения восстановления нужен новый запуск стенда после освобождения
их settings-сессий.
