# MIC-185: IoControl timeout после успешного TCP connect

## Наблюдение

Лог запуска 15:28 показал, что разнесение первого обмена на 150 мс устранило
часть TCP timeout, но не `Mebius IoControl timeout`: у `.151` и `.155` TCP
открывался за 31–32 мс, а `GetSoftVersion` не получал ответа за 3 секунды.
Одиночный reset `.148` после успешного TCP-пинга также завершался IoControl
timeout. Следовательно, причина не сводится к параллельному старту потоков.

## Причина и исправление

Сравнение с `windev-v3.9/Mebius/MebiusDAQ/DAQ/TCPLink/TCPLink.cpp` выявило
существенное отличие: оригинальный `CTCPLink::OnDisconnect` обязательно делает
`shutdown(SD_BOTH)` перед `closesocket`; комментарий исходника прямо указывает,
что это необходимо, чтобы BIOS прибора успел обработать disconnect. В
RecorderLnx сокет ранее сразу освобождался, что могло оставлять settings-сессию
MIC-185 занятой: следующий TCP connect принимался, но IoControl не обслуживался.

`TRecorderMebiusTcpClient.Disconnect` теперь выполняет двунаправленный
`fpShutdown(..., SHUT_RDWR)` перед закрытием. В одноразовую стадию
`TryInitializeSession` добавлена одна восстановительная попытка: корректно
завершить неответившую сессию, подождать 250 мс, заново подключиться и повторить
`GetSoftVersion`/чтение SN. Повтор не помещён в `Configure`, поэтому многократная
смена настроек не смешивается с инициализацией.

## Проверка

Полная сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0,
актуальный EXE слинкован. Требуется холодный стендовый запуск.

## 2026-08-10 — сброс после потери потока

После нескольких минут сбора запись в старую TCP-сессию завершалась `Mebius TCP
write failed`. Ручной сброс закрывал объект устройства, но начинал новую
инициализацию через 250 мс. По журналу TCP к этому времени уже принимался, а
Mebius `IoControl` ещё не обслуживался.

Сброс теперь выдерживает 1500 мс после обязательных `Stop` и `Disconnect`, затем
выполняет полный `Connect -> Initialize -> Configure`. Ошибка чтения, закрытие
сокета и нулевая запись помечают сессию потерянной; источник удаляет такой
клиент и на следующем запуске создаёт новую сессию вместо повторной записи в
старый сокет.

Полная сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0. Требуется
стендовая проверка: длительный Preview, Stop/Preview и ручной сброс MIC-185.

## 2026-08-10 — регрессия запуска и каскадный recovery

Защита от ошибки записи ошибочно заменила контракт `Start`: новый вариант
разрешал запуск только уже запрограммированной сессии и не выполнял прежние
`Connect -> Initialize -> Configure`. Узел мог быть зелёным, но поток не
запускался. Рабочий контракт `Start` восстановлен.

Также после первой неудачной подготовки UI дважды выполнял reset/reconnect всех
offline MIC-185 через общий `PrepareHardwareAll`. По журналу это создавало три
волны подключения пяти приборов и могло занять единственную settings-сессию у
всей группы. Автоматический групповой recovery удалён. Ошибка одного источника
оставляет offline только его; повторная подготовка выполняется адресной командой
«Сброс устройства».

Сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0. Приборы после
предыдущих каскадных попыток пока отвечают на TCP, но не отвечают на IoControl;
для подтверждения восстановления нужен новый запуск стенда после освобождения
их settings-сессий.

## 2026-08-10 — поток прекращался без ошибки соединения

В пятиминутном Preview служебные пакеты MIC-185 сначала поступали штатно, затем
у отдельных сессий исчезали без `EOF`, timeout или исключения. Причиной оказался
режим дочитывания: после первого пакета таймаут сокета уменьшался до 2 мс.
Частично пришедший TCP-пакет уже удалялся из сокета, но при timeout не сохранялся.
Следующее чтение начиналось с середины заголовка, и разбор потока терял
синхронизацию. TCP не гарантирует соответствия одного `Read` одному пакету.

Короткое дочитывание удалено. `ReadMeasDataBlock` штатным таймаутом пропускает
служебные пакеты до первого полного измерительного блока и сразу возвращает его;
несколько аппаратных блоков за один тик больше не склеиваются. Полная сборка
`lazbuild -B RecorderLnx.lpi` завершилась с exit code 0. Требуется контрольный
Preview не менее пяти минут и последующий `Stop -> Preview`.

## 2026-08-10 — запоздалый ответ команды при новом старте

При программировании был получен ответ `CALL_COMMAND (0x00101034)` вместо
ожидаемого `PROGRAMM_DEVICE_BIN (0x00101028)`. Прошивка дослала ответ предыдущей
команды, а клиент считал первый командный пакет безусловным ответом текущего
запроса. `TryIoControl` теперь пропускает ответы с другим IOCTL-кодом и ждёт
ответ своего запроса. Рабочий `DoTick` больше не пытается повторно вызвать
бросающий исключение `Start`: не запущенный источник помечается offline.

## 2026-08-10 — поток прекращался примерно через две минуты

В пяти минутном журнале все MIC-185 перестали выдавать UTS почти одновременно
около `17:47:44`, при времени прибора около `122,33 с`. Recorder оставался в
Preview до `17:50:45`; ошибок TCP, timeout и зависших процедур в журнале нет.

Первоначальная гипотеза об отставании чтения была неверна: журнал рабочей
сессии явно содержит `dataUpdate=200 ms`, то есть при 100 Гц ожидается около
20 измерительных пакетов за цикл, меньше прежнего предела 32. Значение 500 мс
к этой сессии не относится. Причина прекращения потока пока не подтверждена.

Предел чтения временно увеличен до 512 пакетов за цикл. Частично принятый TCP-пакет
сохраняется между короткими timeout. Добавлены сообщения `TEMP parsed` и
`Receive drain limit reached`; последнее означает, что чтение снова не
успевает за прибором. Повторная установка неизменившегося socket timeout убрана.

Полная сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0.
Автоматический CLI-запуск не загрузил рабочую аппаратную конфигурацию и не
является стендовой проверкой. Нужен контрольный Preview более пяти минут из
Lazarus с подключёнными MIC-185.

Последующая строгая фильтрация ответов по IOCTL-коду вызвала регрессию:
инициализация нескольких приборов завершалась `Mebius IoControl timeout`.
Фильтрация отменена и восстановлена прежняя обработка одного командного ответа.

## 2026-08-10 — неблокирующий приём измерительного потока

Повторный журнал уточнил картину: у двух работающих MIC-185 пакеты UTS и температуры
приходили синхронно со временем Recorder до `18:15:55`, затем оба вида служебных пакетов
исчезли без TCP-ошибки. Время UTS шло без накопления отставания. Это исключает прежнее
объяснение пределом 32 пакета и указывает на зависание/повреждение приёма TCP.

В измерительном цикле больше нет короткого блокирующего дочитывания. Перед каждым
`Read` проверяется наличие байтов в сокете с нулевым ожиданием. Если заголовок или тело
TCP-пакета пришли не полностью, принятая часть остаётся в накопителе и дочитывается на
следующем такте. Командный обмен конфигурирования сохраняет обычный таймаут и прежнюю
семантику ожидания ответа.

Полная сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0. Аппаратная
проверка длительным Preview ещё требуется.

## 2026-08-10 — зелёная иконка до протокольной проверки

Дерево устройств показывало MIC-185 исправным сразу после загрузки конфигурации,
поскольку `PrepareHardware` заранее очищал offline. Последующий reset выполнял
настоящий `Connect/Initialize/Configure`, находил `IoControl timeout` и только тогда
показывал ошибку. Предварительная очистка удалена: во время подготовки статус не
подтверждён, а зелёный устанавливается только после успешной конфигурации.

Сборка `lazbuild -B RecorderLnx.lpi` завершилась с exit code 0.
