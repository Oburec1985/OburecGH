# MIC-185: включённая аппаратная ГХ публикует сырые коды

## Симптом

После сохранения настроек тега аппаратная ГХ MIC-185 отмечена и единица
источника отображается как `мВ`, но значение тега остаётся около предела АЦП
`32768`. Ранее в собранном масштабе наблюдался коэффициент `1`.

## Подтверждённая цепочка

- После provider-рефакторинга `TagSettingsDialog` при AutoUnit не передаёт
  видимое значение `fUnitCombo.Text` в draft, а использует прежний
  `Tag.UnitName`.
- MIC-185 provider сохраняет режим источника только из `Draft.UnitName`.
- `ReadState` может показать `мВ` как fallback текущего диапазона, поэтому UI
  маскирует оставшийся режим `код` или пустую исходную единицу.
- Runtime MIC-185 выбирает режим из конфигурации источника, затем
  `SourceUnitName`, затем `UnitName`. При режиме codes преобразование остаётся
  единичным (`K=1`, `B=0`).
- MIC-185 публикует блок как уже преобразованный, поэтому общий tag pipeline
  намеренно не применяет ГХ повторно.

## Дополнительный runtime-дефект

`TagSettingsDialog` меняет флаг ГХ и tag scale, но не обновляет уже собранный
`fValueTransforms` работающего MIC-185. Кэш пересобирается при Start,
программировании или балансировке; Apply во время активного Preview может
оставить прежний единичный transform до следующего запуска источника.

Provider также сравнивает старое и новое состояние ГХ уже после того, как UI
записал новое значение в тег. Поэтому признак очистки истории всегда ложный.

## Источник регрессии

Наиболее вероятный источник — commit `bcef0e1c` от 2026-10-07, где прямое
сохранение MIC-185 единицы из combo заменено общим provider-контрактом.

## Статус

Исправлено. Диалог передаёт видимую единицу в draft и сравнивает результат с
исходным snapshot; provider отмечает реальные изменения unit/source unit; после
успешного Apply менеджер просит только соответствующий источник обновить
runtime-преобразования. MIC-185 строит новый массив преобразований вне потока
сбора и публикует его короткой атомарной сменой snapshot без перепрограммирования
прибора. Коэффициенты аппаратной ГХ теперь строятся только при реально включённом
флаге аппаратной ГХ.

Числовой regression test на production-функциях подтверждает `32768 -> 25 мВ`,
режимы hardware/channel GX on/off, внутреннее преобразование мВ в Ом, AutoUnit и
no-op Apply. `RecorderDataSourcesTest --mic185-unit-only`, отдельный v2 contract
test и forced-сборка RecorderLnx проходят.

## Повторная регрессия: `Ом` не применяется, после Apply канал показывает `-`

Диалог аппаратных настроек сохранял `Ом` в тег и конфигурацию, но не просил
работающий datasource пересобрать кэш преобразований. При программировании уже
запущенного MIC-185 источник останавливался, однако после успешной команды не
запускался снова. Поэтому до перезапуска оставался старый transform `мВ`, а
после Apply поток прекращался и значение превращалось в `-`.

Исправлено: редактор получает менеджер источников и после успешного Apply/OK
адресно обновляет runtime transforms; изменение source/display unit инвалидирует
масштаб и историю. Live-программирование теперь в `finally` возобновляет источник
и сообщает объединённую ошибку, если не удалась команда или повторный Start.
Загрузка проекта сохраняет ручную единицу при `AutoUnit=False`.

На KIP-3 дополнительно обнаружена несогласованность диапазона: в теге оставалось
имя ГХ `range3`, тогда как активный канал запрашивал другой диапазон, а файл
текущей ГХ отсутствовал. Runtime теперь всегда разрешает аппаратную ГХ по
фактическому текущему диапазону и никогда не применяет калибровку другого
диапазона; при отсутствии правильной ГХ выставляется предупреждение источника.

## 2026-10-09: первый канал после изменения Fs показывает `-`

На KIP-3 у `3Е129` в сохранённом проекте обнаружена порция МО `17280`, тогда
как у `3Е130` и следующих каналов того же MIC-185 `.159` порция равна `2` при
`Fs=10 Гц`. Значение `17280` является старым системным маркером автоматической
порции, а не пользовательским вводом.

Причина подтверждена в общем `TagSettingsDialog`: MIC-185 provider правильно
пересчитывал автопорцию всего источника после смены Fs, но затем диалог заменял
отображаемое вычисленное значение обратно на legacy-маркер `17280` только у
редактируемого тега. Подмена удалена. Теперь сохраняется фактическая порция
`ceil(Fs * DataUpdateMs / 1000)`; существующий source-wide helper продолжает
пересчитывать её при следующей смене Fs, а явно отличающееся ручное значение
не изменяется.

Forced Win64-сборки `RecorderTagsTest.lpi` и `RecorderLnx.lpi` прошли. Сам
`RecorderTagsTest.exe` дважды дошёл до известных независимых нестабильных
проверок EventBus/time epoch и завершился на них; ошибок компиляции нет.

Проверено локально: `RecorderDataSourcesTest --mic185-unit-only`, проектный
roundtrip `--mic185-unit-roundtrip-only` и forced Win64 build RecorderLnx — OK.
Fresh Linux build установлен на KIP-1..KIP-4. На KIP-3 существующий проект
подтвердил `unit=Ом`, `sourceUnit=Ом`, корректную текущую ГХ `range3` для
фактически запрограммированного range index 2, 50 принятых блоков без потерь и
чистый Stop/Preview/Acquire. Значение не осталось в состоянии `-`.

## 2026-10-09: смена диапазона на 125 Ом остановила публикацию

125 Ом при питании 4 мА соответствует диапазону ±500 мВ (`range index 0`,
каталог `range1`). На KIP-3 для MIC-185 sn0171 после переключения сначала не
было файлов аппаратной ГХ нового диапазона. Runtime считал отсутствие ГХ
ошибкой достоверности и пропускал весь блок канала, поэтому связь и UTS
оставались живыми, но пользователь видел остановку измерений.

Исправлено двумя уровнями. После успешного программирования источника диалог
автоматически считывает из подключённого MIC-185 недостающие коэффициенты ГХ
текущего диапазона и только затем обновляет runtime transforms. Если ГХ всё же
нельзя получить, канал больше не подавляется: публикуются неизменённые коды АЦП
без программного баланса, пересчёта единиц и последующих ГХ; источник выдаёт
явное предупреждение о кодовом режиме.

Linux-сборка 0.1.150 собрана непосредственно на KIP-3, установлена с резервной
копией 0.1.149 и запущена через RecorderHostAgent. Обнаруженный параллельный
`Recorder.exe` под Wine временно захватывал MIC-185 и вызывал IoControl timeout;
после освобождения соединения RecorderLnx успешно инициализировал sn0171,
перешёл в Acquire и принял 50 блоков без потерь (`syncdrop=0`).
