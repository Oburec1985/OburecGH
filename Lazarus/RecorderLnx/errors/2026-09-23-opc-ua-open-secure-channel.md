# OPC UA: сервер отклоняет OpenSecureChannel

## Симптом

TCP-пинг RecorderLnx до `192.168.15.130:4840` успешен (16 мс), но кнопки
«Проверить связь» и «Найти теги» завершаются на стадии OpenSecureChannel с
сообщением `server returned UA-TCP ERR`.

## Подтверждённые факты

- ICMP до ПЛК работает.
- TCP-соединение через выбранный в RecorderLnx сетевой интерфейс работает.
- HEL/ACK завершается, иначе ошибка имела бы стадию `HEL/ACK`.
- Отказ приходит после отправки OPN и является штатным UA-TCP Error Message.

## Ошибка диагностики

Первоначальная реализация читала только восьмибайтный заголовок `ERR`, не
забирала тело и скрывала переданные сервером `StatusCode` и `Reason`. Поэтому
невозможно было отличить неверный endpoint от ошибки кодирования или политики.

## Изменение

`ReceiveUaMessage` теперь читает тело ERR, декодирует `StatusCode` и строку
`Reason`, после чего возвращает их вместе со стадией OpenSecureChannel.

После повторной проверки ПЛК вернул `0x80AB0000` (`BadInvalidArgument`).
Проверка бинарного RequestHeader выявила причину: null ExtensionObject поля
AdditionalHeader кодировался двумя байтами. По OPC UA Binary он состоит из
двухбайтового null NodeId `i=0` и отдельного байта Encoding=0, то есть занимает
три байта. Пропущенный байт смещал начало тела OpenSecureChannelRequest.

Кодирование исправлено добавлением Encoding=0.

## Проверка

Требуется повторить «Проверить связь» на ПЛК после сборки. Ожидаемый эффект —
сервер перестаёт возвращать `BadInvalidArgument` на стадии OpenSecureChannel.

## Порт перестал принимать TCP после диагностических сессий

После успешного подключения и Browse повторный поиск завершился ещё до HEL с
`TCP: Истекло время TCP-подключения`. Общая кнопка `TCP-пинг` RecorderLnx дала
тот же результат, при этом ICMP ping и ARP до `192.168.15.130` оставались
исправны. Это подтверждает состояние OPC UA-службы/порта, а не ошибку endpoint
или маршрута. Проект использует bind `192.168.3.65`; адрес находится в прямой
подсети `/20` и ранее с ним TCP-пинг проходил.

Клиент при уничтожении ранее освобождал только сокет. Добавлено штатное
завершение: `CloseSession(DeleteSubscriptions=True)`, затем сообщение
`CloseSecureChannel` и только после этого закрытие TCP. Операции закрытия
best-effort и не мешают гарантированному освобождению сокета.

Для уже занятого или зависшего серверного состояния нужен перезапуск OPC UA
службы либо ПЛК; после восстановления проверяется, что серия
`Проверить связь`/`Найти теги` не исчерпывает доступные сессии.

## Автоматический источник без каналов создавал шторм переподключений

В сохранённой конфигурации найден OPC client с `nodes: []`. Несмотря на пустой
список, `PrepareHardware` открывал сессию при загрузке проекта. После ошибки
worker вызывал `PrepareHardware` снова на каждом тике; журнал подтвердил серии
OPN через 100–300 мс. Это могло занять единственный клиентский слот либо
перегрузить реализацию OPC UA в ПЛК.

Исправлено: client без выбранных узлов не обращается к сети, а после любой
ошибки подготовки следующая попытка разрешена не раньше чем через 5 секунд.

## Продолжение проверки: Browse отклонён с 0x80230000

После исправления OpenSecureChannel соединение и сессия стали создаваться, но
Browse возвращал service status `0x80230000`. По официальной таблице кодов OPC
UA это `BadInvalidTimestamp`: сервер отклоняет временную метку вне допустимого
диапазона.

Причина находилась в `TOpcUaWriter.RequestHeader`: поле Timestamp для всех
сервисных запросов всегда кодировалось как `UInt64(0)`, то есть как начало эпохи
OPC UA (1601-01-01), а не текущее время.

Добавлено преобразование текущего UTC-времени в OPC UA DateTime — количество
100-нс интервалов с 1601-01-01 — и это значение теперь записывается в каждый
RequestHeader.

## Итоговая проверка

Одноразовый живой пробник, использующий тот же
`TRecorderOpcUaBinaryClient`, выполнил полный цикл с сервером
`opc.tcp://192.168.15.130:4840`:

- `CONNECT OK`;
- `BROWSE OK: 88 nodes`;
- найдены прикладные переменные ПЛК `blinkerplc`, `cmd_but`, `count_cmdbut`,
  `Tag_`, `Tags_`.

Ошибка `BadInvalidTimestamp` устранена и поиск тегов подтверждён на реальном
сервере.

## Чтение найденных переменных закрывало соединение

После успешного Browse выбор `blinkerplc` и `count_cmdbut` завершался ошибкой
`service: connection closed`. Причина подтверждена в клиентском UI: диагностический
поток получал каждую строку в формате `NodeId|TagName` и разбирал её по первому
символу `|`. Строковые NodeId PLC210 сами содержат `|var|`, например
`ns=4;s=|var|PLC210 OPC-UA.Application.GVL.blinkerplc`. Поэтому реальный адрес
обрезался до `ns=4;s=` и в Read-запрос уходил неверный NodeId.

Исправлено: NodeId и имя тега передаются в поток двумя независимыми списками.
Строкового разделителя больше нет, полный NodeId сохраняется без изменений.
Поддержка чтения Boolean и Float в binary-клиенте уже присутствует.

Проверка: выполнена полная forced-сборка `RecorderLnx.lpi`, exit code 0.
Нужна повторная живая кнопка «Прочитать значения» на выбранных переменных ПЛК.

## Короткий SessionTimeout и восстановление после обрыва

Клиент ранее запрашивал SessionTimeout 3 600 000 мс. После аварийного
завершения сервер мог сохранять потерянную сессию до часа. Параметр вынесен в
настройки OPC UA как «Таймаут сессии, с», значение по умолчанию — 15 секунд,
диапазон — 1–3600 секунд. В JSON он хранится как `sessionTimeoutMs`; старые
проекты без поля получают 15 секунд. Значение передаётся в CreateSession, а
возвращённый сервером revisedSessionTimeout декодируется клиентом.

Дополнительно устранён reconnect-шторм после ошибки рабочего Read: источник
закрывает повреждённый transport и ждёт 5 секунд перед новой попыткой. При
успехе повторяется полный путь `Connect -> Initialize -> Configure -> Start`,
поэтому все сохранённые NodeId регистрируются в новой сессии. Пустой источник
по-прежнему в сеть не выходит.

Проверка: полная forced-сборка `RecorderLnx.lpi`, exit code 0. Аппаратный
сценарий «вытащить кабель -> дождаться ошибки -> вставить кабель» требуется
повторить на стенде.

## Пустая диагностика Read

При чтении трёх скалярных узлов интерфейс показывал пустое `Ошибка:`. Сервер
вернул DataValue без поля Value, но с полем StatusCode. Декодер проверял
отсутствие Value раньше StatusCode и выходил, не заполнив ErrorText.

Исправлено: при отсутствии Value декодируется StatusCode и выводятся полный
NodeId и код `0x........`; отдельно диагностируются пустой массив результатов,
массив вместо скаляра и исключение декодирования. На уровнях API и UI добавлен
fallback, поэтому пустой текст ошибки больше невозможен.

Создан `Tests/OpcUaProtocolDebug_Codex/OpcUaReadProbe.lpr`, использующий
production-класс `TRecorderOpcUaBinaryClient`. Пробник собран успешно. Два
последовательных запуска не дошли до Read: `192.168.15.130` отвечает ICMP за
1 мс, но TCP/4840 не принимает соединение даже после ожидания больше 15 секунд.
`Test-NetConnection` независимо подтвердил закрытый/зависший порт.

Следующий шаг после перезапуска OPC UA-службы или ПЛК: немедленно повторить
пробник, получить StatusCode и продолжать итерации до трёх `READ OK`.

## Пустая диагностика Read

При чтении трёх скалярных узлов интерфейс показывал пустое `Ошибка:`. Сервер
вернул DataValue без поля Value, но с полем StatusCode. Декодер проверял
отсутствие Value раньше StatusCode и выходил, не заполнив ErrorText.

Исправлено: при отсутствии Value декодируется StatusCode и выводятся полный
NodeId и код `0x........`; отдельно диагностируются пустой массив результатов,

Проверка: полная forced-сборка `RecorderLnx.lpi`, exit code 0. Для определения
первопричины отказа ПЛК нужно повторить кнопку «Прочитать значения» и получить
теперь уже видимый StatusCode.
## Debugger exception на массивном Property

`ReadDataValueDisplayText` использовал `raise EOpcUaBinaryError` для обычного
Variant-array. Хотя верхний уровень перехватывал исключение, Lazarus debugger
останавливался на самом `raise`.

Исправлено: массив и неизвестный скаляр являются штатным результатом разбора и
выводятся как `<массив>` / `<тип N>` без исключения. Forced-сборка RecorderLnx
завершилась с exit code 0.

## Дочерние значения Variant-массива — 2026-09-28

Запрос: вместо общей строки `<массив>` показывать элементы массива дочерними
узлами редактора OPC UA и добавить поиск по используемым каналам.

Подтверждённая причина: `ReadDataValueDisplayText` распознавал array-mask, но
безусловно пропускал каждый scalar через `SkipScalar`, поэтому после
протокольного слоя восстановить значения было невозможно.

Исправлено: общий scalar-декодер сохраняет элементы Variant-массива; API
передаёт их редактору, а дерево создаёт дочерние строки без собственного
NodeId. Это не смешивает элементы массива с реальными browsed-узлами вроде
`Tags_[1]`. Правое дерево получило независимый фильтр по подстроке.

Проверка на PLC210 `192.168.15.130:4840`: production probe — `CONNECT OK`,
`BROWSE OK: nodes=1234`; узел `...GVL.Tag_` прочитан как массив из 1000
значений с SourceTimestamp. Два скалярных канала прочитаны с `READ OK`.
Forced-сборка `RecorderLnx.lpi` завершена с exit code 0.

### Исправление двойного представления массива

Live Browse подтвердил, что PLC210 уже возвращает реальные пути
`.../GVL/Tag_/Tag_[1]` (1000 узлов) и `.../GVL/Tags_/Tags_[1]` (100 узлов).
Дубли создавал UI: родительский leaf содержал NodeId в caption, поэтому поиск
родителя по тексту не находил его и создавал параллельный structural-узел;
одновременно добавлялись синтетические значения Variant-массива.

Исправлено: связь строится до рендера по BrowsePath и индексному имени, дети
вкладываются в реальный parent с `Data/NodeId`, а synthetic fallback подавляется
при наличии любого реального индексного ребёнка. Forced Windows build — OK.

## Регрессия пустого дерева после добавления значений Property

Чтение Value было ошибочно добавлено в тот же обязательный ReadRequest, что
DataType/AccessLevel/UserAccessLevel. Неподдержанный Variant одного свойства
прерывал `ReadAccessLevels`, затем весь рекурсивный Browse; UI получал пустое
дерево.

Исправлено: обязательный запрос снова содержит только три структурных атрибута,
а Value каждого Property читается отдельным best-effort запросом. Ошибка одного
значения отображается у этого свойства и не отменяет найденные узлы.

Проверка: forced-сборка RecorderLnx — exit code 0. Аппаратная проверка не
выполнена: production-пробник получил TCP timeout на `192.168.15.130:4840`.

## OPC UA-тег записи отсутствовал в настройках кнопки

Список «Изменяемый тег» ошибочно допускал только `IsVirtual=True`, поэтому
опубликованный аппаратный OPC UA-тег скрывался даже при подтверждённом сервером
праве записи. Источник OPC UA уже переносит `Writable` узла в свойство тега
`ExternalWriteAllowed`, а runtime кнопки проверяет именно это свойство.

Исправлено: picker кнопки фильтрует по `ExternalWriteAllowed`. Это сохраняет
виртуальные теги и добавляет доступные для записи OPC UA-теги, не показывая
каналы только для чтения. Forced Windows-сборка завершилась с exit code 0.

## Stream write error при переходе в просмотр

При уничтожении временного OPC UA-клиента выполнялся best-effort
`CloseSession`. Если сервер уже закрыл TCP, вызов
`fStream.CopyFrom(Message, Message.Size)` попадал в `TStream.WriteBuffer`,
который превращает нулевую/короткую запись в `EStreamError`. Исключение затем
перехватывалось в `CloseSession`, но Lazarus останавливался на first-chance
exception и показывал пользователю `Stream write error`.

Все четыре пути отправки `HEL/OPN/MSG/CLO` переведены на общий `SendMessage`:
он циклически обрабатывает частичные записи, а закрытый транспорт возвращает
как штатную ошибку без `TStream.WriteBuffer`. Одновременно закрыта утечка
буфера запроса `CloseSession`; `ExchangeService` освобождает полученный ответ,
если декодирование заголовка завершилось исключением.

Проверка: forced Windows-сборка завершилась с exit code 0; RecorderLnx запущен,
ответил GUI и штатно закрыт. Live-сценарий с активной OPC UA-сессией недоступен:
`Test-NetConnection 192.168.15.130 -Port 4840` вернул TCP failure, production
probe — `TCP: Истекло время TCP-подключения`.

## Сверка атрибутов с Multi-Protocol MasterOPC Server

Установленный клиент найден по ярлыку как `mps.exe` версии 6.0.33. Его
конфигурация `demo.mpn` подтверждает для PLC210: `cmd_but` — Boolean/
WriteOnly, `blinkerplc` — Boolean/ReadOnly, `count_cmdbut` — Float/ReadOnly;
NodeId совпадают с используемыми RecorderLnx строками `ns=4;s=|var|...`.

Номера OPC UA-атрибутов клиента проверены: Value=13, DataType=14,
ValueRank=15, AccessLevel=17, UserAccessLevel=18, Historizing=20. Исправлено:
ValueRank и Historizing теперь читаются; Current/HDA-права определяются
пересечением серверного и пользовательского AccessLevel; Bad StatusCode
отклоняется; миллисекунды SourceTimestamp не округляются в диагностике;
абсолютный Unix SourceTimestamp не попадает в elapsed-шкалу тегов Recorder.

Оставшиеся ограничения отдельного развития: BrowseNext для continuationPoint,
ArrayDimensions/MinimumSamplingInterval/Description и перенос Uncertain-
качества в модель тега. Текущий scalar Read Boolean/целых/Float/Double и
идентификация прав соответствуют проверенной конфигурации поставщика.
## 2026-09-28 — локальная запись тега не доходила до OPC UA server

**Симптом:** кнопка меняла локальное значение writable-тега `cmd_but`, но
значение переменной на PLC210 не изменялось.

**Подтверждённая причина:** `ExternalWriteAllowed` использовался только как
UI-capability. Кнопка вызывала общий `TagRegistry.PublishValue`, а client API и
binary client вообще не имели OPC UA `WriteRequest`. Дополнительно редактор
терял `DataTypeNodeId`, поэтому Boolean нельзя было корректно отличить от
Double; сервер должен отклонять неверный Variant с `Bad_TypeMismatch`.

**Исправлено:** добавлен явный `PublishExternalValue`, потокобезопасная очередь
исходящих команд у тега, client `WriteRequest` (binary encoding id 673), разбор
StatusCode, точное кодирование Boolean/SByte..Double, сохранение DataTypeNodeId
в JSON и повтор неподтверждённой команды после reconnect. Входящие OPC-значения
не ставятся в очередь записи. Успех и ошибка write пишутся в `LogWindows.log`.

**Проверка:** forced Windows-сборка RecorderLnx и пересборка production read
probe завершились с exit code 0. Формат WriteValue/DataValue сверен с OPC UA
Part 4/6. Живая write/readback-проверка заблокирована внешним состоянием:
`192.168.15.130` отвечает на ping, но TCP 4840 не принимает соединение;
production probe сообщает `TCP: Истекло время TCP-подключения`.

## 2026-09-28 — неполное Browse-дерево

**Симптом:** внешний OPC UA client показывал `DeviceFeatures`,
`PLC210 OPC-UA`, `NetworkSet` и другие Object-узлы, которых не было в
подробном дереве RecorderLnx.

**Подтверждённые причины:** `BrowseRequest` запрашивал Object и Variable,
но в модель результата добавлял только Variable. ContinuationPoint
из BrowseResult выбрасывался, поэтому серверный лимит мог тихо
обрезать ветку. Любая ошибка `ReadVariableAttributes` обрывала весь Browse.

**Исправлено:** Object и Method сохраняются как отдельные узлы;
ContinuationPoint дочитывается через `BrowseNext`; предел глубины поднят
с 16 до 64; ошибка атрибутов помечает только один узел. В UI добавлены
Ctrl/Shift-мультивыбор, групповое popup-добавление и поиск.

**Проверка:** forced Windows build — exit code 0. Live Browse не запустился
из-за внешнего состояния: `192.168.15.130` отвечает на ICMP, но
TCP 4840 недоступен; production probe вернул timeout. Тестовый
RecorderLnx закрыт принудительно после отказа штатного Stop-Process.
