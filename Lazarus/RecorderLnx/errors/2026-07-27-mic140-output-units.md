# 2026-07-27 — MIC-140: единицы не соответствуют активному конвейеру

## Симптом

После выбора термопарной ГХ и компенсации холодного спая диалог тега продолжал
показывать `mV`. Снятие галки аппаратной ГХ также не переводило единицу в коды
АЦП.

## Подтверждённая причина

- Настройки канала хранят отдельные признаки аппаратной ГХ, термопарной ГХ и
  режима выхода.
- Диалог канала сохранял имя термопарной ГХ, но не обновлял `OutputMode` и
  `ChannelCalibrationEnabled`.
- Диалог тега менял единицу по галке канальной ГХ, не учитывая состояние
  аппаратной ГХ.
- В нескольких местах существовали отдельные присваивания `mV`/`degC`, поэтому
  загрузка проекта, аппаратный диалог и runtime могли показывать разные единицы.

Старый `D:\works\bu\recorder_lnx\001_unstable` подтвердил рабочий конвейер
КТХС и порядок преобразований, но в нём также не было полного единого правила
переключения единицы.

## Исправление

- Добавлен единый `RecorderMic140ApplyTagOutputPresentation`.
- Инвариант: без аппаратной ГХ — `code`; с аппаратной ГХ и напряжительным
  режимом — `mV`; с аппаратной и термопарной ГХ — `degC`.
- Выбор/очистка термопарной ГХ обновляет `OutputMode` и
  `ChannelCalibrationEnabled`.
- Массовое применение настроек копирует эти поля для каждого выбранного канала.
- Единый метод вызывается после аппаратного диалога, изменения галок,
  загрузки конфигурации, назначения ГХ и перед программированием источника.
- Галка аппаратной ГХ сразу меняет показанную единицу в `TagSettingsDialog`.

## Проверка

Полная сборка `lazbuild -B RecorderLnx.lpi` завершена с exit code 0.
Аппаратный протокол и код сбора данных не изменялись.

## Follow-up 2026-09-04: единица источника и AutoUnit

Повторная проверка с командой выявила, что прежний единый метод смешивал три
разных состояния: физический режим источника, включение аппаратной ГХ тегом и
автоматическую подпись единиц. Из-за этого ручная единица перезаписывалась, а
при загрузке проекта устаревшая копия флага из MIC-140 channel config могла
перекрыть уже загруженное свойство тега.

Исправлен контракт:

- `SourceValueMode` всегда отражает физический режим MIC-140: `mV` либо `degC`;
- `HardwareCalibrationEnabled` тега выбирает сырые коды или физическое значение;
- при `AutoUnit=True` единица равна `code` для сырых данных и единице источника
  для включённой аппаратной ГХ;
- при `AutoUnit=False` пользовательская единица не изменяется;
- при загрузке нового JSON флаг тега является главным и синхронизирует legacy
  channel config; fallback из channel config оставлен только старым проектам.

MIC-185 не изменялся. Forced-сборки RecorderLnx, Tags и DataSources завершились
успешно. DataSources suite прошёл; Tags suite остановился на существующей
проверке EventBus `expected 0, got 1`, не связанной с единицами MIC-140.

## Follow-up 2026-09-04: включённая ГХ продолжала показывать коды

На активном проекте у `140_{40_1}` подтверждены корректные данные: флаг тега
включён, ГХ `MIC140 sn0326 06_100mV ch01` присутствует, а код около `25303`
должен преобразовываться примерно в `73 мВ`.

Причина была в runtime-кэше: указатель на ГХ фиксировался только при подготовке
источника. После включения галочки во время Preview в кэше оставался `nil`, а
решение о преобразовании дополнительно читалось из копии флага в конфигурации
источника вместо свойства тега.

Исправлено:

- runtime MIC-140 кэширует объект ГХ независимо от текущего состояния галочки;
- ветка `code/physical` на каждом блоке выбирается по
  `TRecorderTag.HardwareCalibrationEnabled`;
- если ГХ назначена во время Preview, существующий кэш подхватывает её без
  пересоздания источника, TCP-сессии и без аппаратного Configure;
- автоматическая единица также определяется по флагу тега;
- MIC-185 не изменялся.

Проверка: forced-сборки `RecorderDataSourcesTest.lpi` и `RecorderLnx.lpi` — OK;
полный существующий `RecorderDataSourcesTest` — все сценарии passed. В текущем
журнале MIC-140 `.40` не прошёл TCP TEST, поэтому показанный на экране старый
буфер не является аппаратной проверкой свежего потока.
