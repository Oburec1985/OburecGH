# SQLdb: schema 3 newer than supported 2

## Симптом

При обращении к Firebird появилось сообщение:

`Database schema 3 is newer than supported 2`.

## Подтверждённые факты

- сообщение формируется только в `TRecorderSqlDbRepository.EnsureDatabase`;
- версия берётся как `max(schema_info.version)`;
- текущий `CRecorderSqlDbSchemaVersion` равен 3;
- актуальный workspace EXE собран 25.08.2026 и поддерживает миграцию v3;
- фактический текущий процесс запущен из
  `Lazarus/RecorderLnx/lib/x86_64-win64/RecorderLnx.exe`;
- установленный/старый EXE от 29.07.2026 не содержит актуального migration code;
- исправление обычного Trend не uses SQLdb и не открывает базу.

## Причина

Конкретный текст с `supported 2` мог создать только старый или альтернативный
бинарник, скомпилированный до перехода SQL-схемы на v3. Запуск SQL runtime на том
же переходе Recorder сделал проблему заметной одновременно с Trend-изменением,
но не создал её.

Точная цепочка Linux package подтвердила stale artifact: `.deb` был создан
25.08 в 13:23:38 и содержит executable размером 58 371 328 байт, тогда как
актуальный Linux executable был собран только в 13:33:49 и имеет размер
58 796 336 байт. `build-installer.bat` не компилировал приложение, а молча
упаковал существовавший на тот момент старый файл.

Schema v3 появилась 21.08.2026 в commit `16ec4d29`, то есть за четыре дня до
исправления Trend. Фактическое время первой миграции конкретной БД без чтения
`schema_info.applied_at` не установлено.

## Безопасное восстановление

Закрыть старый процесс и запускать актуальный workspace EXE. Не понижать номер
в `schema_info`, не удалять и не пересоздавать `RECORDERLNX.FDB`.

Упаковщик дополнен fail-fast проверками: Linux ELF должен быть не старее
production sources, содержать маркеры ожидаемой SQL schema, а бинарник внутри
`.deb` обязан побайтно совпадать со staging input. Успешная сборка печатает
SHA-256. Текущая проверка штатно остановила упаковку: Linux binary 13:33 старее
`RecorderLnx.lpi` 14:24; требуется ещё одна forced Linux-сборка.

## Риск, найденный аудитом

Текущий `EnsureDatabase` выполняет idempotent DDL и commit до проверки newer
schema. Поэтому диагностику неизвестной/новой БД следует делать read-only SQL,
а воспроизведение — только на копии. Будущее улучшение: version preflight до
любого DDL и транзакционные миграции.

## Проверка

Проведён статический аудит команды, проверены исходники, времена EXE/БД и путь
запущенного процесса. Прямой запрос Firebird не выполнялся: пароль SYSDBA не
найден в окружении; обходить credential boundary не стали.

## 2026-08-25: пароль в конфигурации Recorder

Для запуска из Linux GUI/IDE без наследования environment добавлен ключ
`[SQLdb] Password` в project `sql-db.ini`. Он имеет приоритет над прежним
`PasswordEnvironment`; пустое значение сохраняет обратную совместимость с
environment/Windows registry. Диалог показывает отдельное маскированное поле,
а на Unix сохранённый INI получает mode `0600`. Пароль не добавлен в шаблон и
не выводится в логи.

## 2026-08-25: авторизация при графическом запуске Linux

Ярлык запускал EXE напрямую, поэтому графическая сессия могла не получить
`RECORDERLNX_SQLDB_PASSWORD` из `/etc/profile.d`. Пакет теперь устанавливает
пусковую обёртку, загружающую профиль, а Firebird installer записывает
сгенерированный пароль в установленный project `sql-db.ini`. Синхронная ошибка
необязательной SQLdb больше не прерывает загрузку основного проекта.

## 2026-08-25: first-chance exception при пустом пароле

Linux IDE останавливалась на `TIBConnection.DoInternalConnect` до обработки
ошибки worker-потоком. Менеджер теперь проверяет Firebird login до создания
runtime: при пустом пользователе или пароле SQLdb отключается только в памяти,
а `TIBConnection.Open` не вызывается.

## 2026-08-25: фактическая SSH-отладка Linux VM

На `192.168.112.128` активный конфиг сначала содержал пустой пароль. После
переноса Windows Firebird password соединение всё ещё отвергалось, хотя Pascal
видел credentials полностью, а `isql` успешно подключался.

Корневая причина была в формировании подключения: порт вручную добавлялся в
`HostName`, а свойство `TIBConnection.Port` не использовалось; удалённому
Windows Firebird передавалось только имя файла вместо полного server-side пути.
Подключение переведено на штатные `HostName` + `Port`, а путь собирается из
`RootDirectory` и `Database`.

Затем исправлены права `/var/opt/mera/SQLdb/data`: Firebird installer создаёт
каталог владельцем пользователя RecorderLnx с mode `0700`.

Проверка на VM: Linux build/link и post-build завершились с code `0`.
RecorderLnx оставлен запущенным; через 45 секунд процесс жив, SQL errors `0`,
TCP `192.168.3.65:3050` находится в `ESTAB`.

Финальное review дополнительно закрыло edge cases: Windows server root с
завершающим разделителем, `Port=0` как default драйвера, fresh DEB без
`SUDO_USER` и доставку platform-specific post-build scripts. После чистого
перезапуска подтверждён ровно один процесс RecorderLnx, SQL errors `0` и
`ESTABLISHED` к Windows Firebird.
