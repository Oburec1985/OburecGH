# Preview: высокая загрузка двух ядер

Дата: 2026-07-27.

## Симптом

После перехода `Stop -> Preview` два логических ядра могут быть загружены почти
на 100 %. Проверялись три гипотезы:

1. кольцевая запись измерений на диск в Preview;
2. цикл источника данных без фактического ожидания;
3. поточечная обработка и отрисовка высокочастотных сигналов.

## Воспроизведение и измерение

Запуск:

```text
RecorderLnx.exe --preview-seconds=15
```

Текущая конфигурация:

- период данных и UI: 200 мс;
- MERA: 9 сигналов `R4` по 57 600 Гц;
- базовая страница: до 16 осциллограмм;
- один спектральный узел: FFT 8192, 13 привязок.

Дельта CPU по потокам снималась раз в секунду через
`System.Diagnostics.Process.Threads[].TotalProcessorTime`.

Подтверждено:

- процесс потреблял примерно 1,17–1,31 секунды CPU за одну секунду;
- поток `Src_mera.file.1`, TID 9088, потреблял 0,969 секунды CPU за секунду;
- лог источника показывал `Tick took 188..235 ms` при периоде 200 мс;
- поток не получает интервала отдыха и фактически превращается в busy worker,
  хотя внешний цикл формально содержит `SleepInterruptible`.

## Причина 1: поточечное чтение MERA

`Core/uRecorderDataSources.pas`:

- `TMeraPlaybackSignal.PublishVectorDue` проходит каждый отсчёт циклом;
- `ReadRawValue` вызывает `TFileStream.ReadBuffer` отдельно для каждого
  `Single`;
- при 9 каналах по 57 600 Гц это около 518 400 мелких файловых вызовов в
  секунду до учёта публикации тегов и спектров.

Это основная подтверждённая причина загрузки первого ядра.

Дополнительная стоимость того же пути:

- формирование массива времени по каждому отсчёту;
- `TRecorderTagRegistry.AddBlockSamples` создаёт и копирует промежуточный
  массив значений;
- `TRecorderSignalBuffer.AddSamples` копирует last-block и затем поточечно
  переносит данные в кольцо;
- `PublishBlockNotifications` снова получает копию last-block и создаёт
  полное событие блока.

## Причина 2: базовая страница не ограничивает данные разрешением экрана

`UI/uRecorderOglOscillogramView.pas`,
`TRecorderOglOscillogramSurface.Refresh`:

- для каждой из 16 осциллограмм вызывается `lTag.Snapshot`;
- `Snapshot` копирует весь кольцевой буфер;
- каждый отсчёт выбранного окна добавляется через `lTrend.AddValue`;
- при окне 1 с и 16 каналах 57 600 Гц один UI-кадр обрабатывает до 921 600
  точек, а при периоде 200 мс — до 4,6 млн точек/с, хотя ширина графика
  составляет лишь сотни пикселей.

В автоматическом запуске без видимой активной отрисовки UI-поток потреблял
около 0,11–0,14 секунды CPU/с. При видимой базовой странице и реальном
OpenGL redraw этот контур объясняет загрузку второго ядра.

## Отклонённая гипотеза: запись на диск в Preview

`UI/uMainForm.pas`, `ApplyTagEventSnapshot` вызывает
`TRecorderMeraTagWriter.WriteBlock` только если состояние равно `rsRecord` и
файл записи открыт. В `rsPreview` этот путь не выполняется. Нагрузка возникает
до входа в режим записи, поэтому кольцевая дисковая запись не является
причиной данного симптома.

## Требуемое исправление

Не добавлять потоки.

1. MERA: читать из каждого `.dat` сразу порцию отсчётов одним `ReadBuffer`,
   используя заранее выделенный типизированный буфер; затем пакетно
   публиковать блок.
2. Реестр тегов: убрать промежуточные копии для уже преобразованных данных,
   писать две непрерывные части кольца через `Move`.
3. UI: хранить кольцо готовых порций источника и собирать требуемое временное
   окно несколькими `Move`. Передавать все отсчёты в chart одним пакетным
   вызовом, без поточечного `AddValue`. Decimation в эту правку не входит.
4. После правки повторить тот же 15-секундный профиль. Критерий:
   `Src_mera.file.1` стабильно завершает tick заметно быстрее 200 мс и имеет
   реальное ожидание между тиками; UI не масштабируется линейно с Fs.

## Исправление и контрольный замер

- `TMeraPlaybackSignal` заранее выделяет типизированный буфер порции и читает
  `R4` одним `ReadBuffer`, а не отдельным файловым вызовом на отсчёт.
- `TRecorderSignalBuffer` хранит кольцо заранее выделенных блоков. Публикация
  порции выполняет два `Move`; `Snapshot` объединяет последние блоки в
  хронологическом порядке.
- `cBuffTrend1d.ReplaceValues` заменяет всю линию одним `Move`; цикл
  `AddValue` по каждому отсчёту удалён.
- Полная сборка `RecorderLnx.lpi` прошла.
- Повторный запуск `RecorderLnx.exe --preview-seconds=15`: тик
  `Src_mera.file.1` уменьшился с `188..235 ms` до `16 ms` при периоде
  `200 ms`. У потока появился устойчивый запас времени ожидания.
- Дельта CPU наиболее нагруженного потока после прогрева составила примерно
  `94..219 ms` за секунду вместо `969 ms/с` до исправления.

## Поведение после окончания файлового источника

Дополнительный прогон длиной 40–45 секунд показал, что после EOF источника
MERA циклов сбора без ожидания нет: периодические источники сохраняют
планирование по `UpdateTimeMs`, аппаратные циклы либо ожидают сокет, либо
выполняют `SleepInterruptible`/`Sleep`.

Оставшаяся работа приходилась на UI/OpenGL. Таймер мнемосхемы повторно вызывал
`Snapshot` и `ReplaceValues` для неизменившихся тегов. `ReplaceValues`
сбрасывал `GLListID`, поэтому одна и та же линия компилировалась в каждом
UI-кадре после EOF.

Исправление:

- `TRecorderSignalBuffer` получил монотонную `Revision`;
- базовая страница и редактируемый компонент осциллограммы запоминают ревизии
  отображаемых тегов;
- при неизменных ревизиях и длительности окна массив линии не заменяется;
- штатный кэш OglChart (`GLListID`, прежняя роль `needRecompile`) остается
  действительным до изменения данных, осей либо настроек линии.

После исправления нагрузка двух наиболее активных UI/OpenGL потоков в
контрольных секундных срезах снизилась примерно с `140..172 ms/с` на каждый
до `31..109 ms/с`. Остаточная активность соответствует обновлению живых
аппаратных/диагностических тегов и отрисовке остальных компонентов страницы,
а не непрерывному циклу завершившегося файлового источника.
