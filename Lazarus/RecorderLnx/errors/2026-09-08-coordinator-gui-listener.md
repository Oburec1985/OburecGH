# RecorderCoordinator: HTTP listener блокирует/срывает запуск GUI

## Симптом

При обычном запуске вместо рабочей формы сначала показывалось консольное окно.
После включения GUI subsystem отладчик останавливался на
`fServer.Active := True` в listener-потоке.

## Подтверждённые факты

- Проект первоначально собирался без `-WG`, поэтому создавал консольное окно.
- `TFPHTTPServer.Active := True` выполняет цикл listener синхронно; вызов из
  `FormCreate` не позволяет завершить создание и показать форму.
- После первого тестового запуска порт 8765 занимал оставленный экземпляр PID
  8868. Повторный экземпляр получил исключение bind в worker thread.

## Исправление

- В `RecorderCoordinator.lpi` включён `GraphicApplication`, сборка содержит
  `-WG`.
- Listener вынесен из GUI-потока.
- Bind error перехватывается внутри worker и возвращается через `LastError`.
- Из запуска удалено ожидание события `fStarted`: оно взводилось до реального
  bind и не доказывало готовность listener. `Start` теперь возвращает GUI
  немедленно и не зависит от наличия RecorderLnx-клиентов.
- Проверка исходников FPC 3.2.2 показала, что `StopAccepting(False)`/
  `Active=False` только сбрасывает внутренний флаг и не гарантирует пробуждение
  потока, уже заблокированного в `accept`. Поэтому синхронный `WaitFor` из GUI
  мог ждать до появления следующего клиента.
- Listener получил `AcceptIdleTimeout = 50` мс без `OnAcceptIdle` и без
  фиктивного TCP-клиента. `Stop` сбрасывает accepting и сразу возвращает
  управление форме; select timeout ограничивает время, за которое listener
  увидит это состояние. Завершение и освобождение потока контролируются при
  последующем опросе состояния.
- Пока остановка не завершена, кнопка показывает `Останавливается...` и
  отключена. После фактического завершения она снова предлагает запуск.
- Ожидаемый результат `TCP port ... already in use` больше не преобразуется
  UI-слоем в exception: `TryStartService(out Error)` возвращает `False`, а
  форма пишет причину в журнал и показывает обычное сообщение.

## Проверка

Forced-сборка прошла. Без RecorderLnx окно появилось за 167 мс, процесс отвечал,
а `/api/v1/status` вернул `ready`. Параллельный второй экземпляр при занятом
8765 остался отвечающим и не завис. Владелец порта в пользовательском сценарии
оказался ранее оставленным тестовым Coordinator PID 24368; он остановлен.

Lifecycle-тест без клиентов усилен до 100 последовательных циклов с ожиданием
фактического bind. Вызов `Stop` не блокирует вызывающий поток, полное
завершение listener обычно занимает около 62 мс. Forced-сборка
RecorderCoordinator и `git diff --check` прошли.

## Дополнение 2026-09-09: `No REQUEST_METHOD` при старте RecorderLnx

Подтверждено, что исключение `EHTTP: No REQUEST_METHOD passed from server`
возникало не при idle/stop listener, а строго после запуска клиента RecorderLnx.
`TRecorderCoordinatorClientThread.ServerReachable` открывал TCP stream к
Coordinator и сразу освобождал его, не отправляя HTTP request line. FPC принимал
соединение, получал пустую стартовую строку и закономерно поднимал `EHTTP` в
`TRequest.InitRequestVars`.

Preflight сохранён как невыбрасывающая TCP-проверка, но после connect теперь
отправляет полный `GET /api/v1/status HTTP/1.1`, заголовки `Host` и
`Connection: close`, читает ответ до EOF и принимает только валидный HTTP 2xx.
Это не оставляет ни пустого запроса, ни оборванной серверной отправки. Основной
HTTP-запрос клиента идёт как прежде.

Forced-сборка `RecorderLnx.lpi` прошла с exit code 0; `git diff --check`
изменённого Pascal-файла — без ошибок. В сквозной проверке сначала запущен
Coordinator, затем RecorderLnx: оба процесса остались отвечающими, Coordinator
принял регистрацию и heartbeat клиента со `state=ready`; тестовые процессы
после проверки остановлены.
