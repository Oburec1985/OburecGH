# KIP-1: сообщение об отказе записи в /mnt/DATA

## Симптом

Пользователь сообщил, что файловый менеджер не даёт создать каталог внутри `/mnt/DATA` на KIP-1, хотя на остальных KIP запись работает. Точный текст ошибки пока не получен.

## Проверенные факты

- `/dev/sda1` (NTFS, UUID `8A4EE1884EE16D7F`) смонтирован в `/mnt/DATA` как `fuseblk` с `rw`.
- Управляемая запись `/etc/fstab` содержит `uid=1000,gid=1000,umask=0002`; `user` имеет UID 1000, точка принадлежит `user:user` и имеет режим 775.
- Свободно около 3,6 ТБ; доступные журналы не показывают ошибки NTFS/I/O.
- От имени `user` создание уникального пустого каталога непосредственно в `/mnt/DATA` завершилось успешно. Тот же каталог затем удалён; существующие файлы не изменялись.
- Пути `/mnt/data` и `/mnt/Data` отсутствуют; регистр в Linux важен.
- Внутри `/mnt/DATA/usml` действует bind-публикация `MeraFiles`, но она не помешала тесту записи в корне `/mnt/DATA`.

## Вывод и следующий шаг

Отказ записи в корне `/mnt/DATA` на уровне ОС не воспроизведён. Гипотезы о `ro`-монтировании, недостатке места и неверных UID/GID отвергнуты. Для диагностики конкретной операции нужен её точный путь и текст ошибки/скриншот; без них менять mount/fstab/права опасно и необоснованно.

## Повторная проверка самим основным агентом

Через SSH от имени `user` создан обычный (не скрытый) каталог `/mnt/DATA/CodexWriteTest-20260916`. `mkdir` вернул код 0, `ls -ld` показал `drwxrwxr-x user user`; затем `rmdir` этого пустого каталога вернул код 0. Значит успешный результат не зависит от скрытого имени предыдущего теста. Отказ в пользовательском файловом менеджере по-прежнему не воспроизведён; требуется точный путь из адресной строки и текст сообщения.

## Проверка целевого usml

Перед запросом на создание выяснено, что `/mnt/DATA/usml` уже существует (`drwxrwxr-x user user`, время каталога 19:25). `/dev/sda1` по-прежнему смонтирован на `/mnt/DATA` с `rw`. Существующий каталог оставлен без изменений; повторное создание не требуется.
