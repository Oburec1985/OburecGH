# OPC UA: замедление при 1000 тегах

## Симптом

При 1000 читаемых тегах тормозили чтение, запись и интерфейс RecorderLnx.

## Причины

- runtime отправлял отдельный синхронный ReadRequest для каждого тега;
- изменение ServerTimestamp считалось изменением данных и повторно публиковало
  неизменные значения;
- промежуточные команды записи обходились по очереди, хотя OPC нужен только
  последний желаемый уровень;
- успешные массовые записи создавали лишний журнал на каждом цикле.

## Исправление

Чтение объединено в пакетные ReadRequest. Проверка PLC210 показала, что пакет
1000 отвергается `BadTooManyOperations`, поэтому эффективный предел временно
равен 100. Изменение определяется по значению, не по timestamp. OPC-запись на
такте источника отправляет не более одного отличающегося состояния каждого
тега, не повторяет подтверждённые дубли и выполняется перед чтением.

## Регрессия короткого импульса

Вариант latest-only терял нажатие, если `1` и последующий `0` появлялись между
двумя тактами: сервер видел только `0`. Исправлено сохранением переходов:
`1` подтверждается первым WriteResponse, `0` отправляется следующим тактом.
25-секундный auto-preview проекта с 1000 тегами не дал ошибок связи и ни разу
не превысил период 100 мс по добавленной редкой диагностике slow cycle.

## Проверка

Полная сборка Lazarus проходит. Финальная сборка запущена на 40 секунд:
процесс отвечал, CPU за весь запуск около 1.94 с, Working Set около 260 MiB;
процесс после проверки остановлен. Журнал в этом скрытом запуске не обновился,
поэтому живой readback/write результата требует отдельного запуска проекта.

## Повторное проявление на `blinkerplc` — 2026-10-28

Пользователь сообщил, что `blinkerplc` на PLC210 `.130` перестал обновляться,
хотя `Tags_[1]` продолжает работать. Активный конфиг
`C:\Mera Files\RecorderLnx\config\projects\test185_149\default.config.json`
содержит 1106 узлов источника, из них 1004 читаемых; `maxNodesPerRead=1000`.
`blinkerplc` сохранён как читаемый Boolean (`DataType i=1`) с полным NodeId
`ns=4;s=|var|PLC210 OPC-UA.Application.GVL.blinkerplc`. `Tags_[1]` в этом
конфиге — Float с тем же корректным форматом строкового NodeId, но только
записываемый (`readable=false`, `writable=true`), поэтому по нему нельзя
сравнивать путь чтения.

В текущем `C:\Mera Files\RecorderLnx\LogWindows.log` источник `.130` много раз
возвращает на стадии `iterate` `service: status 0x80100000`. OPC UA определяет
код как `BadTooManyOperations`: сервер не принимает число операций в одном
запросе. Значит симптом вызван слишком крупной Read-пачкой, а не повреждённым
адресом `blinkerplc`; после отказа всего ReadRequest цикл источника обрывался и
запускал переподключение.

Исправление: при `BadTooManyOperations` runtime делит размер пачки пополам,
повторяет чтение без переподключения и запоминает допустимый предел на жизнь
сессии. Диагностическая запись содержит новый размер. Проверка после правки:
forced Win64 build `RecorderLnx-opc-read-adaptive.exe` прошёл (237499 строк,
exit 0); основной Recorder оставался запущенным. Повторный сетевой прогон с
`.130` после сборки не выполнялся, поэтому необходимо проверить в новой сборке,
что журнал показывает успешное чтение и адаптированный размер пачки.
