# 2026-09-24 — Редактирование импортированной ГХ не обновляло БДГХ

## Симптом

После импорта ГХ из БДГХ в тег повторное редактирование меняло только объект
калибровки внутри проекта. Исходная запись БДГХ оставалась прежней.

## Причина

Импорт корректно сохранял `TRecorderCalibration.SdbKey`, но общий путь
`EditCalibrationAt -> CommitCalibrationEdit` после подтверждения всегда очищал
`SdbKey`, считая любое редактирование созданием локальной ГХ.

## Исправление

- При подтверждении изменения общей импортированной ГХ сначала обновляется
  запись БДГХ по её точному `SdbKey`.
- Обновление поддерживает JSON-калибровки и совместимые XML/CSV+JSON
  представления масштаба, прямой, таблицы и полинома.
- После успешной записи связь `SdbKey` сохраняется; проект продолжает загружать
  актуальную ГХ из БД.
- Выбор локальной копии по-прежнему снимает связь с БДГХ.
- В диалоге явно указано, когда вариант «Да» обновляет исходную БДГХ.

## Проверка

Forced Windows-сборка `RecorderLnx.lpi` — exit code 0. Общая forced
Linux-сборка — `BUILD_EXIT=0`, `MISSING_LIBS=none`; исправление включено в
DEB 0.1.69 и установлено на MIC-200.

## Остаточный риск

Round-trip на реальном сетевом каталоге БДГХ проверяется общей Linux-сборкой и
последующей пользовательской проверкой на MIC-200.

## Повторное проявление: редактирование из окна pipeline

Пользовательская проверка 0.1.69 показала, что исправление покрывало только
кнопку редактирования в диалоге тега. Двойной щелчок по строке в окне
«Настройка Мульти ГХ» вызывал редактор с исходным объектом и после `OK`
не проходил через `RecorderSdbUpdateCalibration`. Поэтому проектный объект
менялся, а запись БДГХ и её JSON discriminator типа оставались прежними;
масштабный множитель при следующем чтении legacy CSV выглядел таблицей.

Исправлено в `TRecorderCalibrationListDialog.btnPropertiesClick`: редактор
работает с clone, проверяет имя, для связанной через `SdbKey` ГХ сначала
успешно и с проверкой чтением обновляет БДГХ, и только после этого переносит
изменения в проектный объект. `SdbKey` и переименование текущего шага pipeline
сохраняются. При ошибке записи проектная ГХ также остаётся неизменной.

Проверка: forced Windows-сборка `RecorderLnx.lpi` — exit code 0.

## Повторное проявление: аппаратная ГХ и представление в БДГХ

Два обработчика аппаратной ГХ по-прежнему передавали в редактор живой объект
и после `OK` не вызывали запись БДГХ. Кроме того, просмотрщик независимо от
загруженного discriminator всегда открывал вкладку таблицы, поэтому корректно
загруженный `rckScale` выглядел как пустая табличная ГХ.

Теперь связь с источником (`SdbKey` и фактический файл) хранится на объекте
ГХ. Все подтверждённые правки связанного объекта сначала проходят через
единый `RecorderSdbUpdateLinkedCalibration`; только успешная запись и обратная
проверка разрешают commit в реестр. Локальная копия по-прежнему явно снимает
связь. Просмотрщик выбирает представление по `Kind`: scale/linear показывает
параметры и формульный график, таблица оставлена для табличных типов.

Проверка: forced Windows-сборка `RecorderLnx.lpi` — exit code 0.
