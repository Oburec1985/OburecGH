# Firebird: сервер, каталог и применение настроек

**Запрос переключения координатора:** действующий UDP discovery (`Lazarus/SharedUtils/uRecorderLanDiscovery.pas`) только объявляет адреса и не аутентифицирует пакеты; `TRecorderCoordinatorClientThread.ServerReachable` принимает новый адрес только после отказа текущего. Следовательно, объявление .200 не переключает живое соединение с .66. Для управляемого переключения необходима проверяемая команда смены authority, сохранение выбранного адреса на клиенте, прекращение приёма команд старой очереди и подтверждение регистрации у нового координатора. На .200 ранее накоплены pending-команды, поэтому при вводе механизма необходима проверка/отмена устаревших команд до подключения клиентов. Изменений работающих систем по этому пункту пока нет.

**Повторная диагностика АРМ 2026-11-02 16:08 UTC:** API панели .200 сообщает отсутствие RecorderLnx для всех шести машин, тогда как API панели .66 видит все шесть подключёнными в состоянии stopped, в том числе сервер .92. На .200 уже стоят ожидающие команды preview, поэтому нельзя просто перевести клиентов, не разобрав старую очередь: команды могут выполниться неожиданно. На .17/.45/.66/.85 в coordinator-client.ini `AllowRemoteConfig=0` и BaseUrl=127.0.0.1; на .92 и .200 BaseUrl указывает .66. В адресах/идентификаторах панели .200 обнаружены устаревшие записи для .200 и .92. Перенастройка и перезапуск клиентов не выполнены, как и обработка очереди; работа по исправлению продолжается.

**Контрольная точка 2026-11-02:** активным выбором пользователя остаётся Firebird .66 и `/var/opt/mera/SQLdb/recorderlnx.fdb`; ранее созданная пустая база .92 не является текущей целью. На .92 добавлена systemd-зависимость запуска Firebird от `mnt-sda1-base-firebird.mount`; перезагрузка и восстановление после сбоя не проверены. Linux-бинарники RecorderLnx развёрнуты на шести узлах, rcPanel — на .66, .85 и .200; работающие процессы не перезапускались, актуальные исходники после этого развёртывания не устанавливались.

В исходниках исправлено сохранение выбранного локального пути `/home/...`, укорочены названия команд в rcPanel. Экспериментальная постоянная очередь по умолчанию отключена: два независимых координатора могут повторно применить устаревшие настройки, а повторное применение может прервать запись. Тестовый helper изменения прав не установлен; его изменяющие права режимы принудительно отключены из-за гонки подмены каталога. Для завершения нужны единый защищённый координатор, идемпотентное применение и подтверждение ревизии на каждом узле, безопасная подготовка хранилища и сквозная проверка на Linux. Не включать экспериментальные механизмы в production до устранения этих проблем.

**Симптом:** после «поставить всем» адреса различались, вход Firebird .92 отклонялся; выбранный каталог БД не менял полный путь файла.

**Подтверждено:** до исправления app.ini: .92 Host пуст, .200/.45 — .92, .66/.17/.85 — .66; .92 Firebird отклонял зашитые учётные данные и файла БД не было; прежняя БД .66 существует. Абсолютное имя перекрывало выбранный каталог; в локальном Unix дополнительно повторно присоединялся root. .92 /mnt/sda1 — ntfs-3g, Firebird создание файла завершается ошибкой chmod.

**Сделано:** по выбору пользователя создана новая пустая БД на ext4 loop-образе 1 ТиБ в /mnt/sda1/base, подключаемом через fstab с зависимостью от основного диска; каталог /mnt/sda1/base/firebird; текущие учётные данные сервера согласованы с кодом, прежний root-only SYSDBA.password сохранён в .before-recorder-20261102. Существующая база .66 не переносилась и не удалялась. На 6 узлах app.ini выставлены .92 и полный путь на сервере; предыдущие app.ini сохранены как app.ini.before-sql-20261102. Разосланы команды обоим координаторам; они поставлены в очередь, сквозное подтверждение всех экземпляров не получено. Из исходников UI убрано подтверждение рассылки; в настройках изменение каталога обновляет путь файла, DatabaseFileName исправлен для абсолютного Unix-пути.

**Проверка:** isql с .66 и .92 успешно подключился к новой БД; на .92 service active, mount ext4 и зависимость systemd обнаружены. Конфигурации 6 узлов перечитаны. Windows lazbuild -B RecorderCoordinator и RecorderLnx успешны. KIP3 RDP TCP/3389 доступен, файлы RDP проверены.

**Осталось:** Linux-сборка, установка и проверка изменённых RecorderLnx/rcPanel не выполнены. Новая настройка автоматических прав для произвольных каталогов не реализована; текущий ext4-образ подготовлен вручную. Кнопка не гарантирует доставку отключённым клиентам после перезапуска панели. Физический ввод/запись в UI не проверен; отсутствие таблиц при проверке до инициализации — 0 пользовательских таблиц. Открытые процессы могут хранить старые настройки; приложение требуется повторно загрузить/проверить. Лимит созданного образа 1 ТиБ, он разреженный; не гарантирует резервирования места на NTFS. Перезагрузка сервера и восстановление mount не проверены.

**Дополнительная проверка:** изолированные Linux lazbuild -B RecorderCoordinator и RecorderLnx на KIP3 успешны, ldd без отсутствующих библиотек; в исходники включены локальные изменения рабочего дерева. Исполняемые файлы не развёрнуты; сквозная проверка и автоматические права остаются незавершёнными. SHA256 панели 2131cbfc74778eda48bdffedbcaeb5e72455471f573c92cc88caede27dd055a0, RecorderLnx 94c5cff86a763af75c716115b84c7b7e90fcc59977a9ee6745952313b91478c3.

**Уточнение:** пользователь требует именно управления из rcPanel. Сейчас команда хранится только в памяти панели, HostAgent не имеет API изменения SQL-настроек; для работающего Recorder команда сохраняет app.ini сама. Для надёжного применения при выключенном Recorder и после перезапуска панели необходимы постоянное целевое состояние и безопасная доставка через HostAgent, подтверждение каждой машины и проверка. Это не реализовано.

**2026-11-02 — команда .66 из rcPanel на АРМ:** API обоих координаторов показал, что сервер .92 и KIP1/3/4 подключены к rcPanel .66, а rcPanel .200 видит запущенным KIP2, но сервер для него offline. Поэтому команда, отправленная с .200, не доставлялась серверному Recorder. По намерению пользователя вручную записаны Host=192.168.9.66 и Database=/var/opt/mera/SQLdb/recorderlnx.fdb в app.ini всех 6 узлов, команды поставлены обоим координаторам; изменения перечитаны со всех 6 узлов. С .92 выполнен isql SELECT 1 к существующей БД .66 (успех). Старые app.ini сохранены как app.ini.before-kip3-20261102. Открытая до изменения форма может показывать старые данные; графическое обновление не проверено. Причина разделения координаторов не устранена; долговечная доставка rcPanel остаётся незавершённой.
