# Программирование жизненного цикла устройств

Разделять операции на атомарные стадии:

`Discover -> Connect -> Initialize -> Test -> ReadProperties -> Configure -> Start -> Stop -> Disconnect`

Допускать изменение порядка `Test` и `ReadProperties`, только если этого требует протокол. Не скрывать одну стадию внутри другой.

## Именованные значения приборного протокола

- Коды команд, sync/magic, номера протокольных портов и потоков, флаги, служебные размеры и фиксированные значения полей пакета задавать именованными константами в модуле типов соответствующего устройства.
- В месте сборки или разбора пакета не записывать такие значения числовыми литералами. Байтовые смещения локально собираемого пакета можно оставлять числами, если структура последовательна и однозначна.
- Проверять поиском числовых литералов в функциях кодирования пакетов и сопоставлением дампа с описанием протокола.
- Контрольную сумму фиксированной разрядности накапливать в более широком беззнаковом типе; сужать явно только при сериализации или сравнении по модулю разрядности протокола. Проверять на максимальном payload.
## Контракты стадий

### Общие интерфейсы и частные реализации

- Не плодить отдельные интерфейсы под частные возможности конкретного прибора,
  если внешний код может работать через уже существующий общий контракт
  устройства. Интерфейсы нужны, чтобы плагины, UI и сервисные модули
  универсально общались с разными классами.
- Специфику прибора реализовывать в классе-наследнике общего интерфейса:
  через переопределение методов, строковые/типизированные свойства, capability
  checks и безопасные no-op/fallback-ответы для неподдерживаемых свойств.
- Новый частный интерфейс допустим только когда общий контракт принципиально
  не выражает нужную модель: отдельный жизненный цикл, другой владелец ресурса,
  иной потоковый контракт или операция, которую нельзя представить как
  свойство/действие общего устройства без потери смысла.
- Перед добавлением интерфейса задавать вопрос: сможет ли внешний плагин или
  универсальный модуль работать с этим через `IRecorderDevice`/аналогичный
  общий интерфейс? Если да — не добавлять частный интерфейс, а расширить или
  реализовать общий контракт.

### Возврат ошибок

- Каждая функция стадии жизненного цикла должна возвращать код результата: `noError` при успехе либо конкретный код ошибки. Текст и диагностические данные возвращать отдельными выходными параметрами или структурой результата.
- Не использовать `raise`/exception для ожидаемых ошибок связи, таймаута, ответа протокола, состояния прибора, инициализации или конфигурирования. Такие ошибки являются обычным результатом функции и должны обрабатываться вызывающим кодом.
- Исключения допустимы только для нарушения внутренних инвариантов и иных непредвиденных программных дефектов, продолжение после которых небезопасно.
- Не реализовывать безопасный API как `try/except`-обёртку над функцией, которая внутри бросает ожидаемые исключения: отладчик может остановиться на `raise` раньше обработчика. Нижний протокольный уровень также должен возвращать код ошибки.
- При последовательности стадий прекращать цикл на первом результате, отличном от `noError`, сохраняя имя стадии, endpoint и исходный код ошибки.
- Проверять контракт в Lazarus debugger на отключённом приборе, таймауте и некорректном ответе: функция возвращает код ошибки, приложение не показывает исключение и переводит устройство в `offline`.

- `Discover`: находить endpoint и идентификационные данные штатным discovery/broadcast. Не открывать рабочую сессию, не программировать и не менять прибор.
- `Connect`: создать один транспорт и получить монопольную сессию. Не читать свойства и не конфигурировать.
- `Initialize`: выполнить разовые действия для новой сессии: загрузку BIOS/firmware, handshake, ожидание готовности, выдачу session id. Хранить признак успешной инициализации на уровне сессии.
- `Test`: проверить уже открытую сессию безопасной командой без изменения конфигурации. Не открывать краткую probe-сессию непосредственно перед рабочим `Connect` у single-client устройств.
- `ReadProperties`: явно прочитать SN, версию, возможности и число каналов. Ошибку не подменять нулевыми свойствами.
- `Configure`: применить изменяемые параметры. Делать повторяемой и идемпотентной; разрешать многократный вызов в одной сессии.
- `Start`/`Stop`: только управлять сбором. Не повторять `Initialize` и неизменённый `Configure`.
- `Disconnect`: корректно остановить обмен, освободить транспорт и сбросить состояние сессии.
- `Reset`: завершить старую сессию и выполнить полный путь `Connect -> Initialize -> ReadProperties -> Configure`; после успеха обновить UI и кэш свойств.

## Модель состояния

Хранить явное состояние и проверять переходы. Как минимум различать `discovered`, `connected`, `initialized`, `configured`, `running`, `offline`. Отдельно хранить поколение сессии и поколение конфигурации.

При ошибке указывать стадию, endpoint, длительность и текст протокола. Не считать `ping` доказательством готовности прикладного протокола.

## Несколько устройств

Параллелить тяжёлые операции разных независимых устройств по отдельным задачам/потокам. Внутри одного устройства сохранять последовательность стадий и один владелец транспорта. Ограничивать параллелизм, если сеть, шина или сервер прибора имеют общий предел.

Не держать блокировку общего реестра во время сетевого ожидания. Публиковать результат подготовки в реестр короткой атомарной операцией после завершения I/O.

## Явная синхронизация

- Не использовать `WaitFor`/ожидание события как неявную замену модели состояния, если достаточно короткой критической секции и явно читаемого состояния операции.
- Если ожидание действительно необходимо, рядом с ним обязательно указать, какая конкретная операция, ветка или `SetEvent` его разблокирует и почему разблокировка гарантирована также при ошибке и остановке.
- Давать событиям имена по условию завершения (`ListenerStopped`, `ReplyReceived`), а не по действию (`WaitEvent`). Место взвода события должно легко находиться поиском по тому же имени.
- Не ждать сетевого клиента, пакет или прибор в GUI-потоке. Возвращать текущее состояние и завершать ожидание в worker либо через неблокирующее уведомление UI.

## Проверка реализации

### Контроль темпа блоков

- При непрерывном сборе ожидаемое число полных блоков равно
  `N = T / P`, где `T` — длительность сбора, `P` — настроенный период
  обновления данных.
- Считать блоки отдельно для каждого устройства от успешного `Start` до
  `Stop` или последнего корректного блока. Не подменять их числом TCP-пакетов:
  один логический блок может состоять из нескольких пакетов.
- На коротком прогоне допустимо небольшое отклонение из-за неполных интервалов
  старта и останова. Устойчивое отставание или рост расхождения означает
  потерю, повтор, неверную сборку либо неверно запрограммированный размер блока.

1. Построить таблицу «публичный метод -> разрешённые команды протокола -> изменение состояния».
2. По логам восстановить фактическую последовательность для первого запуска, повторного `Configure`, `Start/Stop`, `Reset` и потери связи.
3. Проверить, что discovery не изменяет прибор и не создаёт конфликтующую TCP-сессию.
4. Проверить холодный запуск нескольких устройств, разный порядок и время ответов, одно неработающее устройство и повторный сброс.
5. Убедиться, что SN и версия читаются после каждого нового подключения и обновляются после reset/reconnect.
6. Для циклов чтения и обработки дополнительно применить навык `runtime-programming`.

## Правила изменения существующего драйвера

Сначала измерить и зафиксировать текущую последовательность по логам. Затем разрезать смешанный метод на стадии без изменения протокольного порядка внутри каждой стадии. Добавлять тесты переходов и счётчики вызовов, чтобы `Initialize` выполнялся один раз на сессию, а `Configure` — только по требованию.

### Атомарные итерации

- Вносить за одну итерацию только одно логически независимое изменение поведения, протокола, синхронизации или производительности. Допускается объединять несколько правок одной причины, если по коду и контрактам доказано, что они не меняют команды и формат протокола, их порядок, таймауты, сетевые сессии, переходы состояния и конфигурацию прибора.
- Перед изменением фиксировать исходный сценарий и измеряемый показатель; после изменения повторять тот же сценарий и сравнивать результат.
- Не объединять в одном шаге исправление жизненного цикла, изменение таймаутов, распараллеливание, переработку буферов и оптимизацию вычислений, если хотя бы одна правка может повлиять на обмен с прибором. Чисто локальные изменения обработки уже принятого блока можно объединить, когда они устраняют одну подтверждённую горячую операцию и имеют общий контрольный замер.
- Если изменение не дало ожидаемого результата или вызвало регрессию, отменить только эту итерацию. Не маскировать её дополнительными правками.
- Переходить к следующему изменению только после успешной сборки и проверки предыдущего. В журнале явно записывать: единственное изменение, ожидаемый эффект, фактический эффект и решение оставить либо отменить.
- Исключение допустимо только для минимальных сопутствующих правок, без которых одно изменение не компилируется; перечислять их как часть той же атомарной причины.
