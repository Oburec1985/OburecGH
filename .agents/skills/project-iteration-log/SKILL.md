# Журнал итераций проекта

После каждой пользовательской итерации обновлять журнал проекта, включая
частично выполненную и заблокированную работу.

## Выбор файла

Использовать первый существующий вариант:

1. путь, явно заданный правилами проекта;
2. `cach/notes_last_state.md`;
3. `Docs/iteration-log.md`;
4. `CHANGELOG.md`;
5. создать `cach/notes_last_state.md`, если в проекте уже есть `cach/`;
6. иначе создать `iteration-log.md` в корне проекта.

Не создавать второй журнал, если подходящий уже существует. Журнал хранить
внутри проекта, а не в домашней папке агента.

## Формат записи

Новую запись помещать сверху после заголовка файла:

```markdown
## YYYY-MM-DD HH:MM — краткий результат

**Запрос:** Одно-два предложения с целью пользователя своими словами.

**Сделано:** Короткий перечень только фактически выполненного.

**Проверка:** Сборка, тест, лог, ручная проверка либо «не выполнялась» с причиной.

**Статус:** готово / частично / заблокировано. Для незавершённого — следующий шаг.
```

Если итерация была только вопросом или исследованием, в `Сделано` записать
полученный вывод и просмотренные источники. Не выдавать предположение за
выполненную работу.

## Контракт трёх следов

Одного журнала недостаточно: журналы проектов лежат вне vault и не попадают в
семантический поиск. Поэтому каждая итерация оставляет **три следа**, и только
вместе они дают нерушимость контекста.

1. **Журнал проекта** — запись по формату выше. Это подробный источник правды.
2. **Строка в «Состоянии работ»** — `D:\works\AGrav\00_Система\Состояние_работ.md`,
   таблица «Последние две недели». Колонки: дата, проект, результат в одну строку,
   статус, следующий шаг, путь журнала, тег памяти. Полную запись туда не копировать.
3. **Факт в MemoryDB** — `save_memory_fact` со строгим набором полей:
   - `tags`: `project:<имя>` и `iteration`, при необходимости предметные теги;
   - `project_context`: имя проекта;
   - `source_file`: путь журнала из шага 1.

   Факт пишется как самостоятельное знание: что сделано, чем проверено, что
   осталось. Не дублировать весь текст журнала, не сохранять догадки, временные
   гипотезы, секреты и большие листинги.

Без третьего следа результат не находится по смыслу из другого чата; без второго
его не видно в точке входа; без первого нечего проверять. Если какой-то слой
недоступен (например, MCP-сервер памяти не запущен), записать это в статусе
итерации как ограничение, а не молчать.

## Подъём контекста перед работой

Перед новым циклом по уже существующему проекту:

1. Открыть `Состояние_работ.md` и найти проект в таблице свежих работ или в
   реестре активных проектов — там указан путь журнала.
2. Прочитать последнюю запись журнала и незакрытый следующий шаг.
3. При необходимости поднять более старые решения: `search_memory_facts` с тегом
   `project:<имя>`, затем глобальный индекс и семантический поиск по vault.
4. Проверить найденное по первоисточнику; память и эмбеддинги — навигация, а не
   доказательство.

## Ссылки вместо дублей

- В журнале давать ссылку на подробный документ, error-журнал или артефакт, а не
  пересказывать его целиком.
- В «Состоянии работ» и глобальном индексе — только навигация.
- Существующие проекты и их журналы перечислены в `Состояние_работ.md`; перед
  созданием нового журнала проверить, не указан ли уже путь для этого проекта.

## Правила краткости

- Переформулировать смысл, не копировать чат дословно.
- Обычно укладывать запись в 4–10 строк.
- Не дублировать подробные протоколы, списки файлов и большие логи.
- Объединять последовательные технические попытки внутри одной пользовательской
  итерации в одну итоговую запись.
- Не переписывать старые записи и не удалять сведения о незавершённой работе.

## Когда записывать

Обновлять журнал перед финальным ответом пользователю. Если работа прервана
ошибкой, лимитом или внешней блокировкой, всё равно сохранить текущий результат
и точный следующий шаг.

Проверить перед ответом:

- запрос переформулирован понятно;
- записано только реально сделанное;
- указана проверка;
- статус соответствует фактическому состоянию;
- строка в «Состоянии работ» добавлена или обновлена;
- факт в MemoryDB сохранён с тегами `project:<имя>` и `iteration` и с `source_file`
  на журнал.
