# RunTime-программирование

RunTime — рабочая фаза после запуска: сбор данных, обработка блоков, расчёты,
запись и обновление экрана. Код этой фазы выполняется многократно, поэтому даже
небольшая лишняя операция быстро становится дорогой.

Загрузка проекта, чтение конфигурации, `Init`, `Configure` и подготовка перед
стартом к RunTime не относятся. Тяжёлую подготовку следует выполнять именно там.

## Основные правила

1. **Не выделять память во время работы.** Заранее создавать объекты и буферы
   нужного размера. При повторном использовании очищать их, а не создавать
   заново.
2. **Не искать объекты по именам в повторяющемся коде.** При настройке один раз
   находить теги, каналы, калибровки и обработчики, затем хранить прямые ссылки
   или индексы.
3. **Обрабатывать данные блоками.** Читать, копировать, преобразовывать и
   записывать массив целиком, а не по одному отсчёту.
4. **Вынести подготовку из рабочего цикла.** Таблицы, коэффициенты, планы
   расчётов и связи между объектами строить при инициализации или изменении
   конфигурации.
5. **Не повторять одинаковый расчёт.** Сохранять результат вместе с признаком,
   какие входные данные использовались. Пересчитывать только после их изменения.
6. **Отделять расчёты от отображения.** Значения, нужные другим расчётам,
   обновлять независимо от открытой страницы. Геометрию, подписи и графики
   готовить только для видимых компонентов.
7. **Не обновлять неизменившееся.** Данные и настройки должны иметь номер
   версии или флаг изменения. Если версия прежняя, не пересобирать линию,
   таблицу, файл настроек или команду устройства.
8. **Использовать оптимизированные операции над массивами.** Для копирования,
   суммирования и линейных преобразований применять готовые блочные функции.
   AVX/SSE или другие аппаратные ускорения добавлять там, где измерения
   подтверждают пользу.

## Данные и уведомления

- Источник складывает данные в заранее выделенный кольцевой буфер.
- Уведомление сообщает только: «появился новый блок». Сам массив в очередь
  уведомлений не копируется.
- Каждый потребитель хранит номер последнего прочитанного блока и забирает
  только новые блоки непосредственно из кольца под короткой блокировкой.
- Длина логического блока определяется частотой опроса и периодом обновления:
  `число отсчётов = частота × период`.
- Границы сетевых пакетов не должны менять логические блоки, историю сигнала
  или порядок отсчётов.
- Калибровку, оценки, уведомление клиентов и обновление экрана выполнять после
  готовности целого логического блока, а не после каждого сетевого пакета.

## Расчёты

- Результаты общих расчётов публиковать через принятый в проекте интерфейс.
  В Recorder таким интерфейсом являются теги.
- Если тег уже содержит МО, СКЗ, максимум или другую оценку, следующий расчёт
  должен читать готовое значение, а не повторно обходить его отсчёты.
- Медленно меняющийся общий параметр рассчитывать один раз на блок и
  использовать во всех зависимых каналах. Пример: температура холодного спая.
- Постоянные для конфигурации величины рассчитывать один раз: коэффициенты ГХ,
  FFT-планы, оконные коэффициенты, индексы полос, таблицы соответствий каналов.
- Вместе с сохранённым результатом хранить номер версии его входов. При
  изменении любого входа результат помечать устаревшим.
- Оптимизация не должна менять физический порядок преобразований:
  `код АЦП → аппаратная ГХ → компенсация → канальная ГХ`.

## Потоки, сеть и файлы

- Один рабочий проход должен устойчиво завершаться раньше заданного периода.
  Наличие `Sleep` само по себе не доказывает, что поток не загружает CPU.
- При отсутствии работы поток должен ждать событие, данные или окончание
  периода, а не постоянно проверять состояние в пустом цикле.
- Сеть и файлы читать и записывать порциями в готовый буфер.
- Не писать подробный лог для каждого успешного пакета или отсчёта. В рабочем
  режиме хранить счётчики и редкие итоговые сообщения; подробный лог включать
  только для диагностики.
- Не пытаться скрыть медленный код добавлением новых потоков. Сначала измерить,
  какой поток и какая операция расходуют процессорное время.

## Поиск зависаний и падений

- Повторяющейся или длительной операции назначать короткий постоянный код.
- Перед входом атомарно сохранять код, поток, время и краткий контекст; очищать
  отметку в `finally` при любом выходе.
- Независимый watchdog с редким периодом проверяет активные отметки. Если
  допустимое время превышено, он один раз пишет `STUCK`: код операции, поток,
  контекст и длительность. Повторять запись только при изменении состояния или
  через большой контрольный интервал.
- Подробные `ENTER/EXIT` включать временно для узкого подозрительного участка.
  В штатной работе хранить отметки в памяти и писать только `STUCK`, `ERROR` и
  редкие итоги, чтобы диагностика сама не создавала нагрузку.
- Отличать зависание от штатного ожидания: предел брать из периода операции и
  сетевого/файлового таймаута с разумным запасом.
- Если есть `ENTER`, но нет `EXIT`, сначала проверять место между ними. Если
  процесс завершился аварийно, последняя отметка должна сохраниться в журнале
  или аварийном снимке.

## Отображение

- Расчётные теги и алгоритмы продолжают обновляться независимо от выбранной
  страницы.
- Отображение обновляется отдельным периодическим вызовом наподобие
  `DoRepaint`.
- За один вызов обрабатывать только активную видимую страницу и её видимые
  компоненты. Скрытые страницы не должны готовить линии и вызывать перерисовку.
- Видимый компонент пересобирает изображение только при изменении данных,
  масштаба, осей, стиля или размера.
- Для OpenGL использовать один штатный признак необходимости пересборки
  (`needRecompile` или аналог), а не несколько несогласованных флагов.
- Осциллограмму собирать из последних готовых блоков несколькими копированиями.
  Не добавлять в линию точки по одной и не терять отсчёты без явно включённого
  прореживания.
- После остановки или окончания данных число пересборок линий должно перестать
  расти.

## Жизненный цикл устройства

Разделять состояния:
`Connect → Init → Configure → Start → Stop → Disconnect`.

- `Init` выполнять один раз на открытую сессию устройства.
- `Configure` выполнять только после изменения настроек, явного сброса или
  восстановления потерянной связи.
- Обычные `Start` и `Stop` не должны повторять `Init` и `Configure`.
- Успешный `TestLink` подтверждает связь и не делает конфигурацию устаревшей.
- Явный Reset закрывает прежнюю сессию и требует полного
  `Connect → Init → Configure`.

Проверка: два запуска без изменения настроек дают один `Init/Configure` и две
пары `Start/Stop`.

## Проверка перед сдачей

- В повторяющемся коде нет создания объектов, изменения размеров буферов,
  разбора конфигурации и поиска по именам.
- Данные передаются и обрабатываются блоками; нет лишних копий массива.
- Общие и промежуточные результаты считаются один раз на нужном уровне:
  конфигурацию, сессию, блок, канал или кадр.
- У каждого сохранённого результата понятны входы и условие пересчёта.
- При отсутствии новых данных рабочие потоки ждут, а графические линии не
  пересобираются.
- Скрытые страницы не выполняют подготовку изображения.
- Сравнены результаты до и после оптимизации; измерительный тракт не изменился.
- Измерено процессорное время отдельных потоков до и после исправления.
- Проект собран, а основной рабочий сценарий проверен.
