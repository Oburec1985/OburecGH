# Расширяемая архитектура программ

Проектировать изменение так, чтобы следующая реализация добавлялась локально, без переписывания общего сценария и несвязанных частей программы.

## Основной принцип

Разделять стабильный жизненный цикл или оркестрацию, предметные этапы с ясными контрактами, сменные реализации этапов, состояние выполнения и итоговый результат.

Для алгоритма по умолчанию рассматривать пайплайн:

`Prepare → Validate → Calculate → Finalize/Report`.

Названия и число этапов определяет предметная область. Не создавать пустые абстракции только ради этого шаблона.

## Проектирование

1. Сначала описать верхнеуровневый сценарий предметными действиями.
2. Для каждого этапа определить вход, выход, предусловия, ошибки и допустимые побочные эффекты.
3. Стабильную последовательность держать в базовом алгоритме или оркестраторе; вариантное поведение передавать через наследование, стратегию, интерфейс, композицию или зарегистрированный шаг — выбрать самый простой подход для проекта.
4. Общие данные выполнения объединять в типизированный контекст только когда они образуют настоящую модель состояния. Не превращать контекст в неограниченный контейнер.
5. Проверку входных данных завершать до дорогого расчёта. Частичный результат публиковать только если это явно предусмотрено контрактом.
6. Формирование отчёта и представление результата отделять от расчётного ядра, если они могут меняться независимо.
7. Добавление новой реализации должно преимущественно создавать новый класс, стратегию или этап, а не расширять цепочку условных ветвей в общем коде.
8. Не раскрывать внутренние детали этапа вызывающему коду; верхний уровень должен читаться как сценарий.

## Базовая и конкретная реализация

Базовый алгоритм может задавать порядок шагов, общие инварианты, обработку ошибок и освобождение ресурсов. Конкретная реализация определяет только действительно изменяемые операции. Не наследовать ради повторного использования нескольких строк: при независимом комбинировании поведения предпочитать композицию.

Разрешать переопределение только в предусмотренных точках расширения. Критические инварианты жизненного цикла не должны случайно обходиться наследником.

## Проверка решения

- Верхнеуровневый код показывает полный сценарий без деталей вычисления.
- У каждого этапа одна предметная ответственность и проверяемый контракт.
- Можно заменить или добавить реализацию без изменения несвязанных этапов.
- Ошибка имеет владельца: понятно, на каком этапе она возникла и кто завершает/очищает выполнение.
- Общая логика не дублируется в конкретных реализациях.
- Есть тест базового порядка стадий и отдельные тесты вариантных реализаций.
- Для runtime-участков дополнительно применён `runtime-programming`; для локальной структуры процедур — `clear-code`.

## Сдача результата

Кратко объяснить пользователю стабильный сценарий, точки расширения, выбранный механизм полиморфизма или композиции и как будет добавляться следующая реализация.
